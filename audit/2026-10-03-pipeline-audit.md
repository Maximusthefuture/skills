# Аудит пайплайна java-dev-flow: скиллы, агенты, хуки

Дата: 2026-10-03. Claude Code CLI 2.1.274. Модели тестов: Haiku 4.5 (основная и субагенты), для сравнения бюджета листинга — Sonnet 5 и Opus 5.
Песочница: копия `orders-service` с `.claude/`, собранным из исходников этой папки, и git-коммитом базы. Ваш `orders-service` не трогался.
Потрачено на прогоны: около $6.

## Итог

Каркас собран правильно. Скиллы ссылаются друг на друга без битых ссылок и имён. Агенты грузятся, работают параллельно, только на чтение и возвращают статусы. Stop-хук `critic-gate` реально блокирует ход и заставляет запустить `critic`. Юнит-тесты зелёные.

Сейчас пайплайн **работает не так, как задуман**. Причин пять, и все они в окружении и настройках, а не в логике скиллов:

1. Включён оригинальный плагин `backend-design@synced`. Из-за него задублированы 13 скиллов и 6 агентов, и Haiku выбирает оригинал вместо форка. Его хуки падают на каждом Write/Edit.
2. Хуки форка `backend-design-java` нигде не зарегистрированы. Шаг «обработай предупреждения хуков» в фазе 4 ничего не делает.
3. Листинг скиллов не влезает в бюджет. На Haiku у всех ваших скиллов видно только имя без описания.
4. После автокомпакции от `java-dev-flow` остаются первые 5000 токенов. Фаза 5 (critic), фаза 6, маршруты B/C/P и красные флаги дальше этой границы и пропадают.
5. Тесты на машине не запускаются: `mvn` нет в PATH, в `orders-service` нет `mvnw`, Docker не запущен.

**Haiku как основная модель оркестратора не годится**, даже после исправлений. В S-задаче он пропустил RED, не вызвал `java-tdd` и скрыл в отчёте упавший полный прогон. Haiku годится для узких субагентов (судья хука, прогон тестов, сбор diff, Explore). Для ревьюера и критика — с оговорками, см. раздел 3.3.

## 3. Результаты тестов на Haiku

### 3.1. Маршрутизация: 22 trigger-эвала

**Как есть.** 21/22. Вход в `java-dev-flow` срабатывает благодаря строке в `CLAUDE.md` («Любую задачу по коду начинай со скилла java-dev-flow»). Haiku прямо пишет: «Следуя CLAUDE.md, начну со скилла java-dev-flow».

Вторичная маршрутизация слабая:
- #7 «ночная джоба» → `backend-design:think-before-coding`, то есть оригинал с примерами на Prisma и Python, а не форк;
- #10 «ревью ветки» → встроенный `code-review` Claude Code, а не `java-code-review`;
- #12 «почисти бесполезные тесты» → `java-dev-flow` вместо `test-audit` (FAIL);
- #6 «пагинация на 2M строк» классифицирована как S, хотя меняется публичный контракт GET, то есть это M.

**С исправленными настройками** (`enabledPlugins: {"backend-design@synced": false}`, `skillListingBudgetFraction: 0.05`). 20/22, но маршруты стали точнее:
- #10 → `java-code-review`, #12 → не уходит в оркестратор, #15 «прод горит» → `debugging-discipline`, #17 «проверь changeset» → `migration-safety`, #7 — без дубля оригинала;
- #2 (багфикс) и #5 (рефакторинг): за 4 хода Haiku только искал файлы и до скилла не дошёл. Описание «вызывают ПЕРВОЙ» Haiku соблюдает нестабильно.

Каждый эвал прогонялся один раз, поэтому разница ±2 — в пределах шума. Вывод держится на качестве маршрутов, а не на счёте.

### 3.3. Агенты `java-code-reviewer` + `critic` на diff с дефектами

В diff заложено: changeset `archived_at NOT NULL` без default на таблице ~12M строк, IDOR в `POST /orders/{id}/archive`, `findAll()` с фильтром в памяти, нет проверки статуса и идемпотентности, и `POST /orders` ломается, потому что entity не заполняет NOT NULL-колонку.

| | java-code-reviewer | critic |
|---|---|---|
| Запуск | параллельно, одним сообщением ✔ | ✔ |
| Только чтение | ✔ (хэши файлов до и после совпали) | ✔ |
| Предзагрузка `skills:` | ✔ сразу вызвал `collect_diff.sh` скилла | — |
| Первая строка — статус | ✘ (статус на 5-й строке) | ✔ `Статус: BLOCKERS …` |
| Нашёл | IDOR, статус, идемпотентность, пагинация, NOT NULL, N+1 | NOT NULL на 12M, IDOR, `findAll` + N+1, индекс без CONCURRENTLY, статус, идемпотентность |
| Пропустил | **`POST /orders` перестаёт работать** (требование 5 спеки) | то же; rolling deploy по существу не разобран |
| Ошибки | «компиляция требовала разрешения на mvnw» — `mvnw` в проекте нет; находки продублированы в разделе «Соответствие спеке» | неверный механизм: на PG 11+ `ADD COLUMN NOT NULL` без default на непустой таблице падает сразу, а не держит блокировку 5–20 минут; выдуманный флаг Liquibase |
| Скиллы | — | 6 скиллов, все из **оригинала** `backend-design:*` (лимит в агенте — 2–5, «бери форк») |
| Токены / время | 38.7k / 106 с | 53.2k / 173 с |
| Размер отчёта | 7.7k симв. (~3k токенов в основной контекст) | 14.4k симв. (~5.7k токенов) |

Стоимость всего прогона на Haiku — $0.47. Вывод: на Haiku агенты структурно исправны и ловят очевидное, но пропускают связки («NOT NULL в схеме + entity без значения = сломан createOrder») и ошибаются в механике PostgreSQL. Правило «находки агента — гипотезы, проверь по коду» здесь обязательно.

### 3.4. `critic-gate` (prompt-хук) end-to-end

Судья — Haiku 4.5, фоновая модель Claude Code. Claude Code оборачивает ваш промпт так: «Based on the conversation transcript above, has the following stopping condition been satisfied?», — и передаёт **всю переписку** (в тесте 24–39 сообщений), а не только итоговое сообщение.

## 4. Что доработать — по приоритету

### P0 — ломает работу сейчас

**4.1. Отключить оригинальный плагин `backend-design@synced`.** В `~/.claude/settings.json`:
```json
"enabledPlugins": { "backend-design@synced": false }
```
Или `/plugin` → Installed → Disable, или выключить его на claude.ai. Проверено: после этого дубли скиллов и агентов и падающие хуки на `python` исчезают. Пока плагин включён, правило «если оба — бери форк» (`SKILL.md`, раздел «Имена скиллов»; `critic.md`, шаг 2) не работает: форк в проекте стоит **без префикса**, и модель видит пару `migration-safety` / `backend-design:migration-safety`, а не `backend-design-java:…`.

**4.2. Зарегистрировать хуки форка.** Добавить в `orders-service/.claude/settings.json` блок `PostToolUse` из README (вариант 2) и скопировать скрипты в `~/.claude/hooks/backend-design-java/`. Иначе [SKILL.md:148](../java-dev-flow/SKILL.md) — пустой шаг. В песочнице с регистрацией хуки отработали.

**4.3. Сделать тесты запускаемыми.** Добавить `mvnw` в `orders-service` (`mvn -N wrapper:wrapper`, команды в `CLAUDE.md` — через `./mvnw`) или положить `mvn` в PATH. Запустить Docker. Сейчас фазы 4–5 упираются в «нет Docker», и Haiku эту остановку обошёл молча (3.5).

**4.4. Бюджет листинга скиллов.** В `.claude/settings.json` проекта (или в пользовательском):
```json
"skillListingBudgetFraction": 0.05,
"skillOverrides": {
  "anthropic-skills:docx": "off", "anthropic-skills:pptx": "off", "anthropic-skills:xlsx": "off",
  "anthropic-skills:pdf": "off", "anthropic-skills:morning": "off",
  "anthropic-skills:google-workspace": "off", "anthropic-skills:import-memory": "off",
  "anthropic-skills:test-audit": "off"
}
```
Последний пункт — потому что в проекте лежит своя копия `test-audit`. Значения `skillOverrides`: `on`, `name-only`, `user-invocable-only`, `off` ([документация](https://code.claude.com/docs/en/skills#override-skill-visibility-from-settings)). В песочнице проверен только `skillListingBudgetFraction`. Дополнительно сократи описания: `java-dev-flow` 997 симв., `java-tdd` 910, `java-extensibility-review` 1438, `java-spec-review` 1194. Ключевое — первой фразой: при обрезке остаётся начало.

**4.5. Компакция обрезает оркестратор.** После автокомпакции Claude Code возвращает каждый вызванный скилл, но только первые 5000 токенов, и не больше 25 000 на все скиллы вместе. Где что лежит (оценка по калибровке 2.5 символа на токен):

| Раздел `java-dev-flow/SKILL.md` | Начало |
|---|---|
| Фаза 4 | ~5.3k токенов |
| Фаза 5, critic | ~5.8k / 6.4k |
| Фаза 6, маршруты B/C/P | ~7.6k / 7.8k |
| «Когда остановиться», «Красные флаги» | ~8.7k / 9.5k |

В `java-tdd` «Когда работа готова» начинается на ~6.4k, красные флаги — на ~7.8k. После компакции модель помнит классификацию и дизайн, но не помнит про critic, отчёт и доказательства. Как исправить — 5.1.

### P1 — снижает качество

**4.6. В режиме OpenSpec нет `critic`.** Группа «Проверка» перечисляет только `java-code-reviewer`:
- [config.yaml:42](../java-dev-flow/assets/openspec/config.yaml), [config.yaml:54](../java-dev-flow/assets/openspec/config.yaml);
- [schema.yaml:283](../java-dev-flow/assets/openspec/schemas/java-flow/schema.yaml), [schema.yaml:316](../java-dev-flow/assets/openspec/schemas/java-flow/schema.yaml);
- [templates/tasks.md:17](../java-dev-flow/assets/openspec/schemas/java-flow/templates/tasks.md);

В `orders-service` сегодня включили OpenSpec, поэтому там M и L пойдут через change, и критик запустится только при срабатывании хука. Нужно добавить задачу «агент `critic` по diff, параллельно с `java-code-reviewer`» и обновить скопированный `orders-service/openspec/config.yaml`.

**4.7. `critic-gate` не видит изменений через Bash.** Правило 4 («…коммит, запуск команд») пропускает `git apply`, `sed -i`, генераторы, а также правки, которые сделал субагент. Как исправить:
- в правиле 4 уточнить: «запуск команд, **которые не меняли production-файлы**»;
- добавить пункт: «изменения через Bash (`git apply`, `sed`, скрипты, генераторы) и через субагентов — тоже код»;
- для надёжности поставить вторым Stop-хуком детерминированный `critic_gate.py`. Он видит diff на диске и не тратит токенов. Его 30 юнит-тестов остались в scratchpad прошлой сессии и потеряны — их нужно восстановить в `java-dev-flow/assets/hooks/tests/`.

**4.8. `collect_diff.sh` падает в репозитории без коммитов** (exit 128 — ровно состояние `orders-service`: всё staged, коммитов нет). Тогда `java-code-reviewer` остаётся без diff. Исправление проверено ([collect_diff.fixed.sh](2026-10-03-haiku-harness/collect_diff.fixed.sh)): в начале `find_base` в [collect_diff.sh:19](../java-code-review/scripts/collect_diff.sh):
```bash
  if ! git rev-parse --verify -q HEAD >/dev/null; then
    git hash-object -t tree /dev/null; return   # без коммитов: база — пустое дерево
  fi
```
Применить в `java-code-review/`, `review/` и пересобрать `review/java-code-review.skill`.

**4.9. Модели агентов.** У `critic` и `java-code-reviewer` стоит `model: inherit`. Если основная сессия на Haiku, ревью тоже на Haiku и пропускает связки (3.3). Рекомендация: `model: sonnet` у обоих, как у агентов `backend-design-java`. Если нужна дешёвая первая линия, заведи отдельного `java-code-reviewer-lite` на Haiku.

**4.10. Встроенный `/code-review` конкурирует с `java-code-review`** (#10 в 3.1). Добавить в `CLAUDE.md` проекта: «Ревью diff — скилл `java-code-review` или агент `java-code-reviewer`, не встроенный `/code-review`». В описание `java-code-review` — «вместо встроенного code-review для Java».

**4.11. Устаревшие копии:**
- `java-dev-flow.skill` — без `critic` и `assets/hooks`;
- `jira-tasks.skill` и `~/.claude/skills/jira-tasks` — без нарезки плана, хотя `skill-map.md` на неё ссылается;

## 5. Как тратить меньше токенов и работать на Haiku

### 5.1. Сжать то, что грузится всегда

Оценка по калибровке на Haiku: ваш русский markdown — около 2.5 символа на токен.

| Что попадает в основной контекст на M-задаче | Токены |
|---|---|

### 5.3. Что нужно, чтобы на Haiku работало

Haiku хорошо выполняет короткие императивные шаги. Длинную прозу и правила «никогда не делай X» он соблюдает плохо: в 3.5 нарушены три правила из прочитанного скилла. Поэтому:

1. **Видимые описания:** P0 4.1 и 4.4.
2. **Жёсткие ворота кодом, а не текстом.** Детерминированный хук **tdd-guard**: PostToolUse на Edit/Write в `src/main/**` смотрит транскрипт хода. Если с последней правки `src/test/**` не было запуска теста с падением, хук возвращает в `additionalContext` «RED не был показан: запусти тест и покажи падение до правки кода». Это дёшево и не требует модели. Аналогично Stop-хук **evidence-guard**: последний `mvn`/`gradle` в ходе завершился ошибкой, а в итоговом сообщении нет слов «упал / не запускался / Docker» → block с причиной.
3. **Чеклист выхода в начале скилла.** Пять строк в `java-tdd`: «1) тест 2) запуск → красный, покажи строку падения 3) код 4) запуск → зелёный 5) весь набор; упавшее и незапущенное — в отчёт». Haiku следует нумерованным чеклистам лучше, чем таблицам в середине документа.
4. **Формат классификации — шаблоном, а не примером:** «Маршрут: <фича|изменение|багфикс|рефакторинг|схема|производительность> · …». Добавить правило «меняется публичный контракт (параметры, пагинация, формат ответа) → не S»: Haiku ошибся на #6.
5. **Роли моделей:** оркестратор — Sonnet или Opus; Haiku — `test-runner`, Explore, судья хука, сбор diff; `critic` и `java-code-reviewer` — Sonnet.

### 5.4. Стоимость хуков

- **`critic-gate` (prompt).** Один вызов Haiku на каждое завершение хода во **всех** проектах, потому что хук стоит в `~/.claude/settings.json`. Судья получает всю переписку, и в длинной сессии запрос растёт вместе с ней. Перенеси хук в `.claude/settings.json` Java-проектов или замени на `critic_gate.py` (0 токенов) — либо поставь оба, скрипт первым. Отдельно стоит проверить поведение на очень длинной сессии: что будет, когда переписка не влезет в окно Haiku. В тестах этого не было.
- **Хуки форка** — 0 токенов, пока молчат. Находки идут в контекст коротким блоком. Это правильная цена.

## 6. Выводы

1. **Логика пайплайна корректна:** фазы, ворота, разделение ролей, параллельные ревьюер и критик, хук-страховка. Ссылки, имена, копии и юнит-тесты в порядке. Нужные возможности Claude Code есть в установленной версии.

3. **Главный скрытый риск — компакция.** Оркестратор и `java-tdd` длиннее 5k токенов, поэтому в длинных задачах фаза 5 (`critic`), отчёт и правило доказательств теряются. Лечится разбиением файлов (5.1) и укладывается в ту же работу, что и экономия токенов.

5. **Haiku — для узких субагентов, не для оркестратора.** Без механических ворот (tdd-guard, evidence-guard) он пропускает RED и приукрашивает отчёт. Ревьюер и критик на Haiku полезны как первая линия, но пропускают связки и ошибаются в механике БД — им лучше Sonnet.
6. **Экономия токенов в основной сессии** — около 30–50% на M-задаче: сжать `SKILL.md` до ≤5k, грузить скиллы по месту, вынести прогон тестов, обзор кода, `java-extensibility-review` и `java-spec-review` в субагентов и ограничить длину отчётов агентов (5.1–5.2).
