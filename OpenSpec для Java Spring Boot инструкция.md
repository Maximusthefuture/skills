# OpenSpec для Java Spring Boot: инструкция

Oct 23, 2026 · @Maximus

## Главное

OpenSpec договаривается с агентом о том, **что** строить, до появления кода. Как этот код будет выглядеть, он сам по себе не контролирует: спеки описывают поведение, а шаг verify сверяет реализацию с артефактами и не получает правил из config.yaml ([документация OpenSpec](https://openspec.dev/docs/project-config)).

Поэтому качество кода держится на трёх опорах, а OpenSpec служит процессом, в который они встроены:

| Опора | Что это | Где живёт |
| --- | --- | --- |
| Эталон | 1–2 модуля, написанных так, как нужно. Агент копирует образец намного лучше, чем следует пожеланию «пиши чисто» | `src/main/java/...` |
| Рамки | Короткие конвенции и явные запреты | `AGENTS.md`, `openspec/config.yaml` |
| Обратная связь | Линтеры и тесты, которые валят сборку | Maven или Gradle, хуки агента, CI |

## Подготовка

CLI ставится один раз на машину, `openspec init` запускается один раз на репозиторий ([установка](https://openspec.dev/docs/installation), [настройка проекта](https://openspec.dev/docs/setup)).

1. Проверь Node.js: нужен 20.19.0 или новее (`node --version`).
2. Установи CLI: `npm install -g @fission-ai/openspec@latest` (или `brew install openspec`). Проверка: `openspec --version`.
3. В корне проекта запусти `openspec init` и выбери свой инструмент (Claude Code, Cursor и т.д.). После этого перезапусти IDE или агента.
4. Добавь в профиль `verify`, он не входит в базовый набор из шести workflow: `openspec config profile` → отметь `verify` (для большого проекта ещё `onboard`) → `openspec update` ([профили](https://openspec.dev/docs/profiles)).
5. Закоммить папку `openspec/` и папку инструмента (`.claude/` или `.agents/`) вместе с кодом.

После init появится такая структура:

```
openspec/
├── config.yaml     настройки и контекст для агента
├── specs/          живые спеки: как система работает сейчас
└── changes/        изменения в работе
    └── archive/    завершённые изменения
```

Каждый workflow ставится в двух формах с одинаковыми инструкциями: навык (`openspec-propose`) и команда (в Claude Code — `/opsx:propose`). Если в проекте остался старый `openspec/project.md`, init его не переносит: попроси агента перенести полезное в `config.yaml`, проверь результат и удали файл.

## Фундамент: AGENTS.md и config.yaml

В `AGENTS.md` (или `CLAUDE.md`) описано, как должен выглядеть код, а в `openspec/config.yaml` — как планировать изменения. Оба файла держи короткими: всё их содержимое попадает в контекст агента, и многословные правила ухудшают результат ([документация OpenSpec](https://openspec.dev/docs/project-config)). Ниже стартовые версии под Spring Boot; замени пакеты и стек на свои.

### AGENTS.md

```markdown
# AGENTS.md

## Стек
- Java 21, Spring Boot 4.x, PostgreSQL, Spring Data JPA, Flyway
- Тесты: JUnit 5, AssertJ, Mockito, Testcontainers

## Команды
- После каждой правки: ./gradlew spotlessApply compileJava   (Maven: mvn spotless:apply compile)
- Перед закрытием задачи: ./gradlew check                    (Maven: mvn verify)

## Архитектура
- Пакеты по фичам: com.example.app.<feature>.{web,service,repository,domain}
- Зависимости только вниз: web -> service -> repository
- Контроллер не обращается к репозиторию напрямую
- Эталон: пакет com.example.app.order. Новый код повторяет его структуру и стиль

## Конвенции
- Внедрение только через конструктор, поля private final
- DTO — record; JPA-сущности не выходят за пределы service
- @Transactional только на публичных методах service
- Ошибки: доменные исключения + один @RestControllerAdvice
- Валидация входа через Bean Validation на DTO
- Логирование через SLF4J
- Пакеты помечены @NullMarked, nullable только явно через @Nullable

## Запрещено
- Добавлять зависимости без согласования
- Интерфейсы, фабрики и базовые классы под одну реализацию
- Классы-свалки *Utils, *Helper, *Manager
- catch (Exception e), проглатывание исключений
- Комментарии, пересказывающие код; закомментированный код
- @SuppressWarnings, // NOPMD, CHECKSTYLE:OFF, правки конфигов линтеров

## Готово, когда
- ./gradlew check зелёный: формат, компиляция с Error Prone и NullAway,
  Checkstyle, PMD, SpotBugs, ArchUnit, тесты
```

### openspec/config.yaml

Поле `context` получают все шаги, `rules` подмешиваются только при создании своего артефакта, `operations` влияет на apply и archive.

```yaml
schema: spec-driven

context: |
  Стек: Java 21, Spring Boot 4, PostgreSQL, Gradle.
  Конвенции и запреты описаны в AGENTS.md, соблюдать всегда.
  Эталон реализации: пакет com.example.app.order. Новый код повторяет его структуру.
  Новые зависимости только с явного согласия.
  Все артефакты писать на русском.

rules:
  proposal:
    - Один change покрывает одну capability, не больше 300 слов
  specs:
    - Требования описывают поведение через API и данные, без деталей реализации
  design:
    - Указать модуль-образец, по которому делается реализация
    - Перечислить новые классы с пакетом и слоем (web, service, repository, domain)
    - Описать контракт API (метод, путь, DTO, коды ответов) и миграции Flyway
    - Обосновать каждую новую абстракцию и зависимость; при одной реализации интерфейс не нужен
  tasks:
    - Задача затрагивает один слой и не больше 2-3 файлов
    - Сначала тест (slice-тест или Testcontainers), потом реализация
    - Последняя задача — проход упрощения без изменения поведения

operations:
  apply:
    guidance:
      - После каждой правки запускать ./gradlew spotlessApply compileJava
      - Перед отметкой задачи запускать ./gradlew check; отмечать только при зелёном результате
      - Не добавлять ничего, чего нет в design.md; если план не подходит, остановиться и спросить
      - Не отключать проверки и не править конфиги линтеров
```

## Что заменить под свой проект

Во всех примерах этого документа вместо твоих данных стоят заглушки. Одни и те же значения встречаются в нескольких файлах, поэтому сначала реши, что подставлять, по таблице ниже, а потом пройди по файлам и отметь каждый пункт.

### Значения, которые повторяются

Каждое значение меняй сразу во всех местах из третьей колонки, иначе агент получит противоречивые указания.

| Заглушка в примерах | Что вписать | Где встречается |
| --- | --- | --- |
| `com.example.app` | Базовый пакет проекта | AGENTS.md (Архитектура), тест ArchUnit |
| `com.example.app.order`, «пакет order» | Эталонный пакет | AGENTS.md (Архитектура), config.yaml (`context`), запрос на ревью, формулировки в `/opsx:propose` |
| `./gradlew spotlessApply compileJava`, `./gradlew check` | Команды твоей сборки (Maven: `mvn spotless:apply compile`, `mvn verify`) | AGENTS.md (Команды, Готово), config.yaml (`operations.apply`), запрос на упрощение, хуки агента |
| Java 21, Spring Boot 4, PostgreSQL, JPA, Flyway | Твой стек | AGENTS.md (Стек), config.yaml (`context`, `rules.design`), шаблон design.md в форке схемы |
| `web`, `service`, `repository`, `domain` | Имена твоих слоёв | AGENTS.md (Архитектура), config.yaml (`rules.design`), тест ArchUnit |
| 30 строк на метод, вложенность 3 | Твои лимиты | Конфиг Checkstyle или PMD, запрос на ревью |
| `main` | Имя основной ветки | Запрос на ревью, Spotless `ratchetFrom` |

### AGENTS.md (корень репозитория)

- [ ] **Стек:** версии Java и Spring Boot, база данных, способ доступа к данным, инструмент миграций, библиотеки тестов.
- [ ] **Команды:** оставь только Gradle или только Maven.
- [ ] **Архитектура:** базовый пакет, структура пакетов (по фичам или по слоям), имя эталонного пакета.
- [ ] **Конвенции:** убери строки, которые не совпадают с твоими решениями (например, `@NullMarked` — только если включаешь NullAway), и добавь свои (Lombok или нет, как маппятся DTO).
- [ ] **Запрещено:** допиши проблемы, которые агент уже приносил в твой код.
- [ ] **Большой проект:** добавь раздел «Антиобразцы» со списком старых пакетов, которые нельзя копировать.

### openspec/config.yaml

- [ ] **`context`:** стек, эталонный пакет, язык артефактов (строку про русский убери, если нужны английские).
- [ ] **`rules.design`:** тип API (REST, gRPC, очереди) и инструмент миграций.
- [ ] **`rules.tasks`:** какие тесты пишутся первыми (slice-тесты, Testcontainers).
- [ ] **`operations.apply`:** команды твоей сборки.
- [ ] **Большой проект:** два правила для design из раздела про большой проект.

### build.gradle.kts или pom.xml

- [ ] Подключи плагины: Spotless, Error Prone с NullAway, Checkstyle, PMD, SpotBugs с FindSecBugs; ArchUnit — в тестовые зависимости.
- [ ] NullAway: укажи свой пакет в опции `AnnotatedPackages` или включи режим `OnlyNullMarked`.
- [ ] Пропиши лимиты Checkstyle и PMD, те же, что в запросе на ревью.
- [ ] **Большой проект:** Spotless `ratchetFrom` на твою основную ветку, файлы подавлений для старых нарушений.

### Тест ArchUnit (`src/test/java/.../ArchitectureTest.java`)

- [ ] Базовый пакет в `@AnalyzeClasses`, пакеты слоёв в `definedBy`, шаблон в `slices().matching`.
- [ ] При пакетах по фичам вместо `layeredArchitecture` подойдёт Spring Modulith.
- [ ] **Большой проект:** оберни правила в `FreezingArchRule.freeze(...)`.

### Запросы на ревью и упрощение

- [ ] Сохрани их в репозитории как команды агента (в Claude Code — файлы в `.claude/commands/`), чтобы не копировать вручную.
- [ ] Подставь эталонный пакет, свои лимиты и имя основной ветки.

### Хуки агента (в Claude Code — `.claude/settings.json`)

- [ ] Хук после каждой правки запускает твою быструю команду.
- [ ] Хук запрещает правки конфигов линтеров: укажи их пути (например, `config/checkstyle/`, `config/pmd/`).

### Форк схемы (если делаешь)

- [ ] В `openspec/schemas/<имя>/templates/design.md` поправь секции «Контракт API» и «Изменения БД» под свой тип API и инструмент миграций.
- [ ] Впиши имя схемы в `config.yaml`: `schema: <имя>`.

## Новый проект

Первые два change — это каркас и эталонный срез, а не бизнес-фичи. Всё, что агент напишет потом, будет копией этого кода, поэтому его ты проверяешь построчно.

OpenSpec силён в дельтах к уже существующей системе ([Thoughtworks Radar](https://www.thoughtworks.com/es-es/radar/tools/openspec)), поэтому на пустом репозитории сначала нужно создать то, к чему эти дельты будут применяться.

1. Сгенерируй проект в Spring Initializr ([start.spring.io](https://start.spring.io)): это быстрее и предсказуемее, чем просить агента.
2. Запусти `openspec init`, положи `AGENTS.md` и `config.yaml` из раздела выше.
3. **Change 1 — каркас.** Подключение форматтера и линтеров (список внизу) в строгом режиме, структура пакетов, глобальный `@RestControllerAdvice`, тест ArchUnit, базовый тест на Testcontainers. В новом проекте нет легаси, поэтому все проверки включаются сразу как ошибки, без baseline.
4. **Change 2 — эталонный срез.** Одна простая, но полная фича: эндпоинт, сервис, репозиторий, миграция Flyway, DTO, обработка ошибок, тесты на каждом слое. Доводишь её до состояния «пишем так и только так», затем делаешь archive: в `openspec/specs/` появляется первая спека.
5. Пропиши пакет этой фичи как эталон в `AGENTS.md` и в `context` в `config.yaml`.
6. Дальше каждая фича идёт по циклу из раздела ниже, а задача формулируется как «сделай X по образцу пакета order».

## Большой существующий проект

В большом проекте спеки на всю систему заранее не пишутся: спека на capability появляется, когда её впервые затрагивает какой-нибудь change. Главная опасность здесь в другом — агент копирует окружающий код, включая его худшие части.

1. **Init и правила.** `openspec init`, затем `AGENTS.md` с архитектурой как она есть. Отдельно впиши «антиобразцы» — пакеты, которые нельзя брать за образец.
2. **Эталон.** Найди лучший существующий модуль и объяви его эталоном. Если подходящего нет, первым change отрефактори один модуль до стандарта.
3. **Линтеры только на новый код.** Включить всё сразу как ошибки не получится: старый код даст тысячи нарушений. Существующие нарушения замораживаются, новые валят сборку:
   - Spotless с `ratchetFrom 'origin/main'` форматирует только изменённые файлы;
   - NullAway с опцией `OnlyNullMarked` проверяет только пакеты с `@NullMarked`, их добавляешь по мере переработки;
   - в ArchUnit `FreezingArchRule.freeze(rule)` запоминает текущие нарушения и падает только на новых;
   - для Checkstyle, PMD и SpotBugs текущие нарушения выносятся в файл подавлений (baseline).
4. **Первая задача через onboard.** Если включил `openspec-onboard`, он найдёт в коде небольшую стартовую задачу и проведёт через весь цикл за 15–20 минут ([навыки](https://openspec.dev/docs/skills)).
5. **Сначала explore.** Перед propose в незнакомой части кода запусти `openspec-explore`: он только читает и исследует, код не пишет.
6. **Маленькие changes и никакого попутного рефакторинга.** Добавь в `config.yaml` правила для design:

```yaml
rules:
  design:
    - Перечислить существующие классы, которые меняются, и причину
    - Попутный рефакторинг запрещён; если он нужен — отдельный change
```

Если проект состоит из нескольких репозиториев, планирование можно вынести в отдельный репозиторий-store (бета, см. [настройку проекта](https://openspec.dev/docs/setup)).

## Цикл одной фичи

Качество кода решается на шаге 3, при ревью design.md и tasks.md: поправить план стоит минуты, переписать 800 строк — часы. Команды ниже даны в форме Claude Code; в других инструментах те же workflow вызываются как навыки `openspec-*` ([навыки](https://openspec.dev/docs/skills)).

&#91;embedded content: цикл одной фичи · 7 шагов, 2 петли возврата\]

Правки плана делаются до появления кода; всё, что нашли verify и ревьюер, возвращается в apply.

1. **Explore (по желанию).** `/opsx:explore`, если задача ещё не ясна. Он обсуждает и исследует код, но ничего не пишет.
2. **Propose.** `/opsx:propose сделать X по образцу пакета order`. В `openspec/changes/<name>/` появятся proposal.md, дельты спек, design.md и tasks.md; кода на этом шаге нет.
3. **Ревью плана.**
   - proposal и specs просматриваешь быстро: то ли строим, учтены ли крайние случаи.
   - design.md читаешь всерьёз: указан образец, перечислены новые классы с пакетом и слоем, описаны контракт API и миграции, каждая абстракция обоснована.
   - tasks.md: задачи мелкие, тест идёт первым, последняя задача — упрощение.
   - Правки вносишь через `/opsx:update`: он показывает каждую правку и записывает её только после подтверждения.
4. **Apply в свежей сессии.** `/opsx:apply <name>`. Агент идёт по tasks.md и отмечает выполненные задачи, а при неясной задаче или ошибке останавливается и спрашивает. Хук запускает быструю проверку после каждой правки; задача отмечается только при зелёном `./gradlew check`. Коммить после каждой задачи или группы задач.
5. **Verify.** `/opsx:verify` выдаёт отчёт по полноте, корректности и согласованности с замечаниями уровней CRITICAL, WARNING и SUGGESTION. Сам он ничего не меняет: CRITICAL исправляешь и запускаешь verify заново.
6. **Проход качества.** Отдельный ревьюер и упрощение, см. следующий раздел. verify сверяет код с планом, но не оценивает его качество.
7. **Archive.** `/opsx:archive` сливает дельты спек в `openspec/specs/` и переносит change в `changes/archive/`. Если задачи не закончены, он предупредит и спросит.

## Проход качества

Качество кода проверяет отдельный агент в чистом контексте: автор склонен защищать свой код, а verify сверяет код только с планом. После apply и verify запусти два запроса — сначала ревью, потом упрощение — и посмотри итоговый дифф (не файлы целиком).

### Запрос на ревью

```
Ты ревьюер. Прочитай openspec/changes/<name>/design.md, AGENTS.md и дифф ветки относительно main.
Код не меняй. Найди нарушения по списку, для каждого укажи файл, строку и как исправить:
1. Отступления от эталона (пакет order): структура, именование, обработка ошибок
2. Абстракции без второй реализации: интерфейсы, фабрики, базовые классы
3. Дублирование логики
4. Нарушения слоёв: контроллер ходит в репозиторий, JPA-сущности в API
5. @Transactional не на service, внедрение не через конструктор
6. Широкие catch, проглоченные исключения, голый RuntimeException
7. Методы длиннее 30 строк, вложенность глубже 3
8. Комментарии-пересказы, мёртвый и закомментированный код
9. Зависимости, которых нет в design.md
10. Тесты, проверяющие реализацию вместо поведения (всё замокано)
Ответ: список замечаний по убыванию важности, без общих слов.
```

### Запрос на упрощение

```
Упрости код change <name> без изменения поведения: убери дубли, лишние абстракции,
мёртвый код и лишние комментарии. Контракты API не меняй.
./gradlew check должен остаться зелёным.
```

Каждое замечание, которое повторяется от change к change, переноси в правила (см. следующий раздел).

## Когда правил не хватает

Если агент раз за разом игнорирует правило, переведи его на более надёжный уровень: из текста в шаблон артефакта, из шаблона в проверку сборки.

| Уровень | Пример | Надёжность |
| --- | --- | --- |
| Строка в AGENTS.md или в rules | «Не делать интерфейс под одну реализацию» | Агент может проигнорировать |
| Секция в шаблоне design.md | «Новые абстракции и обоснование» | Пустую или натянутую секцию сразу видно на ревью |
| Проверка в сборке | Правило ArchUnit, лимит в Checkstyle | Обойти нельзя: сборка красная |

### Форк схемы

`config.yaml` только добавляет инструкции и не меняет набор и структуру артефактов. Для этого схему форкают ([схемы](https://openspec.dev/docs/customize-schemas)):

1. `openspec schema fork spec-driven spring` — копия появится в `openspec/schemas/spring/`.
2. Добавь секции в `openspec/schemas/spring/templates/design.md`, оставив заголовок `#` первой строкой:

```markdown
## Образец
Пакет, по которому делается реализация.

## Новые и изменяемые классы
| Класс | Пакет | Слой | Новый или изменяемый |

## Контракт API
Метод, путь, DTO запроса и ответа, коды ответов.

## Изменения БД
Миграции Flyway.

## Новые абстракции и зависимости
Каждая с обоснованием. Пусто — значит, их нет.
```

3. Проверь схему: `openspec schema validate spring`.
4. Укажи её в `config.yaml`: `schema: spring`. Новые changes пойдут по ней, старые останутся на прежней схеме.

Форк — это снимок: `openspec update` его не трогает, и улучшения встроенной схемы в него не попадают.

### Петля улучшения

Каждое замечание ревьюера, которое повторяется от change к change, поднимай на уровень выше по таблице. Обычно через 2–3 недели набор правил стабилизируется.

## Шпаргалка

Команды агента даны в форме Claude Code; полный список — в [навыках](https://openspec.dev/docs/skills) и [CLI](https://openspec.dev/docs/cli).

### В чате с агентом

| Команда | Что делает |
| --- | --- |
| `/opsx:explore` | Обсуждает идею и исследует код, ничего не пишет |
| `/opsx:propose <описание>` | Создаёт change: proposal, дельты спек, design, tasks |
| `/opsx:update` | Правит план change; каждую правку ты подтверждаешь |
| `/opsx:apply <name>` | Реализует задачи из tasks.md |
| `/opsx:verify <name>` | Отчёт о соответствии кода плану (нужен профиль с verify) |
| `/opsx:sync` | Сливает дельты спек в `specs/` без архивации |
| `/opsx:archive <name>` | Сливает дельты и переносит change в архив |

### В терминале

| Команда | Что делает |
| --- | --- |
| `openspec init` | Подключает OpenSpec к проекту |
| `openspec update` | Обновляет навыки и команды в проекте; сами они не обновляются |
| `openspec config profile` | Выбор набора workflow и формы установки |
| `openspec list`, `openspec list --specs` | Активные changes; спеки с числом требований |
| `openspec view` | Сводка по спекам и changes на одном экране |
| `openspec status --change <name>` | Какие артефакты готовы и что делать дальше; удобно в новой сессии |
| `openspec show <name> --diff` | Предложение и дифф требований |
| `openspec validate --all` | Проверка структуры всех changes и спек |
| `openspec schema fork spec-driven <name>` | Копия схемы для настройки |

## Линтеры для Java Spring Boot

Агенту помогают только проверки, которые запускаются в самой сборке и валят её с понятной ошибкой: плагины IDE он из терминала не видит. Порядок в таблице — от самых быстрых проверок к самым медленным.

| Инструмент | Что делает | Когда запускать |
| --- | --- | --- |
| Spotless + palantir-java-format или google-java-format | Сам приводит код к единому стилю, а в `check` проверяет форматирование | После каждой правки (`spotlessApply`) |
| Error Prone | Плагин компилятора: типичные баги (ошибки в equals, проигнорированный результат, неверные форматные строки) становятся ошибками компиляции | При каждой компиляции |
| NullAway + JSpecify | Плагин Error Prone: запрещает разыменовывать возможный null в пакетах с `@NullMarked` | При каждой компиляции |
| Checkstyle | Размер и структура: длина методов и классов, число параметров, вложенность, цикломатическая сложность, именование, star-импорты, запрещённые импорты | Перед закрытием задачи (`check`) |
| PMD | Запахи дизайна: god class, когнитивная сложность, пустые catch, неиспользуемый код, лишние условия | Перед закрытием задачи |
| SpotBugs + FindSecBugs | Анализ байткода: ошибки с null, утечки ресурсов, проблемы многопоточности; FindSecBugs добавляет уязвимости (инъекции, слабая криптография) | Перед закрытием задачи или в CI |
| ArchUnit | Архитектура в виде тестов: слои, циклы между пакетами, внедрение через поля, generic-исключения, место `@Transactional` | Вместе с тестами |
| Spring Modulith | Альтернатива слоевым правилам ArchUnit при пакетах по фичам: проверяет границы модулей одним тестом | Вместе с тестами |
| SonarQube | Сводная аналитика и quality gate на новый код | В CI; в процессе работы агент его не видит |

**Error Prone** даёт самую быструю обратную связь: ошибку компиляции агент исправляет сразу. Начиная с версии 2.43 для его запуска нужен JDK 21 или новее ([релизы Error Prone](https://github.com/google/error-prone/releases)).

**NullAway** особенно уместен на Spring Boot 4: весь портфель Spring перешёл на JSpecify, а NullAway валит сборку, если `@Nullable`-значение используется без проверки в пакете с `@NullMarked` ([обзор миграции на Spring Boot 4](https://lidarmonitor.kapernikov.com/news/spring-boot-4-migration-what-to-expect-and-how-2-x-3-x-journey)). JSpecify-режим NullAway ещё дорабатывается, и с лямбдами в API Spring и Reactor возможны ложные срабатывания ([блог Spring](https://spring.io/blog/2025/11/12/null-safe-applications-with-spring-boot-4/)).

**Checkstyle и PMD** частично пересекаются. Удобно разделить их так: Checkstyle отвечает за размеры и структуру, PMD за дизайн. Если два инструмента не нужны, большую часть закроет один PMD.

### Пример теста ArchUnit

```java
@AnalyzeClasses(packages = "com.example.app", importOptions = ImportOption.DoNotIncludeTests.class)
class ArchitectureTest {

    @ArchTest
    static final ArchRule layers = layeredArchitecture().consideringAllDependencies()
            .layer("Web").definedBy("..web..")
            .layer("Service").definedBy("..service..")
            .layer("Persistence").definedBy("..repository..")
            .whereLayer("Web").mayNotBeAccessedByAnyLayer()
            .whereLayer("Service").mayOnlyBeAccessedByLayers("Web")
            .whereLayer("Persistence").mayOnlyBeAccessedByLayers("Service");

    @ArchTest
    static final ArchRule noCycles =
            slices().matching("com.example.app.(*)..").should().beFreeOfCycles();

    @ArchTest
    static final ArchRule noFieldInjection = GeneralCodingRules.NO_CLASSES_SHOULD_USE_FIELD_INJECTION;

    @ArchTest
    static final ArchRule noGenericExceptions = GeneralCodingRules.NO_CLASSES_SHOULD_THROW_GENERIC_EXCEPTIONS;
}
```

### Настройка под агента

- **Только ошибки, без предупреждений.** Предупреждения агент игнорирует.
- **Строгость по типу проекта.** В новом проекте всё включено сразу, в большом существующие нарушения замораживаются (см. раздел про большой проект).
- **Две команды.** Быстрая после каждой правки: `spotlessApply` плюс компиляция. Полная перед закрытием задачи: `./gradlew check` или `mvn verify`. Обе прописаны в `AGENTS.md` и в `operations.apply` в `config.yaml`.
- **Запрет на обходы.** Агент любит глушить проверку вместо исправления: `@SuppressWarnings`, `// NOPMD`, `CHECKSTYLE:OFF`, правка конфига линтера. Кроме правила в `AGENTS.md`, поставь хук, который блокирует изменения в конфигурации линтеров и ищет новые подавления в диффе.
