# Что хотим сделать потом

Идеи, которые обсудили, но пока не делаем. Когда берём пункт в работу, убираем его отсюда.

## Из Lavish (github.com/kunchenguid/lavish-axi, MIT)

- **Отчёты наблюдателя в HTML.** Сейчас наблюдатель пишет отчёт в markdown. Хотим HTML-страницу:
  - таблицы и графики: стоимость по задачам, частые ошибки агентов, где рой застревает;
  - показ на вкладке наблюдателя;
  - замечание к фрагменту отчёта уходит в следующий запуск наблюдателя или становится задачей.

  Выбор элемента и текста — тот же, что в HTML-плане задачи.
- **Lavish как есть для задач с HTML-результатом** (вёрстка, макеты, наша страница):
  - кнопка «Открыть в Lavish» запускает `npx lavish-axi <файл>` с `LAVISH_AXI_TELEMETRY=0`;
  - мост переносит его замечания в наш протокол, агент получает их через `wait()`.

  Минус — ещё один сервер со своими зависимостями.

## Рой

- **Наблюдатель учится на замечаниях к диффу.** Похожие замечания повторяются — наблюдатель предлагает правило в роль агента.
  *Сделано наполовину:* данные до него доходят — итог задачи (`outcome.reviewComments.texts`, `outcome.acceptance`)
  несёт ваши замечания к диффу и к странице приёмки и вердикт «принята / возвращена». Осталось попросить в
  `examples/runner/observer-prompt.md` искать повторяющиеся замечания и предлагать из них правило для роли (target
  `project`, файл инструкций роли).
- **Ещё один CLI, например Gemini:** шаблон в `runners.*.example.json`, разбор вывода сессии, хуки.
- **Стоимость задачи во время сессии.** Сейчас лимит `maxCostUsd` проверяется только в конце сессии.
- **Черновик задачи агентом.** Одна строка или ссылка на тикет → сессия только на чтение смотрит код и заполняет форму:
  описание, файлы, команду, подготовку (быстро / стандарт / тщательно), путь к контракту. Человек правит и запускает.
- **Автовливание задач с низким риском.** Правило в `runners.json`: задачи по расписанию, правки только в тестах, зелёная
  проверка вливания и ревью без WARNING — вливаются сами. Утром сводка «что влито» с «Откатить». Опирается на проверку
  вливания и откат, которые уже есть.
- **«Сразу реализовать» после «Принять change».** Галочка: после приёмки и вливания OpenSpec-change задача его реализации
  создаётся сама, без похода в форму.
- **Доказательства от тестировщика в пакете приёмки.** Тестировщик запускает сервис и прикладывает вывод curl / ответы к
  `checks`, чтобы человек смотрел готовое, а не запускал сам.
- **Раннее ревью по шагам (необязательное).** Для «тщательной» подготовки: подзадача с коммитом закрыта → ревьюер
  смотрит её подсказкой, без блокировки; PASS по-прежнему в SYNC. Делать, только если итоги задач покажут, что поздние
  ERROR дорого стоят: сначала считать время и деньги раундов исправлений.
- **Мелочи:** заглушка «собираю…», пока строится страница приёмки; время в очереди отдельно от DISCUSS в итоге задачи
  (сейчас наблюдатель видит «долгое обсуждение» там, где задача ждала агентов); `build({tests})` — часть тестов поверх
  `verifyCommand` (агент подбирает команду сам и промахивается).

## Проверить

- **Хуки Qwen вживую** (`examples/qwen-hooks/`), когда будет доступен LM Studio.
- **Контракт API на настоящем Maven-проекте.** Проверено на заглушке `mvnw` и подменённом `~/.m2`
  (`AGENT_NETWORK_M2_REPO`); вживую — настоящий `mvn install`, `_remote.repositories`, генерация интерфейсов
  openapi-generator в сервисе.
- **Уведомления `notify-send` на Linux.** Проверены тестом с подставным отправителем; один раз увидеть вживую.
