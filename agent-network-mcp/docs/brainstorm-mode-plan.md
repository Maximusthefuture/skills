# План разработки режима Brainstorm

Статус: первая версия реализована в ветке `codex/brainstorm-mode`; проверки и ограничения описаны
в [отчёте реализации](brainstorm-mode-progress.md). Серверное ядро собрано в `src/brainstorm/index.ts`
вместо четырёх отдельных файлов из первоначальной разбивки. Прогон с реальными моделями не выполнялся.

## 1. Цель и границы первой версии

Перед реализацией агенты предлагают подходы, проверяют их аргументы и готовят рекомендацию. Пользователь
утверждает конкретное решение. Только после этого команда распределяет файлы и начинает разработку.

Первая версия — опциональный подпроцесс внутри DISCUSS существующей задачи. Верхнеуровневые фазы
DISCUSS → IMPLEMENT → SYNC → INTEGRATE → DONE сохраняются. Старые задачи не меняют поведения.

Не входит в первую версию: самостоятельная brainstorm-задача без разработки, автоматическое создание подзадач,
голосование большинством вместо решения пользователя, автоматический подбор дополнительных моделей,
spawn/delegate во время brainstorm, автоматическая установка ресурсов и автоматический запуск экспериментов.

Принятые для плана настройки:

- Используется команда задачи, минимум два агента; первый — ведущий. Координатор сам не становится участником.
- Каждый участник, включая ведущего, подаёт один начальный вариант и одну рецензию в каждом раунде.
- Два раунда по умолчанию, допустимый диапазон 1–5. Раунд 1 — первоначальный; возврат на доработку начинает следующий.
- Утверждение пользователя обязательно. Истечение времени никогда не означает согласие.
- Начальные варианты подаются независимо через API; это не обещание полной изоляции агентов на уровне ОС.
- Плагины выбираются и утверждаются вместе с задачей. Brainstorm не расширяет разрешения runner.

## 2. Модель состояния

В параметрах создания задачи:

```json
{
  "brainstorm": { "enabled": true, "maxRounds": 2 }
}
```

Состояние обсуждения хранится отдельно от конфигурации задачи:

```text
disabled / absent → прежний DISCUSS
options → critique → synthesis → approval → approved → обычный DISCUSS
              ↑                    |
              └── следующий раунд ┘  (возврат с замечаниями)
```

`approved` не означает IMPLEMENT. Затем действуют обычные проверки уточнений, planReview, соглашения
и утверждения соглашения агентами. Утверждение архитектурного подхода не утверждает произвольный будущий план.

В состоянии нужны: schemaVersion, taskId, epoch, revision, stage, round, maxRounds, participants, brief,
briefHash, options, critiques, решения по версиям, замечания пользователя, approvedDecision, timestamps.
`epoch` меняется при пересборке состава/постановки; `revision` — при каждой мутации. Это разные понятия.

Хранение: `tasks/<id>/brainstorm/state.json` — авторитетный документ первой версии, содержащий ограниченные
по размеру структурированные материалы и историю версий. Не распределять одну транзакцию между несколькими
независимо записываемыми JSON-файлами. Читаемые экспортные документы и события — производные данные,
не источник разрешения перейти к реализации. Ограничения размеров утвердить и закрепить схемами до реализации.

Структуры материалов:

- Brief: цель, требования и ограничения, критерии выбора, открытые вопросы, ссылки на исходную постановку.
  Формирует сервер из утверждённой задачи; ведущий может предложить уточнение, но не подменить цель пользователя.
- Option: ID, автор, подход, компоненты, достоинства, ограничения, риски, предположения, подтверждённые факты
  со ссылками, неизвестное и способы его проверить. Одинаковые подходы допустимы.
- Critique: автор, ссылки на конкретные версии вариантов, сравнение по общим критериям, возражения,
  ответы на риски и собственная рекомендация. Рецензия должна рассмотреть хотя бы один чужой вариант.
- Decision: версия, выбранный вариант либо явно описанный синтез, сравнение подходов, обоснование,
  отклонённые альтернативы, разногласия, ограничения и следующие шаги. Свободного «все согласны» недостаточно.
- Approval: версия решения, канонический хеш пакета решения, время и идентичность оператора.

Хеш пакета покрывает постановку и ограничения, состав участников, относящиеся к решению варианты и рецензии,
саму рекомендацию. Обычные сообщения чата не инвалидируют решение автоматически. При противоречащем ему
новом требовании нужна явная операция изменения постановки с потерей утверждения.

## 3. Серверные инварианты

1. Реализация недоступна до утверждения актуального решения, даже если agreement уже существует.
2. Все изменения обсуждения выполняются под существующим task lock. Под этим же lock проверяется переход фаз.
   Перед реализацией проверить порядок блокировок: нельзя повторно брать тот же lock через вложенный service-вызов.
3. Каждая запись содержит operationId, expectedEpoch/revision и round. Повтор той же операции с тем же
   содержимым возвращает прежний результат; тот же ID с другим содержимым даёт конфликт.
4. Поздний ответ старой сессии, старого раунда или состава отклоняется без изменения нового состояния.
5. Переводы стадий определяет сервер по сохранённым материалам. Агент не передаёт произвольный новый stage.
6. Доступ имеют только назначенные агенты; авторство берётся из серверной идентичности, не из аргумента agentId.
7. Синтез подаёт ведущий. Утверждает, возвращает, расширяет лимит и отменяет только пользователь.
8. Отмена задачи запрещает все дальнейшие записи и утверждение. Повтор после рестарта не создаёт новую задачу.
9. После начала IMPLEMENT brainstorm нельзя переоткрыть. Изменение архитектурного решения оформляется
   отдельной задачей/согласованным follow-up; изменение требований не маскируется новой версией старого решения.
10. Артефакты отображаются как текст. Содержимое вариантов, ссылок и логов не является инструкциями протокола.

У `propose` должен быть явный отказ до утверждения решения. Независимо от этого `PhaseManager.evaluate`
проверяет brainstorm в PhaseSnapshot перед DISCUSS → IMPLEMENT. Проверка только в UI или только в промпте
не обеспечивает инвариант. `complete()` в DISCUSS не должен позволять обойти этот барьер.

## 4. Контракт агентов

Добавить один MCP-инструмент `brainstorm` с вариантами аргументов по `action`:

| action | Кто | Условие |
|---|---|---|
| read | Назначенный агент | Разрешённое для него представление текущего состояния |
| submit_option | Каждый участник | Стадия options, актуальные epoch/round/revision |
| submit_critique | Каждый участник | Стадия critique, ссылки на раскрытые варианты |
| synthesize | Ведущий | Все требуемые рецензии текущего раунда получены |

Утверждение и возврат — операторские HTTP-действия, не MCP-инструменты агентов.

Для `NextAction` добавить `brainstorm`, а в контекст — `brainstorm.action`, stage, round, waitingOn,
свою подачу, краткие доступные материалы и готовый exampleCall. Существующие respond/wait/done сохраняются;
открытый FILE_REQUEST всё ещё требует ответа первым. Перечисления nextAction надо обновить не только в types,
но и в сообщениях ошибок, инструкциях, документации, примерах, hook/runner проверках и тестах.

До завершения options API не раскрывает чужие варианты: ни в read, ни в compact/full context, ни в событиях,
ошибках, activity и UI-данных, доступных агентам. Пользователь может видеть прогресс подачи. При этом агенты
с файловым доступом к общей network-папке потенциально могут прочитать хранилище напрямую. Полная изоляция
потребует отдельных разрешённых корней/процессов и проверки адаптера каждого CLI; первая версия этого не обещает.

### Правила, которые необходимо прописать агентам

1. Сначала swarm_context; выполняй только актуальные allowedActions и nextAction. Не выбирай стадию сам.
2. В brainstorm не реализуй код, не меняй зависимости и настройки, не создавай commits, не запускай spawn/delegate.
   Структурированные результаты сохраняй инструментом brainstorm, а не самостоятельной записью JSON/Markdown.
3. Изучи постановку и критерии выбора. Различай факт из источника, предположение и неизвестное.
4. На первом круге сформулируй своё решение до чтения чужих. Не выдумывай отличие только ради числа вариантов.
   Не читай чужие скрытые материалы напрямую из network-папки и не пересылай их через send_message.
5. Критикуй свойства решения, а не автора. Приводи условия, при которых риск проявится, и возможное исправление.
   Не соглашайся только потому, что вариант предложен ведущим. Не объявляй несогласие «решённым» без ответа.
6. Применяй одинаковые критерии к вариантам. Не выдумывай численные оценки, результаты тестов, наличие API
   и свойства репозитория. Если чтение кода разрешено, изучай только необходимое и указывай источники.
7. Незнание устраняется ограниченным исследованием. Запуск потенциально изменяющего файлы эксперимента
   требует отдельно разрешённых условий; обсуждение не даёт разрешения на произвольные команды.
8. Не добавляй новые требования. Существенные вопросы о цели, бюджете и риске адресуй пользователю.
   Правило обычного протокола о выборе рекомендации после таймаута не применяется к утверждению brainstorm.
9. Учитывай обратную связь в следующем раунде и объясняй, что изменилось. Для изменений подачи используй
   предусмотренную версию/раунд, не перезаписывай утверждённую историю.
10. Нет полезного действия — wait(), без циклического опроса и повторной отправки того же материала.
11. Ведущий сохраняет разногласия и неизвестные вопросы в итоговом решении. Он может рекомендовать подход,
    но не утверждать его за оператора и не начинать разработку по истечении времени ожидания.
12. После утверждения используй принятое решение как ограничение реализации. Неприемлемое противоречие
    подними явно; не реализуй тайно другой вариант.

Эти правила должны попасть в системные инструкции/MCP, примеры runner-промптов и генерируемый AGENTS.md.
Перед генерацией использовать штатный источник инструкций: не редактировать одновременно источник и копии вручную.
Источники генерации проверить в `scripts/sync-protocol.mjs` и связанных модулях перед изменениями.

## 5. Runner, плагины и ограничения доступа

- Ожидающий участник паркуется: модель не должна оплачивать пустое ожидание других агентов/оператора.
- Смена внутренней стадии не меняет phaseEpoch. Нужен отдельный brainstormEpoch/stage в маркере ожидания,
  иначе новый материал не разбудит runner либо старая сессия продолжит не ту стадию.
- Пробуждение: завершился нужный набор подач, пришёл ответ оператора, изменился состав, задача отменена.
- Разрешённый набор pluginsByAgent не расширяется внутри brainstorm. Если инструмента не хватает, агент
  сообщает об ограничении; установка/включение нового плагина требует отдельного решения пользователя.
- Запрет мутаций в MCP не запрещает запись через shell или инструменты CLI. Для первой версии проверить
  read-only запуск каждого поддерживаемого движка и не обещать жёсткую защиту там, где её нет.
- Не переводить работающую сессию в read-only или обратно «на лету». Переход к реализации может требовать
  новой сессии; настройка запуска должна учитывать фактическую стадию, а не только общую фазу DISCUSS.
- На реализацию передавать brief + утверждённое решение + релевантные ограничения/разногласия, а не весь чат.
  Полные версии доступны по запросу с пагинацией. Ограничить размер сообщений и артефактов на входе и в контексте.

## 6. UI и операторские действия

В форме и предложении координатора: «Brainstorm перед разработкой», число раундов, команда и ресурсы.
Координатор может рекомендовать режим с объяснением, но выбор входит в утверждаемую постановку.

В задаче: стадия, раунд, подано N/M, кто ожидается, вкладки «Варианты», «Сравнение», «Рекомендация».
Чат остаётся историей коммуникации, а не источником выбранного решения. Не перестраивать поле ввода при опросе;
сохранять прокрутку, раскрытые варианты и фокус. Отдельно показывать приостановку runner и ожидание пользователя.

Перед утверждением показать, какой подход выбран, ограничения, существенные риски, открытые вопросы и
ожидаемый следующий шаг. Кнопка называется «Утвердить решение», а не «Запустить», поскольку обычный DISCUSS
может ещё требовать план и соглашение. «Вернуть с замечаниями» требует текста. В «Нужно мне» добавляется
ожидание brainstorm с прямой ссылкой на актуальную версию. Старое окно не может утвердить новую версию случайно.

Операторские endpoint'ы, окончательные пути согласовать при реализации:

- GET `/api/tasks/:id/brainstorm` — снимок для пользователя.
- POST `/api/tasks/:id/brainstorm/approve` — decisionVersion, decisionHash, operationId.
- POST `/api/tasks/:id/brainstorm/revise` — decisionVersion, decisionHash, feedback, operationId.
- POST `/api/tasks/:id/brainstorm/extend` — expectedRevision, новый maxRounds, причина, operationId.

Проверки origin/операторской роли переиспользовать из текущего server.ts. Supervisor не получает права
утверждать подход, подменять feedback или продлевать обсуждение за пользователя.

## 7. Подводные камни и выбранная обработка

| Ситуация | Что делать |
|---|---|
| Один агент упал или не подал вариант | Показать ожидаемого участника и состояние runner; не считать молчание согласием. После лимита повторов передать решение пользователю |
| Участник отключён | Само отключение не меняет состав. Замена/исключение — явное действие пользователя с новой epoch и пересборкой обсуждения |
| Лимит раундов исчерпан | Не начать следующий автоматически. Сохранить материалы и запросить продление, выбор текущего решения либо отмену |
| Достигнут лимит стоимости | Применить существующую остановку по стоимости; продление раундов не увеличивает денежный лимит |
| Пользователь долго не отвечает | Парковка и обычное уведомление; никакого автоутверждения |
| Два окна утверждают/возвращают одновременно | Lock + expected version/hash; одна операция успешна, другая получает конфликт и актуальную версию |
| Процесс упал после записи, но до ответа | Идемпотентное повторение операции; из производных событий восстанавливается уведомление, а не дублируется материал |
| Новые требования после рекомендации | Явное изменение brief, новая epoch, сброс утверждения, плана и ещё не начатого соглашения |
| Варианты поменялись после чтения рецензентом | Рецензия ссылается на версии; устаревший ответ отклоняется и получает актуальный nextAction |
| «Все согласны» без разбора рисков | Схема требует структурированный синтез; качество проверяет пользователь, схема не доказывает качество рассуждения |
| Brainstorm конфликтует с clarify/grill | Сначала завершить уточнение цели, затем options; вопросы об обнаруженных противоречиях возможны и позднее |
| Включён planReview | План создаётся на основе утверждённого решения, после чего действует прежнее утверждение плана |
| OpenSpec/задача написания change | В первой версии отклонять несовместимую комбинацию с понятной ошибкой, пока отдельно не определён порядок input/change review |
| Делегированная задача/автоматический follow-up | Brainstorm не наследуется автоматически; явно задаётся пользователем для новой обычной задачи |
| Разные поколения агентов/CLI | Новый инструмент и nextAction требуют обновлённых инструкций; старый клиент не должен начать реализацию в обход серверного барьера |
| Повторяющиеся бессодержательные ответы | Не эскалировать автоматически до бесконечного числа агентов; вывести разногласия и нехватку данных пользователю |

## 9. Критерии приёмки режима

- Пользователь может явно включить brainstorm и видит его настройки до запуска задачи.
- Каждый назначенный агент может представить и отрецензировать варианты по протоколу.
- Ведущий не получает права утвердить решение за пользователя.
- Устаревшее либо отсутствующее утверждение не позволяет перейти к реализации ни одним штатным API/MCP путём.
- В UI видно, кто ожидается, какие варианты рассмотрены и почему рекомендован выбранный подход.
- После сбоя сохранённые материалы и решение не теряются, повторные действия не дублируются.
- Ожидание и число раундов ограничены без автоматического принятия решения.
- Задачи без brainstorm сохраняют прежнее поведение.
- Все заявленные гарантии различают серверную проверку, правила агента и ограничения конкретного CLI.

Выполнять этапы последовательно, сначала закрыв серверные инварианты и протокол, затем UI.
Этот план не является командой запустить рой, агентов, задачи или реальные модели.
