# Projects MVP: план реализации и пользовательские сценарии

## Цель

Добавить Project Coordinator над существующим swarm-протоколом. Coordinator ведёт постоянный диалог с пользователем, отвечает на вопросы, предлагает задачи, после подтверждения создаёт их через существующий механизм operator, передаёт follow-up сообщения в связанные задачи и хранит память проекта.

Существующие `Task` выполняют роль threads. Отдельная сущность `Thread` не вводится. Advisor в объём работ не входит.

## Продуктовые границы первого выпуска

Основной результат: пользователь проходит путь «описал желание → уточнил предложение → подтвердил задачу → ответил на вопрос → получил результат», не изучая фазы swarm и внутренние сущности run/proposal/operation.

- В MVP один Project Coordinator и один постоянный диалог на существующий проект UI / сеть (`networkDir`). Второй проект для включения чата создавать не нужно. Стабильный `projectId` сохраняется на диске, а не вычисляется из имени или позиции в списке UI. Повторное открытие той же сети использует прежний диалог; одновременные процессы должны разделять блокировку владельца и не запускать два Coordinator.
- Список всех задач сети остаётся доступен. В контекст Coordinator попадают только созданные им или явно подключённые задачи; существующие задачи подключаются действием «Добавить в обсуждение».
- Прямое создание задачи сохраняется для пользователей, которым не нужен предварительный диалог.
- Все существующие режимы Task/OpenSpec сохраняются. Документ обратной связи аналитику выделен в следующий выпуск: его контракт ниже сохранён, но он не блокирует приёмку MVP.
- В первом выпуске нет нескольких независимых диалогов внутри одного проекта или связывания одной задачи с несколькими проектами. Модель реестра может поддержать это позднее, без включения такого UI сейчас.

## Пользовательские сценарии и интерфейс

1. **Обсуждение без запуска.** Пользователь открывает проект и пишет вопрос. Coordinator отвечает или предлагает анализ; Task не создаётся без отдельного подтверждения. Пустой экран объясняет возможности чата и предлагает начать обсуждение либо подключить существующую задачу.
2. **От желания к задаче.** Карточка предложения показывает цель, ожидаемый результат, границы работы, команду, режим, применённые ограничения стоимости и блокеры. Основные действия: «Создать задачу», «Изменить», «Отклонить». Технические параметры доступны в подробностях. Неизвестная стоимость обозначается как неизвестная; лимит не выдаётся за прогноз.
3. **Исправление предложения.** Изменение создаёт новый immutable proposal со ссылкой `supersedes`; старый становится `superseded` и больше не может быть подтверждён. Смена версии и approval сериализуются. Если задача уже создана, правка становится явным follow-up либо новым предложением, но не переписывает выполненную операцию.
4. **Контроль выполнения.** В диалоге есть серверные карточки «В очереди», «В работе», «Нужно ваше решение», «Завершено», «Не удалось выполнить». Карточка ожидания объясняет причину и ведёт прямо к существующему согласованию/вопросу; возвращение сохраняет черновик и позицию чата. Polling обновляет эти карточки без запуска LLM.
5. **Уточнение текущей работы.** Перед отправкой в задачу видны её название, ID и точный текст. Пользователь выбирает адресата и отправляет сообщение отдельным действием. При нескольких возможных адресатах Coordinator спрашивает; угадывание запрещено. Обычный ввод в проектный чат сам по себе не отправляет указания агентам.
6. **Продолжение завершённой работы.** Для закрытой задачи предлагается новая Task. Proposal хранит исходный `parentTaskId`; effective payload и preflight учитывают его и, если применяется, `baseCommit` по существующим правилам сервиса. Результат предыдущей задачи доступен по ссылке, новая задача проходит отдельное подтверждение.
7. **Остановка и очередь.** «Остановить ответ» отменяет только обработку Coordinator. Рядом поясняется, что уже запущенные задачи продолжаются, и даётся ссылка на управление задачей. Ожидающее сообщение можно убрать или заменить до запуска. Замена атомарно отменяет старый queued run и создаёт новое сообщение/run с новым ID и ссылкой на исходное; история сохраняется. При гонке с запуском сервер возвращает конфликт, UI предлагает остановить текущий ответ. После остановки ответа очередь ставится на паузу до «Продолжить», чтобы уточнения не запускались неожиданно.
8. **Сбой и повтор.** UI сохраняет исходный запрос и показывает понятную причину, результат уже выполненных действий и доступный следующий шаг. Повтор доставки того же сообщения использует прежний ID. Явная повторная обработка после ошибки создаёт новый run с `retryOfRunId`; до запуска сервер выполняет reconciliation прежних операций и передаёт их результаты и сохранённые proposals. В retry-run запрещено создавать новые task proposals: возвращаются прежние IDs, а новый вариант пользователь запрашивает отдельным сообщением. Неоднозначная операция требует ручного разбора, не повторной мутации; сопоставление по тексту не используется.

Компоновка: проекты и задачи слева, диалог в центре, ввод снизу. В интерфейсе нет обязательного выбора внутренних фаз. Ввод имеет явный контекст «Обсуждение проекта» или выбранную задачу; переход между ними сохраняет отдельные черновики. Карточки ожиданий и итогов строятся из состояния сервера, а не из утверждений модели. Итог различает «работа агентов завершена», «принято пользователем» и «влито в проект».

### Что Coordinator знает о проекте

Память — договорённости, а не доказательство состояния кода. В MVP Coordinator читает ограниченный snapshot и через project tools получает подробности связанных задач, вопросы, результаты проверок, acceptance evidence и подтверждённые решения. Ответы по этим данным содержат ссылки на задачу/артефакт и время состояния. Инструменты проверяют принадлежность проекту, ограничивают размер ответа (до 16 KiB на страницу), используют пагинацию и не читают произвольные пути. История чата также доступна постранично; усечение контекста явно помечается.

Shell и свободное чтение репозитория Coordinator недоступны. Для вопроса, требующего исследования кода, он предлагает отдельную задачу анализа с явным результатом и подтверждением запуска; не утверждает, что исследовал код по одной памяти. Минимум два агента остаётся действующим ограничением. Набор project tools и их схемы фиксируются до реализации: чтение контекста/истории/связанных задач, предложение задачи, предложение изменения памяти; отправка в задачу выполняется только по подтверждённому UI/API действию.

## Архитектурные границы

- Project Coordinator — отдельная роль, а не участник swarm и не замена `Supervisor`.
- LLM Coordinator запускается только для обработки нового сообщения или queued run; в idle модель не работает.
- Диалог, runs, proposals, операции и память проекта хранятся на диске в `.agent-network/project/`.
- Coordinator запускается в отдельном пустом `cwd` по образцу изоляции Supervisor. Отдельный CLI config/allowlist отключает shell/coding tools и проектные hooks; доступны только project tools. Все записи через Coordinator tools дополнительно проходят run-scoped серверные проверки: run существует, активен, не отменён и принадлежит проекту.
- `ProjectCommandService` — единственная точка изменения состояния swarm для новых действий Coordinator MCP и Project UI. Существующие прямое создание задач, schedules и карточки согласований сохраняют свои пути; их глобальная миграция сюда не входит в MVP. Сервис проверяет approvals, membership, лимиты и идемпотентность, затем вызывает `NetworkService.createTaskAsOperator()` или `messageLead()`.
- Coordinator lifecycle связан с `UiProject`: запуск в `start()`, остановка в `stop()` и на обоих путях закрытия проекта/server close.
- UI v2 получает маршрут `#/project`. Используются текущие same-origin/loopback проверки, `textContent` и polling; WebSocket не добавляется.

## Модель данных

### Project

- Стабильный `projectId`, имя и метаданные.
- Реестр связанных `taskIds` с происхождением `created` или `attached`.
- Ссылка на активный run, очередь входящих сообщений и persistent флаг паузы очереди. При restart пауза сохраняется; queued runs возобновляются только при снятой паузе.
- Настройки Coordinator: `approval: always`, `maxOpenTasks`.
- Бюджеты не дублируются: ProjectCommandService явно передаёт существующие `maxTaskCostUsd` и `verifyCommand` в создание Task и использует `maxCostUsd`/`checkCostLimit`. Нельзя полагаться на проверки только в UI route.

### Message и Run

- У каждого входящего сообщения постоянный `messageId`.
- У каждой обработки постоянный `runId`; состояния `queued/running/succeeded/failed/cancelled`.
- На проект допускается один активный run; остальные сообщения обрабатываются последовательно.
- Run содержит ссылку на сообщение, результат/ошибку и созданные proposal/operation IDs.
- Сервер завершает run после выхода CLI; отдельный stateful-инструмент `finish` не нужен.
- Отмена сначала устанавливает `cancelRequested`, abort’ит CLI и запрещает новые записи/операции этого run. Проверка отмены и запись сериализуются сервером. Состояние `cancelled` устанавливается только после фактического выхода CLI; следующий run до этого не запускается.
- Отмена не удаляет queued messages и не подтверждает/отклоняет автоматически уже сохранённые pending proposals и pending memory changes; пользователь управляет ими отдельно.
- При открытии проекта сохранённый `running` без живого владельца run признаётся осиротевшим и переводится в `failed` с причиной `interrupted`; `queued` остаются в очереди, после чего очередь возобновляется, если пользователь не поставил её на паузу.

### Proposal

- Постоянный `proposalId`, `projectId`, `runId` и `operationId`.
- Единый нормализованный effective payload содержит `title`, `description`, `agents`, `parentTaskId`, `baseCommit`, параметры `openspec`, `proposes`, `from`, `clarify`, `grill`, `planReview`, а также resolved `maxTaskCostUsd`, `maxCostUsd` и `verifyCommand`. Канонический hash рассчитывается от всего effective payload.
- Preflight, человекочитаемое описание, approval и создание используют один effective payload. Изменение любого resolved параметра после approval требует повторного подтверждения.
- Нормализация проверяет существующие комбинации: `openspec + proposes` запрещены, `from` требует `proposes`, `proposes + planReview` запрещено. Отсутствие `grill` сохраняется отличным от `grill: false`: для `from` только отсутствие поля включает автоматический допрос.
- Proposal содержит человекочитаемое описание выбранного режима: обычная задача, уточнение, допрос, утверждение плана, существующий/новый OpenSpec change или задача с входными артефактами аналитиков.
- Состояния `pending/approved/rejected/superseded/executed/failed`.
- Хранятся результат операции, `taskId` при успехе и ошибка при неудаче.
- LLM получает `propose_task`, но не `create_task`. Создание инициирует отдельный UI/API endpoint после явного подтверждения.
- Preflight выполняется до approval и повторно при создании: проверяются агенты, effective payload, `maxOpenTasks`, общая папка, бюджет и `verifyCommand`. Для Task с существующим `openspec` дополнительно выполняется эквивалент `checkAgentFolders`: change должен быть доступен в worktree каждого выбранного агента. Пользователь видит применённые настройки и блокеры до согласования.
- Для продолжения preflight проверяет принадлежность `parentTaskId` сети и реестру Project, статус `COMPLETED` или `CANCELLED`. `baseCommit` проверяется по доступной git-истории и явно выбранному результату родителя; произвольный commit от модели не принимается. Для отменённого родителя UI не обещает готовый результат: пользователь видит и подтверждает базу продолжения, а при отсутствии проверенной базы создание блокируется до её выбора.
- Полнота параметров: `contract`, `allowSpawn`, `maxFixRounds`, `maxFollowUps` также включаются в effective payload, нормализацию, preflight, hash и раскрываемые настройки с сохранением различия между отсутствующим полем и явным значением. До реализации сверить перечень с `NewTaskInput` и зафиксировать контрактными тестами передачу всех поддерживаемых полей; неизвестные поля отклоняются, а не молча игнорируются.

### Operation и durable correlation

- `operationId` — идемпотентный ключ каждой mutating operation; состояния `prepared/executing/finalizing/succeeded/failed`.
- В `Task` добавляется структурированный origin/correlation marker с `projectId` и `operationId`; в follow-up `Message` добавляются те же идентификаторы. Эти поля сохраняются атомарно с основной записью TaskStore/MessageStore; старые записи без полей остаются совместимыми.
- До вызова swarm фиксируется `prepared`, затем `executing`; после вызова сохраняется результат.
- Межхранилищная транзакция между ProjectStore и TaskStore не предполагается. Reconciliation ищет Task/Message точно по `projectId + operationId`; сопоставление по title или content запрещено.
- Для Task без `from` найденная запись восстанавливает успешное создание. Для Task с `from` найденная запись переводит operation в `finalizing`: до первого завершённого manifest reconciliation идемпотентно докопирует входные файлы и проверяет полный ожидаемый набор. Только после успешной finalization operation становится `succeeded`.
- При finalization сохраняется manifest входной копии: относительный путь и content hash каждого файла плюс общий `inputSnapshotHash`. Это фиксированный snapshot артефактов Task, а не версии исходных документов аналитика.
- Если manifest уже сохранён, recovery только проверяет destination-файлы по его hashes и не копирует повторно потенциально изменившиеся источники. Расхождение destination с manifest переводит operation в `failed` для ручного разбора.
- Task с `from` недоступна runners до завершения finalization и сохранения manifest. После restart runners возобновляются только после reconciliation всех таких Task.
- Отсутствие записи разрешает безопасный retry. Неоднозначное состояние переводится в `failed` для ручного разбора, без повторной мутации.
- Повтор с тем же `operationId` возвращает сохранённый/восстановленный результат, а не создаёт дубликат.

## Контракты операций

### Создание задачи

1. Проверить, что proposal существует, принадлежит проекту и находится в допустимом состоянии.
2. Проверить совпадение hash effective payload и повторно выполнить все preflight-проверки, включая `checkAgentFolders` для существующего OpenSpec change.
3. Проверить существующее ограничение `createTaskCore`: минимум два разных агента.
4. Проверить `maxOpenTasks`: учитываются связанные задачи в `ACTIVE` и `BLOCKED`.
5. Для созданных Coordinator code tasks в общей папке допускается не более одной открытой задачи (`ACTIVE` или `BLOCKED`). Code task в этом правиле — Coordinator-created Task без `proposes`; общей считается папка с совпадающим нормализованным `cwd`. Это ограничение MVP, а не глобальная гарантия эксклюзивности папки.
6. Проверку лимита и создание сериализовать через ProjectCommandService.
7. Создать Task через `createTaskAsOperator()` с durable correlation marker. Для `from` выполнить восстанавливаемую finalization и сохранить input manifest.
8. Добавить `taskId` в реестр Project и сохранить результат operation. Каждый шаг восстанавливается reconciliation; атомарность между разными хранилищами не декларируется.

### Attach существующей задачи

- Attach разрешён только для Task той же сети и не изменяет её исходный origin.
- Запись реестра Project содержит `projectId`, `taskId`, `operationId` и тип `attached`; повтор с тем же `operationId` возвращает существующую запись.
- Reconciliation attach выполняется по этой записи реестра, а не поиском Task/Message. Отсутствие записи после сбоя разрешает идемпотентный retry.
- В MVP действует один Project на сеть; повторный attach той же Task не создаёт вторую связь даже с новым operationId. Удаление связи не изменяет Task; перед detach UI предупреждает о потере доступа Coordinator к её контексту.
- Detach любой связанной задачи в `ACTIVE` или `BLOCKED` запрещён сервером: так нельзя обойти `maxOpenTasks` или ограничение общей папки. Закрытую задачу можно отключить. Ограничение одной открытой Coordinator-created code task дополнительно проверяется по durable origin всех задач сети, независимо от наличия связи в реестре.

### Follow-up в задачу

- `send_to_task` — серверная операция подтверждённого UI/API действия, не свободный инструмент LLM. Неизменяемые taskId и текст подтверждаются пользователем; изменение требует нового подтверждения. Операция разрешена только для Task, явно связанной с Project.
- Допустимы только связанные задачи в `ACTIVE` или `BLOCKED`.
- Запись в `pendingMessages` подтверждает доставку в очередь протокола, но не исполнение и не разблокировку `BLOCKED`.
- Для `COMPLETED` и `CANCELLED` follow-up запрещён; Coordinator предлагает новую задачу.
- Повтор по `operationId` находит исходное Message по durable marker и не добавляет дубликат.
- Urgent delivery в MVP не реализуется.

### Project memory

- Устойчивый контекст каждого проекта хранится в `.agent-network/project/<projectId>/memory.md`.
- Файл содержит цель, договорённости, архитектурные решения и важные ограничения.
- Сообщения, статусы задач, runs и proposals хранятся отдельно и не смешиваются с памятью.
- Размер `memory.md` ограничен 16 KiB; Coordinator получает его содержимое через ограниченный snapshot новой LLM-сессии.
- UI предоставляет read-only просмотр `memory.md`; сложный редактор не добавляется.
- Для исправления Coordinator создаёт persistent pending memory change с `changeId`, предлагаемым содержимым/diff и `baseHash` исходной версии. До подтверждения `memory.md` не изменяется.
- Отдельное UI/API действие approve/reject применяет именно immutable pending change, независимо от завершения исходного run. Если текущий hash памяти не совпадает с `baseHash`, изменение не применяется и требуется новый draft.

### Контекст новой LLM-сессии

Snapshot ограничен и формируется сервером:

- цель проекта не более 4 KiB;
- project memory не более 16 KiB;
- не более 20 pending/failed proposals в виде summaries: не более 1 KiB каждый и не более 20 KiB суммарно; полный effective payload остаётся в ProjectStore;
- сообщения — не более 50, каждое усекается до 2 KiB, секция сообщений не превышает 8 KiB: сохраняются самые новые, помещающиеся в лимит;
- server-generated статусы — не более 50 связанных задач, секция не превышает 4 KiB: приоритет имеют открытые и ожидающие пользователя задачи;
- служебные поля и JSON-обёртка — не более 4 KiB;
- сериализованный snapshot строго не более 64 KiB. Лимиты секций суммарно оставляют запас; если фактический размер всё же превышен, сервер последовательно исключает старые сообщения, неактивные статусы и старые proposal summaries. Обязательный остаток — цель, память, актуальные pending summaries и служебные поля — заранее ограничен и помещается в 64 KiB.

Автоматическое сжатие памяти, сложный редактор памяти и автоматический режим создания задач не входят в MVP.

### OpenSpec и режимы Task

- Coordinator может создать через proposal как обычную Task, так и Task с существующими режимами `clarify`, `grill`, `planReview` и OpenSpec.
- Нормализованные поля effective payload передаются в существующий механизм создания Task; новых OpenSpec-протоколов Coordinator не вводит.
- Подтверждение proposal означает только создание Task. Последующие plan/input/change approvals, вопросы, приёмка, вливание и архивирование остаются в существующей карточке задачи.
- Project показывает состояние «ждёт вас» и прямые ссылки на требуемое действие; механики OpenSpec approvals в чате не дублируются.

### Следующий выпуск: документ обратной связи аналитику

Этот раздел и связанные с ним инварианты относятся к следующему выпуску и не входят в критерии готовности MVP. Для задач с входными артефактами аналитиков формируется отдельный документ, не смешанный с project memory:

- текущий draft — `.agent-network/tasks/<taskId>/analyst-feedback/draft.md`;
- неизменяемые подтверждённые revisions — `.agent-network/tasks/<taskId>/analyst-feedback/revisions/<revisionId>.md`.

Источники документа — структурированные данные существующего OpenSpec-контура и явные комментарии пользователя, а не вся переписка Coordinator:

- manifest зафиксированной входной копии и `inputSnapshotHash`;
- расхождения, найденные при просмотре input;
- вопросы и ответы оператора; ответы аналитика включаются только после их явного добавления пользователем комментарием;
- решения по пунктам: `taken/adapted/dropped/added`, причина и ссылка на место в change;
- описание изменений по этим решениям и комментариям, без обещания автоматического семантического diff;
- пункты, возвращаемые на доработку, с конкретным ожидаемым результатом;
- версии input/change страниц, change hash и текущий статус согласования.

Workflow:

1. Пользователь просматривает input и обсуждение, отмечает пункты для возврата аналитику и добавляет комментарии. Выбор привязывается к версии страницы и стабильному идентификатору пункта (индекс/hash departure или coverage) и переживает перегенерацию draft только в пределах той же версии источника.
2. Сервер формирует draft из зафиксированных вопросов, решений и coverage. Coordinator помогает с формулировками, но не изменяет исходные артефакты аналитиков.
3. Документ явно сообщает, на какие `inputSnapshotHash`, input/change versions и change hash он опирается. Всегда указывается, что полнота coverage сервером не верифицирована; при пустой coverage дополнительно показывается заметное предупреждение о неполноте.
4. Пользователь выполняет независимое действие «Подтвердить документ для аналитика». Оно не утверждает change, не завершает фазу и не разрешает запись в change. Подтверждение создаёт неизменяемую revision.
5. Пользователь открывает/скачивает revision и сам передаёт её аналитику; автоматическая внешняя отправка не выполняется.
6. После новой версии change или coverage старая revision не меняется и помечается как основанная на прежней версии. Новый draft создаётся из актуальных данных; прежний выбор пунктов помечается как требующий пересмотра и не переносится автоматически по индексу или тексту.

### Обязательные инварианты реализации

- Manifest сохраняется атомарно только после полной проверки destination-файлов. Recovery не может наблюдать частично записанный manifest; gating finalization действует на все пути выбора Coordinator-created Task runner’ом и не блокирует остальные задачи.
- Проверка `baseHash` и запись `memory.md` сериализуются как одна критическая секция. Два одновременных approval с одинаковой базой не могут оба примениться: второй получает version conflict.
- Каждая analyst-feedback revision создаётся из одного согласованного snapshot источников: `inputSnapshotHash`, input/change versions, change hash, выбранные пункты и комментарии фиксируются вместе. Параллельные обновления не могут смешать версии; признак устаревания вычисляется UI отдельно и не изменяет подтверждённый файл.

## Этапы реализации

### Этап 1. Основа хранения и ранний интерфейс диалога

Реализовать хранение Project, Messages, Runs, Proposals и Operations; очередь с одним активным run; отмену; idempotency и reconciliation. Добавить явный реестр Project ↔ Task. Сразу добавить маршрут диалога в UI v2: пустое состояние, история, ввод, очередь, пауза и восстановление черновика. До этапа 3 запуск задач недоступен; пользовательская компоновка проверяется до завершения всех серверных интеграций.

Критерии готовности:

- повтор сообщения/операции не создаёт дубликатов;
- сбой после создания Task/Message корректно восстанавливается по durable `projectId + operationId`, без сопоставления по тексту;
- attach восстанавливается идемпотентно по реестру Project и не изменяет origin существующей Task;
- сохранённый `running` после перезапуска переводится в `failed/interrupted`, а queued runs возобновляются только при снятой паузе;
- отмена завершается только после выхода CLI; cancelled/cancelling run не может выполнить позднюю запись или мутацию и не удаляет pending proposals/memory changes;
- pending memory change сохраняет immutable содержимое/diff и `baseHash`; при конфликте версий запись отклоняется;
- ручные и scheduled tasks не попадают в Project без явного attach.

### Этап 2. Работающий диалог и редактируемые предложения

Добавить изолированный запуск Coordinator и ограниченный snapshot контекста. Coordinator отвечает пользователю и формирует proposals через `propose_task`, но не создаёт Task напрямую.

Критерии готовности:

- в idle LLM не запущена;
- Coordinator не получает shell/coding tools и не подхватывает hooks рабочего проекта;
- run корректно завершается после выхода CLI;
- snapshot не содержит неограниченную историю и полные proposal payloads, принимает статусы только от сервера и соблюдает лимит 64 KiB;
- proposal сохраняет единый effective payload с режимами Task/OpenSpec, resolved настройками и человекочитаемым описанием.

### Этап 3. Сквозной сценарий от предложения до результата

Реализовать preflight и approve/reject proposal, идемпотентное создание Task со всеми поддерживаемыми параметрами, attach связанных Task и follow-up через существующие NetworkService APIs. Одновременно подключить UI-карточки создания, адресного follow-up, ожиданий и результата; пройти пользовательские сценарии 1–8.

Критерии готовности:

- approval enforcement находится на сервере, а не в prompt;
- невозможно создать Task из изменённого effective payload или с другими resolved настройками после approval;
- preflight и создание применяют одинаковую нормализацию режимов и для существующего OpenSpec change выполняют `checkAgentFolders`;
- Task с `from` считается успешно созданной только после восстанавливаемой finalization, проверки входных файлов и сохранения `inputSnapshotHash`; до этого runners её не запускают, а recovery не изменяет зафиксированный manifest;
- `maxOpenTasks` и ограничение одной Coordinator-created code task в общей папке соблюдаются при параллельных запросах;
- follow-up чужой или завершённой Task отклоняется;
- повторная мутация возвращает прежний результат.

### Этап 4. Завершение и проверка UI Projects

Завершить добавленный на этапах 1–3 `#/project`: проверить диалог, очередь/статус run, остановку run, proposals с preflight и approve/reject, ошибки операций, список связанных задач и read-only просмотр `memory.md`.

Критерии готовности:

- пользователь видит различие между предложением, созданием, доставкой follow-up и исполнением;
- действия названы раздельно: «Создать задачу», «Утвердить план», «Посмотрел вход», «Принять change»; подтверждение документа для аналитика появится в следующем выпуске;
- для связанных задач отображается «ждёт вас» со ссылками на план, input/change, вопрос, BLOCKED, приёмку или вливание;
- очередь показывает, какое сообщение обрабатывается и какие сообщения ожидают;
- pending proposal нельзя утвердить дважды;
- память доступна для просмотра; pending memory change подтверждается отдельно и применяется только при совпадении `baseHash`;
- обновление UI использует polling и не требует WebSocket;
- применяются существующие проверки безопасности и безопасный рендеринг текста.

### Этап 5. Hardening и документация

Покрыть тестами restart/reconciliation, дедупликацию, отмену, approval, membership, лимиты, параллельные approvals, follow-up, finalization `from`, memory conflicts, superseded proposals, адресацию follow-up, гонку замены queued сообщения и запусков, сохранение паузы и единственного владельца Coordinator. Обновить документацию и явно описать ограничение общей папки.

Критерии готовности:

- существующие тесты swarm не регрессируют;
- новые сценарии восстановления воспроизводимо проходят;
- документация не обещает глобальной координации обычного UI, schedules и Coordinator;
- ограничения follow-up и минимум двух агентов отражены в UI/API ошибках.

## Приёмка пользовательского опыта

Проверить на работающем UI, а не только unit-тестами:

- Новый пользователь создаёт первую задачу из диалога без чтения документации протокола; зафиксировать время, ошибки и места, где понадобилась помощь.
- Вопрос «что происходит?» получает серверный статус; ожидание решения видно без запуска новой LLM-сессии.
- Из двух активных задач уточнение попадает только в явно выбранную; закрытая задача предлагает продолжение, сохраняя связь.
- Изменённое предложение нельзя подтвердить по старой карточке; двойной клик и две вкладки не создают дубликатов.
- После «Остановить ответ» пользователь видит, что задачи продолжаются, а очередь чата приостановлена.
- После перезапуска доступны история и pending approvals; UI не предлагает повторно создать уже созданную задачу.
- Сообщение длиннее лимита snapshot не теряется в хранилище: Coordinator может получить нужную страницу, либо явно сообщает о недостатке данных.
- Полный основной путь доступен с клавиатуры, фокус сохраняется после polling, ошибки связаны с соответствующим действием, ввод не очищается при неуспешной отправке.

Численные цели скорости и успешности устанавливаются после первого прохода сценариев; до него удобство считается гипотезой, а не доказанным результатом.

## Что не входит в MVP

- Документ обратной связи аналитику с revisions и выбором пунктов (контракт следующего выпуска сохранён выше).
- Несколько диалогов на проект и несколько Projects на одну сеть.
- Свободный доступ Coordinator к коду, shell и автоматическое исследование репозитория.

- Advisor.
- Отдельная сущность Thread.
- Автоматическое создание задач без подтверждения (`approval=always` только).
- Централизованный scheduler для всех источников задач.
- Глобальная эксклюзивная блокировка общей папки.
- WebSocket, urgent follow-up, автоматическое сжатие и сложный редактор памяти.
