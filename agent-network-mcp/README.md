# agent-network-mcp

Локальный MCP-сервер (stdio, TypeScript, без внешней инфраструктуры), через который два и более AI coding agents
(Qwen CLI, Claude Code, Codex, ...) совместно выполняют одну задачу по жёсткому протоколу:

```
DISCUSS ──agreement одобрен всеми──▶ IMPLEMENT ──все READY_FOR_SYNC──▶ SYNC ──все PASS──▶ INTEGRATE ──PASS──▶ DONE
                                         ▲                               │                   │
                                         ├───── NEEDS_FIX (ERROR) ───────┘                   │
                                         └───── NEEDS_FIX (сборка/тесты/конфликт) ───────────┘
              после maxFixRounds неудачных раундов задача BLOCKED → оператор: task unblock / task cancel
```

**Главный принцип: LLM не управляет workflow.** Фазой, одобрениями, статусами и переходами владеет сервер. Агент только
выполняет работу через небольшой набор tools (`swarm_context`, `propose`, `complete`, `send_message`, `wait` и несколько
вспомогательных); на каждом шаге сервер сам говорит ему, что делать
(`nextAction`, `allowedActions`, `hint`; для `propose` и `respond` — готовый `exampleCall`). Публичного tool для смены фазы нет и не будет.

Каждый агент запускает **собственный** процесс MCP по stdio. Все процессы работают с одной директорией
`.agent-network/` на файловой системе. Файловая система — источник истины; `fs.watch` — лишь оптимизация пробуждения.

## Быстрый старт

Нужны Node.js ≥ 20 (проверено на 20.12) и CLI агента: [Qwen Code](#qwen-cli) (в том числе с локальной моделью в
LM Studio) или [Claude Code](#claude-code).

Основной способ работы — страница с runner'ами. Вы ставите задачи в браузере, runner'ы сами запускают агентов (свежая
сессия CLI на каждую задачу), а вы видите их логи, отвечаете на их вопросы и смотрите статистику.

**1. Соберите сервер.**

```bash
cd /abs/path/agent-network-mcp
npm install
npm run build          # dist/: его запускают и runner'ы, и MCP-серверы агентов
```

Чтобы запускать короткой командой `agent-network-mcp` из любой папки, один раз сделайте `npm link` (глобальная ссылка
на эту папку; после `git pull` хватит `npm run build`, убрать — `npm unlink -g agent-network-mcp`):

```bash
npm link
```

**2. Запустите в папке проекта** (git-репозиторий хотя бы с одним коммитом) — одна команда:

```bash
cd ~/myprojects/test
agent-network-mcp ui                      # шаблон по установленному CLI; явно: --template claude или --template qwen
```

(без `npm link` — `node /abs/path/agent-network-mcp/dist/index.js ui`). В первый раз в проекте появляется **свой
конфиг** `<проект>/.agent-network/runners.json`, скопированный из шаблона:

- **шаблон** — по CLI в `PATH`: есть только `claude` — Claude Code, только `qwen` — Qwen Code; есть оба — `ui`
  спрашивает в терминале (без терминала и без ответа — Qwen). `--template claude|qwen` выбирает сам;
- **под стек проекта** (по файлам в корне): `pom.xml` — Maven, `build.gradle(.kts)`/`settings.gradle(.kts)` — Gradle,
  `package.json` — npm (yarn и pnpm — по lockfile). Под него ставятся сборка в разрешениях shell (`./mvnw` или `mvn`,
  `./gradlew` или `gradle`, `npm test` и `npm run`), `verifyCommand` задач (`./mvnw -q -B verify …`,
  `./gradlew check --console=plain`, скрипт `verify`/`check`/`test`/`build` из `package.json`) и инструкции ролей
  ([instructions/](examples/runner/instructions), `gradle/`, `npm/`). Что найдено, `ui` пишет в терминал и вторым
  комментарием в конфиг. Стек не найден — остаются разрешение и инструкции Maven из шаблона, а `verifyCommand` нет:
  задайте их сами.

Папка `.agent-network` исключена из git. Дальше `ui` берёт этот файл, а `--template` уже не действует: чтобы
начать заново с шаблона, удалите файл. Worktree агентов (`../test-backend` и т.д.) создаются сами, сеть —
`<проект>/.agent-network`. Подробности — [Запуск в своём проекте одной командой](#запуск-в-своём-проекте-одной-командой).

**3. Модели и прочее правьте в этом конфиге** (`.agent-network/runners.json` проекта, пути в нём не нужны). Страница
тоже записывает туда свои изменения (модель агента, инструкции, расписания, надзор), а не в пример в репозитории.

- `model` и `models` — какая модель у агентов и из каких выбирать на странице: [Модели](#модели-где-взять-имена-и-куда-их-писать);
- для Qwen с LM Studio — адрес сервера в `--openai-base-url` (в двух командах: агентов и надзора), например
  `http://192.168.1.10:1234/v1`;
- сборка в разрешениях shell (`Bash(./mvnw:*)` / `run_shell_command(./mvnw)`) и `verifyCommand` — уже под стек проекта,
  поправьте, если нужна другая команда (например, с линтером: `npm run check`);
- `prices` (необязательно) — цена токенов для моделей, которые не сообщают стоимость сами, например Qwen:
  [Цена токенов](#цена-токенов-если-cli-не-сообщает-стоимость);
- `maxTaskCostUsd` — лимит стоимости задачи по умолчанию.

После правки файла перезапустите `ui`. Свой конфиг в другом месте — `ui --runners путь/runners.json`; страница только
для просмотра — `ui --read-only`.

**4. Без git или по-своему.** Агенту можно задать `"cwd"` (папка, где он работает), всем — `"project"` и
`"networkDir"`; `"worktree": false` в `defaults` — без авто-worktree. Для пробы хватит одной папки: `"cwd"` в `defaults`
([когда этого мало](#два-агента-в-одной-папке-или-в-worktree)).

**5. Страница с runner'ами** — http://127.0.0.1:4777 (другой порт — `--port 4790`).

Runner'ы стартуют вместе со страницей (агент с `"autostart": false` — по кнопке «Старт») и ждут задач, не тратя модель.
`runners.json` читается при старте: после его правки перезапустите UI (Ctrl+C и снова). Модель и файл инструкций агента
меняются прямо на странице, без перезапуска.

**6. Поставьте задачу** в разделе «Задачи» кнопкой «+ Новая задача»: название, конкретное описание, lead (он сводит
работу в конце) и остальные агенты — отметьте только тех, кто нужен в этой задаче. Runner'ы подхватят её за пару секунд.
Дальше на странице:

- **Обзор** — что идёт и что в очереди, расход за 24 ч / 7 д / 30 д, что сейчас делает каждый runner, задачи по фазам,
  последние события;
- **Задачи** — карточка задачи: фаза, кого ждут, подзадачи агентов, сообщения, статистика (время, токены, модели);
- **Запуски** — каждая сессия агента: длительность, токены, стоимость;
- **Runner'ы** — статус, модель, файл инструкций, лог сессии (текст агента и его вызовы `→ tool(...)`);
- **вопросы агентов** висят над любым разделом — если в задаче чего-то не хватает, агент спрашивает вас; ответ уходит
  прямо в его сессию.

Несколько проектов — на одной странице: `ui --runners shop.json --runners blog.json`, переключение в разделе «Проекты».

> **Описание задачи — самое важное.** Агенты не должны придумывать задание. Если в описании (поле формы, `--description`) нет конкретики
> («реализуй ...», без фичи и файлов), слабая модель начнёт выдумывать свой план (так и случилось на первом прогоне).
> Пишите: проблема, ожидаемое поведение, затрагиваемые файлы, распределение ролей, что менять нельзя.

### Модели: где взять имена и куда их писать

Модель агента задают три поля `runners.json`:

```json
"defaults": {
  "command": ["qwen", "{prompt}", "-m", "{model}", "..."],
  "model": "qwen/qwen3.5-9b",
  "models": ["qwen/qwen3.5-9b", "qwen/qwen3-coder-30b"]
},
"agents": [
  { "id": "backend" },
  { "id": "reviewer", "model": "qwen/qwen3-coder-30b" }
]
```

- `"{model}"` в `command` — место, куда runner подставляет модель: `"-m", "{model}"` у Qwen Code,
  `"--model", "{model}"` у Claude Code. Без него модель задаёт сама команда, и выбора на странице нет.
- `"model"` — модель по умолчанию (в `defaults`) или своя модель агента. Обязательна, если в команде есть `{model}`.
- `"models"` — **список для выбора в карточке runner'а.** Пишется в `defaults` (общий) или у агента (тогда у него свой).
  Без списка на странице видна только текущая модель и пункт «другая…», где имя вводится вручную.

Выбор на странице применяется со следующей сессии агента и записывается в `runners.json` (`"model"` у агента). Имя модели —
то, которое понимает CLI, без пробелов и не с `-`:

| Откуда модель | Как узнать имена |
|---|---|
| LM Studio (Qwen Code с `--openai-base-url`) | `curl http://<адрес>:1234/v1/models`, поле `id`; модель должна быть скачана в LM Studio |
| Qwen Code с `~/.qwen/settings.json` | `id` моделей в разделе `modelProviders` этого файла |
| Ollama через OpenAI-совместимый `http://localhost:11434/v1` *(не проверялось)* | `ollama list`, имя вида `qwen2.5-coder:7b` |
| Claude Code | `haiku`, `sonnet`, `opus` или полное имя модели |

Какая модель реально отработала сессию, видно в логе runner'а (`[session] model …`) и в «Статистике по агентам» задачи.

### Цена токенов: если CLI не сообщает стоимость

Claude Code сам сообщает стоимость каждой сессии. Qwen Code и локальные модели сообщают только токены. Стоимость таких
сессий считается по вашим ценам из поля **`"prices"` в `runners.json`** (на верхнем уровне, рядом с `"agents"`), в
долларах за 1 млн токенов (цифры в примере условные):

```json
{
  "networkDir": "/abs/project/.agent-network",
  "defaults": { "command": ["qwen", "{prompt}", "-m", "{model}", "..."], "model": "qwen/qwen3.5-9b" },
  "agents": [ { "id": "backend" }, { "id": "reviewer" } ],
  "prices": {
    "qwen/qwen3.5-9b": { "input": 0.05, "output": 0.25 },
    "qwen/qwen3-coder-30b": { "input": 0.1, "output": 0.4, "cacheRead": 0.01 }
  }
}
```

- Ключ — имя модели, как его сообщает сессия: строка `[session] model …` в логе runner'а или колонка «Модель» в
  «Статистике по агентам». Регистр не важен.
- `input` — цена входных токенов, `output` — выходных. `cacheRead` (токены из кэша) и `cacheWrite` (запись в кэш)
  необязательны, без них берётся цена `input`.
- Для бесплатной локальной модели поставьте `0`. Чтобы прикинуть, сколько та же работа стоила бы у провайдера, впишите
  его цены.
- Стоимость по вашим ценам на странице помечена «≈ … (по ценам из runners.json)». Если у модели есть токены, но нет ни
  стоимости от CLI, ни цены, статистика пишет «нет цены для <модель>».
- Цены применяются ко всем сессиям, и прошлым тоже: файл перечитывается при изменении, перезапускать UI не нужно. Если
  после правки файл не читается, страница сообщает об ошибке и считает по прежним ценам.
- В терминале: `task stats --runners runners.json` считает стоимость по тем же ценам.

### Без runner'а: агенты в обычных сессиях CLI

Если агентов запускаете вы сами (интерактивные сессии Claude Code или Qwen, по одной на агента), runner и `runners.json`
не нужны:

**1. Подключите сервер к каждому CLI** ([подробно ниже](#подключение-к-cli)). Везде одно и то же, меняется только способ записи конфига:

| Переменная | Значение |
|---|---|
| команда | `node /abs/path/agent-network-mcp/dist/index.js` |
| `AGENT_ID` | `backend,reviewer` — пул имён; каждый процесс займёт первое свободное |
| `NETWORK_DIR` | `/abs/path/project/.agent-network` — **один и тот же** у всех агентов; или `auto` — см. [Несколько проектов](#несколько-проектов-network_dirauto) |

**2. Создайте задачу.** Либо оператор из терминала:

```bash
node dist/index.js task create --network-dir /abs/path/project/.agent-network \
  --agents backend,reviewer --title "Короткое название" \
  --description "Что именно сделать, в каких файлах, какой контракт, кто что делает" \
  --verify "mvn -q verify"          # необязательно: чем lead проверяет слитый результат
```

Либо попросите одного из запущенных агентов: «Создай задачу для reviewer: <конкретное описание>» (агент вызовет `create_task`;
оба CLI к этому моменту должны быть запущены). Тогда шаг 3 для создателя выполнен сам.

**3. Запустите агентов** (по одному CLI на каждого) с одним и тем же промптом:

> Ты агент в agent-network. Начни с `swarm_context` и выполняй `nextAction`, пока не `done`.

Следить за ходом можно в [UI](#ui) или командами `task list` / `agent list`.

## Подключение к CLI

Общее для всех: у каждого агента **свой процесс**, `NETWORK_DIR` одинаковый. `AGENT_ID` — либо уникальный на агента
(`backend`, `reviewer`), либо пул `backend,reviewer` (удобно для одного общего конфига). Имена в пуле должны совпадать с
`--agents` задачи. Первый в `--agents` — **lead** (ему `swarm_context` говорит `propose`, остальным `wait`).

### Qwen CLI

`~/.qwen/settings.json` (глобально) или `.qwen/settings.json` в проекте:

```json
{
  "mcpServers": {
    "agent-network": {
      "command": "node",
      "args": ["/abs/path/agent-network-mcp/dist/index.js"],
      "env": {
        "AGENT_ID": "backend,reviewer",
        "AGENT_TYPE": "qwen",
        "NETWORK_DIR": "/abs/path/project/.agent-network"
      }
    }
  }
}
```

Запуск: `QWEN_CODE_ENABLE_AGENT_TEAM=1 qwen` (по желанию; экспериментальный режим agent team). Qwen читает `QWEN.md`; положите
рядом копию `AGENTS.md` как `QWEN.md`, если ваша версия не подхватывает `AGENTS.md`. Если задан и глобальный, и проектный
блок `agent-network`, убедитесь, что действует нужный (проектные настройки работают только в доверенных папках).

Для локальных моделей через LM Studio используйте `"wireApi": "chat-completions"` (см. [Проблемы](#если-что-то-не-работает)).
Чтобы агент на Qwen брал задачи одну за другой без остановки — runner, см. [Runner → Qwen Code](#qwen-code).

### Claude Code

```bash
cd /abs/path/project
claude mcp add agent-network --scope local \
  -e AGENT_ID=backend,reviewer -e AGENT_TYPE=claude \
  -e NETWORK_DIR=/abs/path/project/.agent-network \
  -- node /abs/path/agent-network-mcp/dist/index.js
claude mcp get agent-network     # должно быть ✔ Connected
```

`--scope local` хранит запись в `~/.claude.json` только для этого проекта (в репозиторий ничего не попадает). Tools
называются `mcp__agent-network__swarm_context` и т. д. Перезапустите сессию, чтобы они появились. Claude Code читает
`CLAUDE.md`; чтобы подтянуть правила проекта, добавьте в него строку `@AGENTS.md`. Убрать: `claude mcp remove agent-network -s local`.

#### Хуки: сообщения доходят до занятого агента

Без хуков агент видит сообщения только в `wait()` и в ответах tools agent-network. Пока он в IMPLEMENT пишет код
(Edit, Bash), `FILE_REQUEST` соседа лежит непрочитанным до его `complete`, а сосед всё это время ждёт. Команда
`agent-network-mcp hook` закрывает это двумя хуками Claude Code:

| Хук | Что делает |
|---|---|
| `PostToolUse` (`hook post-tool`) | после любого tool (кроме tools agent-network) проверяет непрочитанные сообщения этому агенту; о новых добавляет в контекст короткую сводку: от кого, тип, начало текста, файлы; `FILE_REQUEST`, `BLOCKER`, `FIX_REQUEST` помечены «X is waiting for you». Об одном сообщении говорит один раз. Открытый `FILE_REQUEST` (прочитан, но владелец ещё не ответил запрашивающему — то же правило, что у `nextAction: respond`) повторяет не чаще раза в минуту, пока нет ответа |
| `Stop` (`hook stop`) | пока у агента есть активная задача (`ACTIVE`, не DONE), один раз не даёт закончить ход: «вызови `wait()` и продолжай цикл»; если кто-то ждёт ответа на запрос файлов, называет его. Повторная остановка (`stop_hook_active`) проходит, поэтому агент, который ждёт ответа пользователя, не застревает |

Хук только читает сеть: прочитанными сообщения помечает сервер, когда агент вызывает `swarm_context` или `wait`. Свою
память о том, что уже показано, хук держит в `.agent-network/hooks/<agent>.json`. Любая ошибка — тишина и exit 0.

Агента хук находит сам: его MCP-сервер — прямой потомок того же процесса `claude`, что и хук (`pid` из
`agents/<id>.json` + дерево `ps`). Это работает и с пулом `AGENT_ID=a,b`. Если сервер запущен через обёртку (`npx`, `sh -c`)
или нет `ps` (Windows), передайте `--agent <id>`. Сессия без agent-network в соседнем терминале чужого агента не находит.

Готовые настройки — [examples/claude-hooks/settings.json](examples/claude-hooks/settings.json); вместе с хуками
`java-dev-flow` — [settings.with-java-dev-flow.json](examples/claude-hooks/settings.with-java-dev-flow.json). Положите
содержимое в `.claude/settings.local.json` проекта (или каждого worktree), замените `/abs/path/...`. `--network-dir` —
тот же каталог, что `NETWORK_DIR` у MCP; без флага берётся переменная `NETWORK_DIR` окружения `claude`. Хуки
подхватываются при старте сессии, проверить — `/hooks`. Задержка: до следующего вызова tool, обычно секунды. Сессию,
которая уже закончила ход и простаивает, хук не будит: этого не допускает Stop-хук.

#### Хуки для Qwen Code (пример, добавляете сами)

В Qwen Code (проверено на 0.24.7) хуки того же формата, что у Claude, и наша команда `hook` подходит к ним как есть.
Пример — [examples/qwen-hooks/settings.json](examples/qwen-hooks/settings.json), замените `/abs/path`:

| Хук | Что делает |
|---|---|
| `PostToolUse` (`hook post-tool`) | новые сообщения агенту — в контекст после любого вызова (`read_file`, shell…), как у Claude: ваше сообщение lead'у доходит, даже пока он работает |
| `Stop` (`hook stop`) | один раз не даёт закончить ход, пока у агента есть активная задача |
| `PreToolUse` на `run_shell_command` (`hook pre-shell`) | составную команду (`cd …`, `&&`, `;`, `\|`) отклоняет с подсказкой «одна команда за вызов» — headless-Qwen всё равно отклонил бы её целиком; сборку и тесты в shell (`./mvnw`, `gradle`, `npm test`…) — с подсказкой вызвать `build` |
| `PreToolUse` (`hook pre-bash`) | также отклоняет `git push` агента: наружу работу отправляете вы с вкладки «Раскатка» |
| `PreToolUse` на `skill` и `read_file` (`hook pre-skill`) | отклоняет скилл, который вы выключили агенту (`disabledSkills`, таблица «Скиллы агентов» на странице): вызов `skill` или чтение его `SKILL.md` |
| `PreToolUse` на `write_file` и `replace` (`hook pre-write`) | в задаче, которая пишет OpenSpec change, отклоняет запись вне `openspec/changes/<имя>/` (то же для команд shell в `hook pre-shell`) |

Куда положить — на выбор:
- **`.qwen/settings.json` проекта** (или каждого worktree) — только для этого проекта;
- **`~/.qwen/settings.json`** — для всех ваших сессий Qwen (вне сети хуки молчат: агента и сети нет — ничего не выводят);
- **отдельный файл + `QWEN_CODE_SYSTEM_DEFAULTS_PATH=/путь/к/файлу`** в окружении runner'а — не трогая ни проект, ни свой
  `~/.qwen`; это самый низкий приоритет настроек Qwen, хуки из него добавляются к остальным. Проверено: Qwen подхватывает
  хуки из такого файла.

Агента хук берёт из `--agent`, иначе из `AGENT_ID` сессии (runner его задаёт; Qwen передаёт хукам своё окружение), иначе
ищет по дереву процессов; сеть — `--network-dir`, иначе `NETWORK_DIR`, иначе git-репозиторий папки. Вживую с моделью
срабатывание `PostToolUse`/`PreToolUse` у Qwen пока не проверено (LM Studio был недоступен) — проверьте одной задачей.

### Codex CLI *(не проверялось)*

У Codex таймаут вызова tool по умолчанию 60 с, а `wait` по умолчанию ждёт 120 с: добавьте в `env`
`AGENT_NETWORK_WAIT_MS = "50000"`.

Конфиг глобальный (`~/.codex/config.toml`), поэтому идентичность удобнее задавать пулом:

```toml
[mcp_servers.agent-network]
command = "node"
args = ["/abs/path/agent-network-mcp/dist/index.js"]
env = { AGENT_ID = "backend,reviewer", AGENT_TYPE = "codex", NETWORK_DIR = "/abs/path/project/.agent-network" }
```

Codex читает `AGENTS.md` из корня проекта.

### Свои MCP-серверы для агентов runner'а (например, Serena)

Агентам роя можно дать и другие MCP-серверы — например, [Serena](https://github.com/oraios/serena) для навигации по
коду. Подтянутся ли они сами, зависит от CLI:

- **Qwen Code.** Runner запускает его с `--mcp-config qwen-mcp.json`. Судя по `qwen --help`, этот файл добавляется к
  серверам из `~/.qwen/settings.json`, а не заменяет их (флага вроде `--strict-mcp-config` у Qwen нет). Поэтому сервер,
  добавленный глобально (`qwen mcp add …`), скорее всего стартует и в сессиях runner'ов. *Вживую с Serena не проверялось.*
- **Claude Code.** Нет: в примере стоит `--strict-mcp-config`, и сессия видит только серверы из `mcp.json`.

Чтобы агенты могли **пользоваться** сервером, а не только видеть его, нужны ещё две вещи:

1. **Разрешить его инструменты.** В headless-режиме Qwen без подтверждения выполняет только то, что есть в
   `--allowed-tools`; остальное отклоняется. Добавьте в `command` в `runners.json` `"mcp__serena"` рядом с
   `"mcp__agent-network"`. У Claude Code — то же в `--allowedTools`, плюс сам сервер в `mcp.json`.
2. **Смотреть в worktree агента.** Указывайте в настройке Serena проект как текущую папку, а не абсолютный путь. CLI
   запускает MCP-серверы в папке сессии, а runner — в `cwd` агента, так что у `backend`, `reviewer` и `tester` будет
   каждый свой код, а не общий проект.

**Где подключать.** Лучше не глобально, а в тот же `qwen-mcp.json` (у Claude Code — `mcp.json`), рядом с
`agent-network`. Тогда сервер будет только у агентов роя, а ваши обычные сессии CLI его не увидят. Надзору на Qwen
такие серверы не нужны: если подключили глобально, добавьте в его `command` `--allowed-mcp-server-names supervisor`, иначе
описания чужих инструментов попадут ему в контекст.

**Цена.** Описания инструментов перечитываются на каждом ходе. Serena добавляет пару десятков инструментов, и токенов на
ход станет заметно больше: примеры специально держат контекст коротким. Лишние инструменты отключайте через
`--exclude-tools` (Qwen) или не перечисляйте в `--tools` (Claude Code).

### Сабагенты у агентов роя

Агент роя может раздавать сабагентам ограниченные поручения внутри своей сессии: прочитать и свести много файлов,
выяснить, почему падает один тест, посмотреть свой diff глазами ревьюера. Сабагент работает в своём контексте и
возвращает агенту короткий итог, поэтому длинный вывод не попадает в контекст агента.

- **Claude Code** — в примере `Agent` есть в `--tools` и `--allowedTools`. `--agents` описывает сабагента `helper`:
  только `Read`, `Grep`, `Glob`, `Bash`, файлы не меняет, отвечает коротко. Агенту доступны также проектные агенты
  из `.claude/agents/` (например, `critic`) и встроенные.
- **Qwen Code** — в примере `agent` не исключён, `--max-subagent-depth 1` (сабагент своих не запускает). Флага вроде
  `--agents` у Qwen нет: `helper` — это файл [qwen-agents/helper.md](examples/runner/qwen-agents/helper.md), его кладут
  в `~/.qwen/agents/` (видят все проекты и worktree) или в `.qwen/agents/` проекта с коммитом.
  - В живой проверке на `qwen3.5-9b` модель верно решила отдать поиск `helper`, но вызвала `agent` через посредника
    `tool_call` (через него Qwen показывает MCP-инструменты роя) и получила отказ «Tool "agent" is already visible…
    Call it directly», после чего искала сама. Теперь `qwen-prompt.md` говорит: встроенные инструменты — напрямую.
  - Там же: Qwen в headless-режиме отклоняет составные команды целиком (`cd … && git commit`, `grep … | head`), даже
    если сама команда разрешена. Промпт велит одну простую команду на вызов и поиск через `grep_search`.
  - Небольшая модель может и с подсказкой путаться в вызове; для сабагентов надёжнее модель покрупнее
    (`qwen3-coder-30b`).
  - Проверить у себя: `bash examples/runner/try-subagents-qwen.sh` (по умолчанию `qwen/qwen3.5-9b` и LM Studio на
    `http://192.168.31.7:1234/v1`; другой адрес — `BASE_URL=http://127.0.0.1:1234/v1 bash …`). Скрипт собирает во
    временной папке маленький git-проект с TODO, двух агентов и `helper`, поднимает страницу на `:4793` и в конце пишет,
    вызывался ли сабагент, трогал ли он инструменты роя и что получилось в `TODO_REPORT.md`.
- **С роем говорит только сам агент.** Сабагент не вызывает инструменты agent-network (`complete`, `send_message`,
  `subtasks`…), иначе он действовал бы от имени агента в обход протокола. Встроенный `general-purpose` унаследовал бы
  эти инструменты, поэтому системный промпт велит брать `helper` или проектного агента и писать это в поручении.
  Это правило промпта: сервер отличить вызов сабагента от вызова самого агента не может.
- **В ленте «Активность»** события сабагента помечены «↳ сабагент» и выделены цветом. Вызов сабагента показан как
  `Agent` — `helper: <поручение>`. В сырой лог runner'а попадает только работа самой сессии.
- **Стоимость.** Каждый сабагент — отдельный контекст и отдельные токены. Она входит в стоимость сессии, которую
  сообщает CLI. Выгодно, когда поручение экономит агенту больше чтения, чем стоит само.
- **Выключить** — убрать `Agent` из `--tools` (Claude) или добавить `agent` в `--exclude-tools` (Qwen).

### Lead добавляет агентов в команду (`spawn_agent`)

Сабагент живёт внутри сессии агента. Если нужен полноценный участник роя — со своей папкой, своей частью работы и
ревью, — lead может добавить его сам, не прописывая заранее в задаче:

```json
"spawn": {
  "templates": {
    "backend": { "description": "Another developer: production code and its tests for an independent part of the work." },
    "tester":  { "description": "A tester: cross-cutting tests in its own test package.", "model": "haiku",
                 "instructionsFile": "{agentNetworkMcp}/examples/runner/instructions/tester.md" }
  },
  "maxPerTask": 2
}
```

- **Шаблон** — агент без `id`: любые поля агента (`model`, `command`, `instructionsFile`…), остальное из `defaults`;
  `description` обязателен — его читает lead. Проверяется при старте, как обычные агенты.
- **Только с вашего разрешения:** галочка «Lead может добавлять агентов» в форме задачи (`task create --spawn` в
  CLI), по умолчанию выключена. Без неё lead не видит `spawnable`, а `spawn_agent` отказывает: работа делится между
  агентами задачи. Причина — стоимость: добавленный агент — отдельная сессия, в замерах это +$0.25–0.39 к задаче
  за ~$0.9. Follow-up задачи наследуют галочку; поручения (`delegate`) от неё не зависят.
- **Когда:** только lead, только в DISCUSS и до `propose()`. В `swarm_context` lead видит `spawnable` (шаблоны и
  сколько ещё можно), в подсказке — когда это оправдано. `spawn_agent({template, reason, id?})` добавляет агента в
  задачу: id свежий (`backend-2`) или свой, если не занят.
- **Runner** страница запускает сама за пару секунд: в своём worktree `<проект>-backend-2` на ветке
  `swarm-backend-2` (если у шаблона есть worktree). Дальше это обычный участник: получает часть в `propose()`,
  одобряет соглашение, работает, ревьюит. Когда его задача закрыта, runner останавливается.
- На странице такой агент помечен «добавлен lead'ом · шаблон», с причиной во всплывашке; в runner'ах — «нет в
  runners.json». Модель ему можно сменить на странице, но в файл это не пишется.
- **Роли.** Шаблон решает, *на чём* агент работает (CLI, модель, права в shell, стоимость), роль — *что* он делает.
  Lead даёт роль при добавлении: `spawn_agent({template: "backend", reason, role: "architect", instructions: "..."})` —
  своя, написанная под задачу (40–6000 символов: что делает, на что смотрит, какими скиллами пользуется, чего не
  делает, как отчитывается), или `role: "architect"` без `instructions` — из **библиотеки ролей** проекта
  (`.agent-network/roles/<имя>.md`, первая строка — описание; lead видит их в `spawnable.roles`). Runner получает роль
  как инструкции: сначала роль, потом инструкции шаблона. Права роль не расширяет: нагрузочному тестировщику с `k6`
  нужен шаблон с `Bash(k6:*)`, его заводите вы.
- **Библиотека ролей.** Удачную роль, которую написал lead, сохраняет кнопка «Сохранить роль в библиотеку» в блоке
  «Добавлены lead'ом» карточки задачи; на вкладке «Runner'ы» — список ролей проекта (посмотреть, удалить). Дальше
  lead берёт её по имени, не переписывая.
- **Ограничения:** `maxPerTask` на задачу и лимит стоимости задачи. После перезапуска страницы runner добавленного
  агента поднимается снова, пока его задача открыта; его worktree «Убрать worktree» не видит, если runner не в пуле.
  Без секции `spawn` инструмент недоступен.


### Lead поручает работу новому раннеру (`delegate`)

`spawn_agent` добавляет в задачу полноценного участника: он проходит все фазы, ревьюит и ревьюится. Для разовой работы
это тяжело. В IMPLEMENT и INTEGRATE lead может вместо этого **поручить** самостоятельный кусок новому раннеру из тех же
шаблонов `spawn`: нагрузочный тест, тест конкурентности, поиск причины падения, замер.

- `delegate({template, job, files?, role?})` создаёт **задачу-поручение** на одного агента (`tester-job1`). Она сразу в
  IMPLEMENT, без соглашения и ревью, со своей веткой от последнего коммита lead'а (`git merge <baseCommit>`) и с
  лимитом стоимости родительской задачи. Раннер запускается сам, как у `spawn_agent`.
- У lead'а появляется открытая подзадача «delegated to tester-job1: …»: свою часть он не сдаст (`OPEN_SUBTASKS`), а
  интеграцию с PASS — тоже (`JOBS_OPEN`), пока поручение не вернулось.
- `complete()` исполнителя завершает поручение (DONE). Lead получает сообщение с итогом, файлами и коммитами
  (`git merge <commit>`), его подзадача отмечается выполненной. Отменили поручение — подзадача снимается, lead узнаёт.
- Лимит `maxPerTask` общий для добавленных агентов и поручений. Поручение не поручает дальше.
- На странице: у задачи блок «Поручения» со статусом и итогом, у самого поручения — «поручение от task-001».

### Пул идентичностей (`AGENT_ID=a,b,c`)

Один процесс — ровно одна идентичность (иначе агент мог бы одобрять и ревьюить сам за себя). Пул лишь решает, *какая*:
при старте процесс атомарно (под lock) занимает первое имя, которое не держит живой процесс. Имя, оставшееся за умершим
процессом или `OFFLINE`, перехватывается. Если все имена заняты, сервер не стартует. Значение — строка; массивов в `env`
CLI не бывает.

### Два агента в одной папке или в worktree?

Для проверки протокола и небольших задач с непересекающимися файлами хватает одной папки проекта (но параллельные
сборки в одной папке мешают друг другу: общий `target/`, `node_modules/.cache`). Для настоящей параллельной работы
заведите по git worktree на агента (`git worktree add ../proj-backend -b swarm-backend`) и в каждом положите конфиг MCP
с общим `NETWORK_DIR`. Worktree одного репозитория делят базу объектов, поэтому коммит из любого worktree виден серверу
и остальным агентам по хэшу; ветки агентов в конце сливает lead (фаза INTEGRATE). Скрипт [scripts/qwen-demo.sh](scripts/qwen-demo.sh) собирает такой стенд с нуля
(демо-репозиторий, два worktree, конфиги Qwen, готовая задача).

### Несколько проектов (`NETWORK_DIR=auto`)

Чтобы не прописывать путь к сети в конфиге каждого проекта, задайте в глобальном конфиге MCP (`~/.qwen/settings.json`,
`~/.claude.json` или `claude mcp add --scope user`) `"NETWORK_DIR": "auto"`. Сервер найдёт сеть по git-репозиторию папки,
где запущена сессия: `<корень основного checkout>/.agent-network`. Корень берётся из `git rev-parse --git-common-dir`,
он общий у всех worktree репозитория, поэтому агенты в `shop`, `shop-backend` и `shop-reviewer` попадают в одну сеть
`shop/.agent-network`, а агент, открытый в `blog`, — в сеть `blog`. Вне git-репозитория сервер не стартует и пишет
почему. Id агентов живут внутри сети, так что `backend` в двух проектах одновременно не конфликтует.

Это включается только явным `auto`: без `NETWORK_DIR` сервер по-прежнему не стартует, чтобы `.agent-network` не
появлялась в каждом репозитории, где вы открыли CLI. Добавьте `.agent-network/` в `.gitignore` проектов.

**Что поправить, чтобы включить** (один раз, в глобальном конфиге MCP; проверено на Claude Code и Qwen Code 0.24.7):

- **Qwen** — `~/.qwen/settings.json`, значение `mcpServers.agent-network.env.NETWORK_DIR`:
  ```json
  "mcpServers": {
    "agent-network": {
      "command": "node",
      "args": ["/abs/path/agent-network-mcp/dist/index.js"],
      "env": { "AGENT_ID": "backend,reviewer", "AGENT_TYPE": "qwen", "NETWORK_DIR": "auto" }
    }
  }
  ```
- **Claude Code** — сервер уровня пользователя (то же самое можно написать в `~/.claude.json`, раздел `mcpServers`):
  ```bash
  claude mcp add agent-network -s user -e AGENT_ID=backend,reviewer -e AGENT_TYPE=claude -e NETWORK_DIR=auto -- node /abs/path/agent-network-mcp/dist/index.js
  ```

Проверка: откройте CLI в папке проекта (или в его подпапке, или в worktree) и выполните там
`node /abs/path/agent-network-mcp/dist/index.js agent list` — агент должен быть в списке. Чтобы вернуть прежнее, поставьте
вместо `auto` абсолютный путь. Папка вне git-репозитория с `auto` не работает (сервер не стартует, клиент покажет его
отключённым): для неё задайте путь явно — запуском `NETWORK_DIR=/abs/path/.agent-network qwen` или конфигом в самом проекте.
Runner'ы и `runners.json` от этой настройки не зависят: runner передаёт каждой сессии явный путь.

Операторские команды (`task`, `agent`, `ui`, `run`, `hook`) без `--network-dir` и `NETWORK_DIR` находят сеть так же —
по репозиторию текущей папки (`run` — по `--cwd` агента). Команды, которые только смотрят (`task list`, `task stats`,
`agent list`), сеть не создают, а сообщают, что её ещё нет; `task create` создаёт. Для runner'ов — свой `runners.json` на
проект и одна страница на все: `ui --runners shop.json --runners blog.json` (см. [UI](#ui)).

## Протокол

| Фаза | Что происходит | Переход дальше |
|---|---|---|
| **DISCUSS** | Агенты обсуждают (`send_message`), один делает `propose` (agreement: summary, **по одному assignment на каждого агента**, decisions, interfaces), все делают `complete()` = approve | все assigned агентов одобрили → **IMPLEMENT** (автоматически) |
| **IMPLEMENT** | Каждый работает над своим assignment, затем `complete({result, filesChanged, commits?})` | все `READY_FOR_SYNC` → **SYNC** (автоматически) |
| **SYNC** | Ревьюеры проверяют чужую работу (`reviewTargets`) и сдают `complete({status: PASS \| NEEDS_FIX, findings})` | когда отчитались **все** ревьюеры раунда: хоть один `NEEDS_FIX` → **IMPLEMENT**, иначе → **INTEGRATE** |
| **INTEGRATE** | Lead (первый в `--agents`) сводит работу всех (при отдельных worktree сливает ветки), запускает сборку и все тесты (`verifyCommand`), сдаёт `complete({status, result, commits, findings?})` | `PASS` → **DONE**; `NEEDS_FIX` → **IMPLEMENT** |
| **DONE** | Задача завершена | — |

Допустимы только переходы `DISCUSS→IMPLEMENT`, `IMPLEMENT→SYNC`, `SYNC→INTEGRATE`, `SYNC→IMPLEMENT`, `INTEGRATE→DONE`,
`INTEGRATE→IMPLEMENT` (`PhaseManager`, любой другой даёт `INVALID_TRANSITION`). Фаза меняется только как следствие
протокольных действий агентов.

**Раунд ревью собирается целиком.** `NEEDS_FIX` не прерывает раунд: задача ждёт отчётов всех ревьюеров и только потом
уходит в IMPLEMENT. Так ничья проверка не пропадает, а исправляющий получает все замечания сразу (`fixRequests`).

**`NEEDS_FIX` только для ERROR.** `NEEDS_FIX` требует хотя бы одного finding с `severity: ERROR` (дефект или нарушение
agreement); `WARNING`/`INFO` сдаются вместе с `PASS` как заметки. `PASS` с ERROR-находкой отклоняется. Чинят агенты,
названные в `relatedAgent` ERROR-находок; если не назван никто, переделывают все. Остальные остаются `READY_FOR_SYNC`.

**Повторное ревью только исправленного.** После исправлений начинается новый раунд SYNC (`syncRound`), но проверяется только
работа исправлявших (`reviewScope`): ревьюерами становятся все остальные, исправлявший ждёт. С двумя агентами это одно ревью
вместо двух, с тремя — два вместо шести. Если исправляли все, все ревьюят всех.

**Интеграция.** Без неё в конце остались бы неслитые ветки, а общую сборку никто бы не запускал. Lead сливает ветки (или, в
одной папке, просто берёт HEAD), запускает `verifyCommand` (или сборку и тесты проекта) и сообщает результат. Конфликт или
красные тесты — `NEEDS_FIX` с ERROR-находкой на виновника; после исправления — ревью исправленного и снова интеграция.

**Лимит раундов.** У задачи `maxFixRounds` (по умолчанию 3, `task create --max-fix-rounds N`): сколько раз ревью или
интеграция могут вернуть её в IMPLEMENT. Если `NEEDS_FIX` приходит, когда раунды исчерпаны, задача не зацикливается, а
получает статус `BLOCKED` (`blockedReason`), агентам говорят ждать. Оператор решает: кнопка «Разблокировать +1/+2/+3» в карточке задачи на странице или `task unblock --id ... [--rounds N]`
(добавляет раунды, отложенное исправление стартует сразу) или `task cancel`.

**Исправление без изменений — сразу к оператору.** Ревью после раунда исправлений снова находит ERROR у агента, который
в этом раунде ничего не принёс: ни коммита сверх тех, что он сдал до раунда (без git — ни одного изменённого файла).
Значит, проблема та же, и следующие раунды ничего не изменят. Задача сразу становится `BLOCKED` с причиной «… again for
tester, which delivered nothing in the last fix round», не дожидаясь `maxFixRounds`. В прогоне `add-multi-currency`
Haiku-тестер три раунда подряд сдавал те же коммиты, и задача упёрлась в лимит только на четвёртом. После
«Разблокировать» этот раунд идёт дальше и повторно не блокируется.

**Оператор молчит — исправление берёт lead.** Застрявшая задача (исправление без изменений или исчерпанные раунды) ждёт
оператора столько же, сколько вопрос, — `AGENT_NETWORK_OPERATOR_TIMEOUT_MIN`, по умолчанию 10 минут. Если за это время
никто не решил, исправление застрявших агентов на один раунд переходит к lead'у:

- их ERROR-находки становятся его (`fixRequests[].forYou`), их файлы на этот раунд выдаются ему через grants, подсказка
  говорит «you take over the fix of tester»; застрявший агент этот раунд ждёт;
- переход делает тот, кто первым увидит истёкший срок: runner (он и так ждёт `BLOCKED`-задачу без модели), открытая
  страница или `wait()` агента в интерактивной сессии; задача меняется под блокировкой, второго перехода не будет;
- ревью исправления lead'а: PASS — дальше как обычно; снова `NEEDS_FIX` — задача окончательно `BLOCKED` с причиной «the
  lead could not resolve it either», без таймера: решает только оператор;
- передачи нет, если исправлять должен сам lead: передавать некому.

На странице у такой задачи видно, до какого времени ждут, и кнопки «+1/+2/+3» (ещё раунды застрявшему), «Отдать lead'у
сейчас» и «Отменить задачу». В CLI — `task handover --id ...`. Ждать не нужно — `AGENT_NETWORK_OPERATOR_TIMEOUT_MIN=1`
(минимум) или кнопка «Отдать lead'у сейчас».

**Защита от слепого approve.** `complete()` в DISCUSS одобряет только ту версию agreement, которую процесс уже показал
агенту (в `swarm_context`, ответе `propose` или теле ошибки `AGREEMENT_NOT_REVIEWED`). Повторный `propose` заменяет
agreement, увеличивает `version` и сбрасывает одобрения.

**Поля не из текущей фазы.** `complete()` принимает у каждой фазы свой набор полей (DISCUSS — никаких, IMPLEMENT —
`result, filesChanged?, commits?, tasksDone?`, SYNC — `status, findings?`, INTEGRATE — `status, result, commits?,
findings?, followUps?`). Поле не из этого набора не обрывает вызов: оно отбрасывается, а в `warnings` попадает
`"ignored fields not used in this phase: ..."`. Обязательные поля фазы (`result` в IMPLEMENT/INTEGRATE, `status` в
SYNC/INTEGRATE) по-прежнему требуются — их отсутствие остаётся `INVALID_INPUT`.

**Текущая задача.** Агент работает с самой старой `ACTIVE` задачей, где он назначен (после её завершения или отмены
переходит к следующей). Поэтому ни один tool не принимает `taskId`.

Статусы задачи: `ACTIVE`, `BLOCKED` (исчерпан лимит раундов, ждёт оператора), `COMPLETED`, `CANCELLED` (отменяет оператор).
Заблокированная задача остаётся текущей для своих агентов, пока оператор её не разблокирует или не отменит.

### Подзадачи и follow-up задачи

**Подзадачи** — план агента для своей части. Большое задание агент делит на шаги (`subtasks({add: [...]})`), отмечает
текущий (`start`) и выполненные (`done`), лишние снимает с причиной (`drop`). Список лежит в
`tasks/<id>/subtasks/<agent>.json`: перезапущенная runner'ом сессия видит в `swarm_context`, что уже сделано, коллеги видят
прогресс (`otherAgents[].subtasks: "2/5 done, s3 in progress"`), ревьюер в SYNC — весь план рядом с кодом. `complete` в
IMPLEMENT не принимается, пока шаги открыты (`OPEN_SUBTASKS`).

#### Follow-up задачи

Если по итогам задачи остались правки, которые её не блокируют (WARNING/INFO из ревью, замеченное при слиянии), lead
сам ставит под них новые задачи — при условии, что оператор разрешил это при создании:

```bash
node dist/index.js task create --network-dir <dir> --agents backend,reviewer --title "..." --description "..." --follow-ups 3
```

- `--follow-ups N` — бюджет на **всю цепочку**: задача и все её follow-up'ы вместе создадут не больше N задач. Без флага —
  0, как раньше. `task list` показывает `followUps: "1/3 used"` у корня и `parentTaskId` у follow-up'ов.
- На INTEGRATE lead видит `followUps: {max, used, remaining, notes}` (`notes` — несрочные замечания ревью) и при PASS
  передаёт `complete({status: "PASS", result, commits, followUps: [{title, description, agents?}]})`. Описание конкретное
  (≥ 40 символов), `agents` по умолчанию те же (первый — lead). С `NEEDS_FIX` follow-up'ы не принимаются: дефекты чинятся в
  самой задаче. Сверх бюджета — `FOLLOW_UP_LIMIT`, задача при этом не меняется.
- Задача переходит в DONE, и follow-up'ы сразу становятся текущими задачами агентов: runner'ы запускают новые сессии,
  агенты в `wait()` получают `UPDATED`. Наследуются `--verify` и лимит раундов.
- **База кода.** У follow-up'а `baseCommit` = слитый HEAD родителя. Агент сначала делает `git merge <baseCommit>` в свою
  ветку; коммиты, которые его не содержат, отклоняются с этой командой в тексте ошибки.

### Коммиты

Коммиты сервером не проверяются. Агент может передать их в `complete({..., commits})` — они записываются как есть и
видны остальным в `teamImplementations`. Если агент в своей ветке забыл передать хэш, сервер записывает HEAD его ветки
сам и пишет об этом в `warnings`; если в ветке с начала задачи (или с прошлого отчёта, в раунде исправлений) нет новых
коммитов — предупреждает, что ревьюеры его изменений не увидят. **В отдельном worktree коммит нужен до `complete()`**: незакоммиченные правки
лежат только в папке автора, ревьюер их не видит, а lead сливает ветки только по коммитам. Сервер сравнивает папку агента
с checkout'ом, где создана задача; если у агента своя ветка, подсказка `implement`/`fix` говорит «закоммить перед
`complete()`». Ревьюер, не увидевший изменения из `filesChanged`, просит автора закоммитить, а не пишет NEEDS_FIX. В
общей папке коммиты по-прежнему необязательны. Изменённые файлы — это `filesChanged`, который сообщает агент; владение проверяется по нему.
У follow-up задачи `baseCommit` — HEAD, который lead назвал при INTEGRATE: подсказка, откуда начинать, а не требование.
Флаг `task create --no-commits` устарел и ничего не делает.

## Tools

Агент видит **тринадцать** tools: основной цикл (`swarm_context`, `propose`, `complete`, `send_message`, `wait`), свой
чек-лист и сборку (`subtasks`, `build`), контракт API задачи (`contract`), инструменты lead'а (`plan`, `spawn_agent`, `delegate`, `resolve_comments`) и
`create_task`. Каждый вызов, которого нет в `allowedActions`, сервер отклоняет с подсказкой. Идентичность отправителя всегда берётся из `AGENT_ID` процесса; поля `from`/`agentId` в
аргументах игнорируются.

| Tool | Аргументы | Что делает |
|---|---|---|
| `swarm_context` | — | Всё для решения «что дальше»: задача (с `lead`, `maxFixRounds`, `verifyCommand`, `blockedReason`), фаза, ваше assignment, другие агенты, `pendingMessages`, agreement, implementations коллег (`teamImplementations`; в SYNC без авторского `summary`), в SYNC `reviewTargets`, после исправлений `fixedFindings`, а в `teamImplementations` — `notInYourBranch` (коммиты автора, которых нет в вашей ветке), `integration`, `fixRequests`, `handoff` (сессию сменяет свежая), `allowedActions`, `nextAction`, `hint`, `exampleCall` (для `propose` и `respond`). Только чтение, можно звать когда угодно |
| `create_task` | `title`, `description`, `agents` (обязательны), `verifyCommand?` | Начать новую задачу, **только если пользователь попросил**. Создатель становится lead; `agents` — id *других* зарегистрированных агентов. Подробнее ниже |
| `send_message` | `to`, `message` (обязательны), `requestFiles?`, `grantFiles?` | Сообщение одному другому агенту задачи; через `requestFiles`/`grantFiles` ведутся переговоры о чужих файлах |
| `propose` | `summary`, `assignments[{agentId, responsibility, files, tasks?, dependsOn?}]` (обязательны первые три), `decisions?`, `interfaces?` | Только DISCUSS: предложить/заменить agreement. У каждого агента заявлены **файлы** (пути или маски), заявки не должны пересекаться; `dependsOn` — см. [Зависимости](#зависимости-dependson-тесты-против-настоящего-кода) |
| `subtasks` | `add?`, `start?`, `done?`, `drop?[{id, reason}]` | Свой план части задачи: шаги `s1`, `s2`…, один «в работе», отметки о выполнении, снятые шаги с причиной. Хранится на сервере (перезапущенная сессия видит, что сделано), прогресс видят остальные. `complete` в IMPLEMENT отказывает (`OPEN_SUBTASKS`), пока есть открытые шаги. Ответ компактный |
| `build` | `command?`, `timeoutMin?`, `in?` | Сборка или тесты в папке агента; ответ — итог, число тестов и что упало, полный лог в файле. Без `command` — `verifyCommand` задачи; `in: "contract"` — в worktree контракта задачи (по умолчанию его `install`). Подробнее — [Сборка и тесты через `build`](#экономия-токенов-короткая-база-и-компактный-swarm_context) |
| `contract` | `file?`, `diff?` | Задача, которая меняет контракт API: его координаты, версия, изменённые файлы, файл, дифф. Только чтение; меняет контракт lead — [Контракт API в другом репозитории](#контракт-api-в-другом-репозитории) |
| `complete` | зависит от фазы | DISCUSS: без аргументов — одобрить agreement. IMPLEMENT: `{result, filesChanged?, commits?, tasksDone?}` — своя часть готова. SYNC: `{status: PASS\|NEEDS_FIX, findings?}` — ревью. INTEGRATE (lead): `{status, result, commits?, findings?, followUps?}` |
| `plan` | `html?`, `edits?[{find, replace}]`, `note?`, `read?` | Lead, задача с «Планом на утверждение»: план HTML-страницей; оператор правит и утверждает его на странице. См. [План на утверждение](#план-на-утверждение) |

| `delegate` | `template`, `job`, `files?`, `role?`, `instructions?` | Lead, IMPLEMENT/INTEGRATE: поручить самостоятельный кусок новому раннеру; возвращается lead'у как подзадача |
| `resolve_comments` | `resolve[{id, status, note?}]` | Lead: ответить на замечания оператора к диффу — исправлено или отклонено с причиной |

### Интеграция: PASS только после зелёной сборки

Если у задачи есть `verifyCommand`, интеграцию с PASS сервер принимает, только когда последний `build()` lead'а — это
`verifyCommand`, он зелёный, запущен в этом раунде INTEGRATE на коммите, который lead называет итоговым (`commits`), и
без незакоммиченных изменений. Иначе — `VERIFY_REQUIRED` с тем, чего не хватает. «Готово» значит зелёная сборка,
а не слово агента.

С PASS задачи с кодом lead сдаёт и **таблицу приёмки** (`acceptance`): по критерию на требование, тесты и код, которые
его доказывают, ручная проверка, риски. Сервер проверяет, что каждый названный файл и метод теста есть в итоговом
коммите. По ней вы принимаете задачу: [Приёмка](#приёмка-пакет-вместо-диффа).

### Файлы: кто что меняет

**Проверка по git, а не по списку агента.** Если агент работает в своей ветке (worktree), при сдаче части сервер сам
берёт файлы из его коммитов с начала задачи — без коммитов-слияний и без подтянутой работы других агентов — и
добавляет их к `filesChanged`. Чужой файл, изменённый в коммите и не указанный в списке, даёт тот же отказ
`FILE_NOT_OWNED`; свой забытый файл просто добавляется с предупреждением.

Чтобы агенты не затирали друг другу правки, в DISCUSS они сообщают друг другу, какие файлы будут менять, и закрепляют это в agreement:

1. В `propose` у **каждого** агента обязательно поле `files` (пути или маски: `src/main/**`, `src/*.java`, `src/test/Foo.java`;
   `dir/` = вся директория). У каждого файла ровно один владелец: пересекающиеся заявки сервер отклоняет с `FILE_OVERLAP` и
   показывает, какие именно заявки конфликтуют. Одобряя agreement, агент видит файлы всех (`ownership` в `swarm_context`).
2. В IMPLEMENT агент меняет только свои файлы. **Читать можно любые файлы без разрешения** — владение касается только изменений. Нужно изменить файл другого — просьба владельцу:
   `send_message({to: owner, message: "зачем", requestFiles: ["src/test/Helper.java"]})`. Сообщение приходит владельцу с типом
   `FILE_REQUEST` и списком файлов (сервер проверяет, что адресат действительно владелец). Запросивший не ждёт сложа руки:
   он продолжает свою работу, а запрос виден у него в `yourOpenRequests`.
   **Запрос открыт, пока владелец не ответит запросившему** (разрешением или любым сообщением-отказом); просто прочитать его
   недостаточно. Пока запрос открыт, у владельца `nextAction` = **`respond`** (с `openFileRequests` и готовым `exampleCall`),
   и это действие идёт раньше его собственной работы: другой агент заблокирован. `wait` в этом состоянии возвращается сразу.
   Занятый агент видит такие запросы, если вызывает `swarm_context` между шагами работы (так требуют `AGENTS.md` и инструкции).
3. Владелец разрешает: `send_message({to, message: "условия", grantFiles: [...]})` (сервер проверяет, что файлы его, и записывает
   разрешение в `tasks/task-NNN/grants/`; у получателя оно видно в `ownership.grantedToYou`). Отказ — обычное сообщение с причиной.
4. `complete` в IMPLEMENT отклоняется с `FILE_NOT_OWNED`, если в `filesChanged` есть чужой файл без разрешения (ответ называет
   файлы и владельцев). Файлы, которые никто не заявил, допускаются с предупреждением `warnings`: нужно сообщить остальным.

Агенту, которому нечего менять (только проверяет чужую работу), дают `files: []`: он ничего не правит, читает любые
файлы, сразу сдаёт IMPLEMENT (`complete({result: "review only"})`) и работает в SYNC. Хотя бы один агент должен владеть
файлами. Без этого слабые модели выдумывали «свой» файл (SUMMARY.md, CONTRIBUTING.md), лишь бы заявка не была пустой.

Маски сравниваются точно: `src/*Controller.java` и `src/*Service.java` не пересекаются, поэтому делить файлы можно и внутри
одной директории; `src/**/*Test.java` и `src/main/**` пересекаются (`src/main/FooTest.java`).

Это договорённость, а не файловая блокировка: сервер не следит за диском и сверяет заявки с тем, что агенты сообщают в
`filesChanged`. Для настоящей параллельной работы
по-прежнему лучше worktree на каждого агента.

### Зависимости (`dependsOn`): тесты против настоящего кода

Тестер пишет тесты API параллельно с разработчиком, то есть против кода, которого ещё нет. В прогоне `add-multi-currency`
Haiku-тестер угадал путь (`/api/orders` вместо `/orders`) и способ передать клиента (тело вместо `X-Customer-Id`), хотя
контракт был в `interfaces`. Ошибку нашли только ревьюеры в SYNC, четыре раунда исправлений ушли впустую, задача стала
`BLOCKED`. Теперь в `propose` у задания есть `dependsOn: ["backend"]`:

- агент по-прежнему работает параллельно: подсказка велит писать по `agreement.interfaces` и по коду как он есть
  (контроллеры, классы запросов и ответов), ничего не угадывая;
- его `complete()` в IMPLEMENT принимается, только когда все из `dependsOn` сдали свою часть (`READY_FOR_SYNC`), иначе
  `DEPENDENCY_NOT_READY`. После такого отказа `nextAction` — `wait` (без `complete`), и `wait()` будит агента, когда
  зависимость сдаётся;
- в своём worktree он должен ещё и влить их коммиты: подсказка называет `git merge <hash>`, а без этого `complete()`
  получает `DEPENDENCY_NOT_MERGED` (проверка та же, что `notInYourBranch` в SYNC). В итоге тесты прогоняются на настоящем
  коде ещё в IMPLEMENT, и несовпадение видит сам тестер, а не ревьюер;
- в `swarm_context` фазы IMPLEMENT — `dependsOn: [{agentId, reported, commits?, notInYourBranch?}]`, в карточке задачи на
  странице — «сдаёт после: …»;
- сервер отклоняет `dependsOn` на себя, на чужого агента, на агента без файлов (ревьюер: ждать нечего) и циклы.

Lead в DISCUSS записывает в `interfaces` точные контракты (метод, путь, заголовки, тело, коды) и ставит `dependsOn` тому,
чья работа вызывает новый код другого; так велят подсказка сервера и [инструкции ролей](examples/runner/instructions).

### `create_task` (задачу может создать агент)

Задачу создаёт либо оператор ([CLI](#cli-оператора)), либо агент по просьбе пользователя: «создай задачу для backend и reviewer:
...». Агент зовёт `create_task({title, description, agents: ["reviewer"]})`; он добавляется автоматически и становится
**lead**, остальные просыпаются со статусом `UPDATED`. Защиты от мусорных задач:

- только если у агента нет активной или заблокированной задачи (`HAS_ACTIVE_TASK`; отменённая или завершённая не мешает);
- `description` не короче 40 символов, без заглушек: проблема, ожидаемое поведение, файлы, кто что делает; в описании
  слова пользователя, придумывать задание нельзя (`AGENTS.md` это требует);
- `verifyCommand` — команда сборки/тестов для фазы INTEGRATE, только если пользователь её назвал;
- все агенты из `agents` уже зарегистрированы (иначе `AGENT_NOT_REGISTERED` со списком `registeredAgents`), то есть сначала
  запускаются оба CLI, потом создаётся задача;
- без активной задачи `swarm_context` показывает `allowedActions: ["create_task", "wait"]`, но `nextAction` остаётся `wait`:
  сам по себе агент задачу не начинает.

### `nextAction`

| Значение | Фаза | Что делать |
|---|---|---|
| `respond` | любая | другой агент ждёт ответа на запрос ваших файлов: ответить (`grantFiles` или отказ), потом продолжить |
| `propose` | DISCUSS | (lead) согласовать роли и вызвать `propose` |
| `approve` | DISCUSS | прочитать `agreement`, `complete()` одобряет, `propose` заменяет |
| `implement` | IMPLEMENT | сделать свою часть, `complete({result, ...})` |
| `fix` | IMPLEMENT | прочитать `fixRequests`, исправить, снова `complete` |
| `sync` | SYNC | проверить работу из `reviewTargets`, `complete({status, ...})` |
| `integrate` | INTEGRATE | (lead) свести работу всех, прогнать сборку и тесты, `complete({status, result, commits?})` |
| `wait` | любая | ничего не делать, вызвать `wait()` (в том числе если задача `BLOCKED`) |
| `done` | DONE | завершить работу |

`exampleCall` при `propose` и `respond` — готовый вызов с реальными id агентов (`{tool, args}`): помогает слабым моделям,
которые иначе шлют пустые аргументы.

### `wait`

Возвращается со `status`:

| status | Когда |
|---|---|
| `MESSAGES` | есть непрочитанные сообщения (в `pendingMessages`) |
| `ACTION_REQUIRED` | у агента появилось действие (`nextAction` ≠ `wait`) |
| `UPDATED` | сменилась задача, фаза или статус, но действия для агента нет (новая задача, откат в IMPLEMENT, отмена, `BLOCKED`) |
| `DONE` | задача завершена |
| `TIMEOUT` | ничего не произошло; просто вызвать `wait` снова |

Со всеми статусами, кроме `TIMEOUT`, приходит полный свежий контекст. `TIMEOUT` отвечает коротко (`task` с id/фазой/статусом,
`nextAction`, `allowedActions`, `waitingOn`, `hint`): пока агент ждёт медленного коллегу, каждый ход не тащит в его контекст
agreement и все implementations заново. Таймаут по умолчанию 120 с (раньше 30 с), то есть ждущий агент тратит в 4 раза меньше
ходов; его можно поменять через `AGENT_NETWORK_WAIT_MS`, держите его ниже таймаута вызова tool у клиента (у Codex 60 с). Если что-то уже требует внимания, `wait` возвращается сразу, так что заблокировать
агента с работой он не может. Решение принимается по состоянию на диске, а не по самому событию.

### Сообщения

Адресные: одно сообщение — один получатель. `swarm_context` **не** помечает их прочитанными (он идемпотентен): они
считаются прочитанными, когда агент совершает следующее действие (`send_message`, `propose`, `complete`, `wait`). После
рестарта непрочитанные показываются снова.

Оператор тоже пишет агентам. Ответ на вопрос (`send_message({to: "operator"})` → ответ со страницы) приходит тому, кто
спросил. Всё остальное, что оператор пишет сам (кнопка ✉ в карточке задачи или надзор), получает **только lead**: он
выполняет своё и передаёт остальным через `send_message` то, что касается их, — у команды один план и один голос. См.
[UI с runner'ами](#ui-с-runnerами-задачи-и-агенты-из-браузера). Для агента это обычные сообщения от `operator` в `pendingMessages`.

### Ошибки

Ошибки возвращаются с `isError: true`, без stack trace, в формате, пригодном для LLM:

```json
{
  "error": "INVALID_PHASE",
  "message": "propose is only available during DISCUSS (task is in IMPLEMENT).",
  "currentPhase": "IMPLEMENT", "status": "ACTIVE", "taskId": "task-001",
  "nextAction": "implement",
  "allowedActions": ["send_message", "complete", "wait"],
  "pending": ["reviewer"]
}
```

Плюс контекст по случаю: `validRecipients`, `taskAgents`, `agreement`, `networkDir`. Коды: `AGREEMENT_NOT_READY`,
`AGREEMENT_NOT_REVIEWED`, `AGENT_NOT_REGISTERED`, `AGENT_ALREADY_REGISTERED`, `TASK_NOT_FOUND`, `NO_ACTIVE_TASK`,
`INVALID_PHASE`, `INVALID_TRANSITION`, `FILE_OVERLAP`, `FILE_NOT_OWNED`, `HAS_ACTIVE_TASK`, `NOT_ASSIGNED`, `ALREADY_COMPLETED`, `NOT_STARTED`, `MESSAGE_NOT_FOUND`,
`FORBIDDEN`, `INVALID_INPUT`, `INVALID_CONFIG`, `TASK_BLOCKED`, `OPEN_SUBTASKS`, `DEPENDENCY_NOT_READY`, `DEPENDENCY_NOT_MERGED`, `FOLLOW_UP_LIMIT`, `LOCK_TIMEOUT`, `INTERNAL_ERROR`. После любой ошибки агент может
восстановиться вызовом `swarm_context`.

### Расширенный набор (только для отладки)

С `AGENT_NETWORK_ADVANCED=1` дополнительно доступны 19 мелких tools: `agent_register`, `agent_list`, `agent_heartbeat`,

`implementation_start/complete/list`, `sync_submit`, `sync_list`, `integration_submit`, `phase_get`. Для обычной работы не включайте.

## CLI оператора

Команды выполняются вне LLM. `--network-dir` (абсолютный путь) можно заменить переменной `NETWORK_DIR`; без обоих команда
берёт сеть git-репозитория текущей папки (см. [Несколько проектов](#несколько-проектов-network_dirauto)).

```bash
node dist/index.js task create  --network-dir <dir> --agents backend,reviewer --title "..." [--description "..."] \
                               [--verify "mvn -q verify"] [--max-fix-rounds 3] [--follow-ups 0] [--openspec <change>]
node dist/index.js task list    --network-dir <dir>      # id, title, phase, status, agents, syncRound, maxFixRounds, blockedReason
node dist/index.js task stats   --network-dir <dir> [--id task-001] [--runners runners.json]   # время, токены, стоимость (с ценами из runners.json)
node dist/index.js task cancel  --network-dir <dir> --id task-001 [--reason "..."]
node dist/index.js task unblock --network-dir <dir> --id task-001 [--rounds 1]
node dist/index.js task handover --network-dir <dir> --id task-001   # застрявшее исправление — lead'у сейчас
node dist/index.js agent list  --network-dir <dir>      # id, type, role, status, lastSeenAt, pid
node dist/index.js supervisor journal  --network-dir <dir> [--task task-001] [--since 24h] [--kind note,action] [--json]   # журнал надзора
node dist/index.js supervisor sessions --network-dir <dir>               # сессии надзора: инциденты, итог, стоимость
node dist/index.js supervisor session 3 --network-dir <dir> [--full]     # одна сессия надзора целиком
node dist/index.js ui          --network-dir <dir> [--port 4777] [--runners runners.json ...]   # см. «UI»
node dist/index.js run --agent backend --network-dir <dir> [--cwd <dir>] [--once] -- claude -p "{prompt}" ...   # см. «Runner»
```

- `task create` не требует, чтобы агенты уже были запущены: они подхватят задачу при старте (`swarm_context`/`wait`).
  С `--openspec <change>` задача реализует готовый OpenSpec change, а `--title` и `--description` можно не задавать
  (см. [OpenSpec](#openspec-рой-по-готовому-change)).
- `task unblock` для `BLOCKED`-задачи добавляет `--rounds` раундов исправлений (по умолчанию 1) и сразу запускает отложенное
  исправление; спящие агенты просыпаются.
- `task cancel` (для `ACTIVE` и `BLOCKED`) снимает задачу с работы (неверное или пустое задание). Агенты переходят к следующей задаче или ждут;
  спящий `wait` просыпается со статусом `UPDATED`. Папка задачи не удаляется (иначе номера задач переиспользовались бы и
  курсоры событий у агентов разошлись бы).
- Статусы агентов: `ONLINE`, `WORKING`, `WAITING` (сейчас в `wait`), `OFFLINE` (процесс завершился штатно).

## Runner: агенты работают без остановки

**Ожидание без модели (парковка).** Сессия runner'а, которой нечего делать, кроме как ждать других агентов, сначала
ждёт в `wait()` с самым длинным таймаутом (5 мин): такой ход читается из кэша промпта и стоит копейки. Если ждать
приходится дольше — после двух таймаутов подряд — сервер отвечает ей `done`, она завершается, а runner ждёт без модели
и запускает свежую сессию, как только для агента появилось дело: фаза, раунд, сообщение ему, новое соглашение, чья-то
сданная часть, замечания к диффу (и не позже чем через 15 мин, для проверки). Блокировка, разблокировка и чужие сборки
запаркованных агентов не будят. Перезапуск сессии заново пишет кэш и тратит пару ходов, поэтому короткое ожидание
дешевле переждать, а долгое — запарковать. Не паркуется сессия с непрочитанными сообщениями, своим вопросом оператору
или открытым запросом файлов. В логе runner'а: «parked in IMPLEMENT, waiting without a model».

**Экономия контекста.**
- `maxContextTokens` (в примере 80000): сессия, чей контекст перерос порог, завершается после текущего вызова
  инструмента, и свежая продолжает с подзадач и git — как после лимита ходов. Если сессия упёрлась в порог, ничего
  не сделав (ни подзадачи, ни изменений в git), это неудачная попытка: пауза и счёт `maxRestarts`, а не бесконечные
  свежие сессии. Остановленная так сессия не успевает получить от CLI итог со стоимостью: runner сам складывает
  прочитанные ею токены (выход — 0: в событиях сообщений его счётчик неполный) и помечает запись `usagePartial`.
  Статистика при чтении оценивает её по ставке той же модели в сессиях сети, которые стоимость получили (в ставку
  уже входит их выход), — с пометкой «оценка»; так цену получает и первая остановленная сессия задачи.
- `plan({read: true})` отдаёт страницу плана целиком, только если она до 24k символов. Большую страницу lead получает
  как список заголовков и читает по частям (`around`), чтобы она не оставалась в контексте до конца сессии.
- `disabledSkills` (у агента или в `defaults`): скиллы, которые агенту нельзя загружать; `disabledSkillsByTask` — то
  же только в задачах одного типа (`propose` / `code`). Подробнее — в
  [Скиллы агентов](#скиллы-агентов-включить-и-выключить).
- `withoutTools` (в примере у reviewer — `["Agent"]`, у tester — `["Agent", "Skill"]`): встроенные инструменты, которыми
  роль не пользуется, убираются из команды; описание каждого инструмента перечитывается на каждом ходе. `Skill` у reviewer
  оставлен: ревью OpenSpec change идёт скиллом `java-spec-review`.
- Под runner'ом MCP-сервер не отдаёт общие инструкции (их заменяют системный промпт runner'а и подсказки) и
  `create_task`; одинаковая подсказка `hint` повторно приходит как «(unchanged)».

Внутри задачи агентом движет `nextAction`. Но на `done` сессия кончается, и следующую задачу агент сам не возьмёт.
Ждать её внутри той же сессии дорого: каждый `wait()` — это ход модели с перечитыванием контекста, а контекст растёт
от задачи к задаче. `run` — супервизор без LLM, по одному на агента:

**Выжимка папки в промпте.** В начале каждой сессии runner сам дописывает в конец промпта состояние папки агента: ветку,
последние 5 коммитов и незакоммиченные файлы (до 25, остальное числом). Новой сессии не нужно тратить первые ходы и
контекст на `git log` и `git status`; после лимита ходов она сразу видит, где остановилась предыдущая. Если файлов
незакоммичено 8 и больше, промпт после лимита ходов велит сначала закоммитить то, что уже работает.

```
ждёт (без модели) ─▶ есть задача для агента ─▶ запускает сессию CLI ─▶ сессия кончилась
      ▲                                                                  │
      ├──── задача COMPLETED / CANCELLED ◀───────────────────────────────┤
      └──── задача ещё ACTIVE: перезапуск с пометкой «продолжи» (≤ --max-restarts), потом ждёт, пока задача изменится
```

```bash
node dist/index.js run --agent backend --network-dir /abs/project/.agent-network --cwd /abs/project-backend -- \
  claude -p "{prompt}" --output-format stream-json --verbose --model sonnet --mcp-config examples/runner/mcp.json --strict-mcp-config \
    --permission-mode acceptEdits --allowedTools mcp__agent-network Read Write Edit "Bash(./mvnw:*)" \
    "Bash(git status:*)" "Bash(git diff:*)" "Bash(git log:*)" "Bash(git show:*)" "Bash(git add:*)" "Bash(git commit:*)" "Bash(git merge:*)" "Bash(git rev-parse:*)"
```

- **Каждая задача — свежая сессия.** Задача та же, что считает текущей сервер: самая старая `ACTIVE`/`BLOCKED` с этим
  агентом. Промпт (`{prompt}`, по умолчанию — «ты агент X, задача Y, вызови `swarm_context`, иди по `nextAction` до `done`»)
  подставляется вместо `{prompt}` в любом аргументе или добавляется последним. Свой шаблон — `--prompt-file` с
  `{agent}`, `{taskId}`, `{title}`, `{attempt}`, `{resume}`; инструкции агента поверх стандартного промпта —
  `--instructions-file`. Оба файла читаются перед каждой сессией. Модель: `{model}` в команде (`-m "{model}"`,
  `--model "{model}"`) и `--model <имя>`.
- **Сессии передаются** `AGENT_ID`, `NETWORK_DIR`, `AGENT_NETWORK_TASK_ID`, `AGENT_NETWORK_ATTEMPT` (и `AGENT_NETWORK_FRESH_PHASES` при `--fresh-phases`). Claude Code подставляет
  `${AGENT_ID}` и `${NETWORK_DIR}` в MCP-конфиг, поэтому один [examples/runner/mcp.json](examples/runner/mcp.json) годится
  всем агентам.
- **Перезапуск.** Сессия вышла, а задача ещё `ACTIVE` (упала, кончились `--max-turns`, модель остановилась раньше):
  новая сессия через `--restart-delay-ms` × номер попытки с пометкой «это сессия N, вызови `swarm_context`, не переделывай
  сделанное». После `--max-restarts` (по умолчанию 3) runner сдаётся, пока задача не изменится (фаза, статус, новое
  сообщение агенту), — лимит не сгорит на модели, которая не может продвинуться. Под страницей (`ui`) задача при этом
  встаёт в **BLOCKED** с причиной «<агент>'s runner gave up»: иначе остальные агенты ждали бы его вечно. На карточке —
  «Попробовать снова» (runner начнёт с новой сессии; раунды исправлений не тратятся) или «Отменить»; надзор может
  вернуть задачу в работу сам, если убрал механическую причину.
- **Короткие сессии: `--max-turns 70`** (у Qwen `--max-session-turns 70`; так в примерах). Каждый ход перечитывает весь
  контекст сессии, а он растёт на 1–2 тыс. токенов за ход, поэтому сессия из 200 ходов стоит в несколько раз дороже трёх по
  70. Runner читает лимит из команды. Сессия упёрлась в него (у Claude — `error_max_turns`) и за это время что-то сделала
  (отметила подзадачу, отправила сообщение, сдала отчёт) — это плановый конец, а не сбой: новая сессия стартует сразу, не
  считается попыткой для `--max-restarts`, а её промпт говорит «предыдущая упёрлась в лимит: посмотри `swarm_context`,
  `git status` и `git diff` и продолжай». Во вкладке «Запуски» такая сессия — «лимит ходов». Если за все ходы ничего не
  сделано, это обычная неудачная попытка.
- **Свежий ревьюер: `--fresh-phases SYNC`** (в `runners.json` — `"freshPhases": ["SYNC"]`; по умолчанию выключено).
  Идея — «золотая рыбка» из модели Elephant-Goldfish ([статья](https://drensin.medium.com/elephants-goldfish-and-the-new-golden-age-of-software-engineering-c33641a48874)):
  ревьюит тот, кто не участвовал в обсуждении. Без опции ревьюер в SYNC — та же сессия, что спорила в DISCUSS и писала
  свою часть: он помнит, «что имелось в виду», и пропускает то, чего в коде нет. С опцией сессия, видевшая задачу в более
  ранней фазе, при входе задачи в SYNC получает `nextAction: "done"` с `handoff: {phase: "SYNC"}` и заканчивается
  (Stop-хук её не держит). Runner сразу, без паузы, запускает новую сессию с пометкой «ты свежая сессия для SYNC». Она
  видит только задачу, соглашение (`summary`, `decisions`, `interfaces`) и код. Такая передача не считается попыткой для
  `--max-restarts`. После раунда исправлений повторное ревью тоже уходит свежей сессии, а `fixedFindings` подсказывает
  ей, что проверять. Цена — одна лишняя сессия (≈ 7k базовых токенов при [короткой базе](#экономия-токенов-короткая-база-и-компактный-swarm_context))
  на агента и раунд SYNC. Допустимы `IMPLEMENT`, `SYNC`, `INTEGRATE`; проверялось на `SYNC`. Независимо от опции, в SYNC
  `teamImplementations` не показывают `summary` авторов: ревьюер судит по коду и коммитам, а не по пересказу.
- **`BLOCKED` под runner'ом.** Сессия, запущенная runner'ом (`AGENT_NETWORK_RUNNER=1`), на заблокированной задаче получает
  `nextAction: "done"` и заканчивается, а не крутит `wait()` до решения оператора; попыткой это не считается. В
  интерактивной сессии агент по-прежнему ждёт.
- **Свежая копия в SYNC.** Сервер проверяет в папке ревьюера, есть ли в его ветке коммиты из `implementation.commits`
  автора (`git merge-base --is-ancestor`). Чего нет — в `teamImplementations[].notInYourBranch`, и подсказка говорит
  «сначала `git merge <hash>`». Иначе ревьюер читает и тестирует старую копию (например, слитую в прошлом раунде) и
  повторяет уже исправленные находки — так прогон на Haiku упёрся в лимит раундов.
- **Не запускает сессию**, пока задача `BLOCKED` (ждёт `task unblock`) и пока id агента держит живой процесс (например,
  интерактивная сессия с тем же `AGENT_ID` или не успевший выйти MCP-сервер прошлой сессии).
- Ctrl+C: SIGTERM сессии, через 10 с SIGKILL; второй Ctrl+C — выход сразу. `--once`: одна задача и выход (для CI).
- `-p` у `claude` неинтерактивный: разрешения не спросить, поэтому нужен явный `--allowedTools` (и `acceptEdits` для
  правок). `--allowedTools` принимает несколько значений: ставьте `"{prompt}"` сразу после `-p`, иначе флаг заберёт
  промпт себе. `bypassPermissions` — только в изолированном worktree или контейнере.
- **git — только нужные команды.** `"Bash(git:*)"` разрешил бы агенту `push`, `reset --hard`, `branch -D`, `config`.
  Протоколу хватает `status`, `diff`, `log`, `show`, `add`, `commit`, `merge` (follow-up и интеграция), `rev-parse`;
  остальное в `-p` отклоняется (проверено: `reset --hard`, `branch -D`, `push` получают отказ). Префикс точный:
  `git -C <dir> commit` под `git commit:*` не попадает.
- **Скиллы: `Skill` в `--tools`.** `--tools` задаёт, какие встроенные инструменты вообще есть в сессии; без `Skill`
  модель видит названия скиллов, но загрузить их нечем. В `--allowedTools` его писать не нужно: подтверждения он не
  требует, а скиллы подхватываются сами из `.claude/skills` папки агента и `~/.claude/skills`.
- С [хуками](#хуки-сообщения-доходят-до-занятого-агента) сессия узнаёт о сообщениях во время работы, а Stop-хук не даёт ей
  выйти посреди задачи; runner — страховка, если она всё же вышла.
- Codex: `-- codex exec "{prompt}"` *(не проверялось; его MCP-конфиг должен брать `AGENT_ID` из окружения или быть своим
  на агента)*.

Два агента в двух worktree с общей сетью — [examples/runner/run-claude.sh](examples/runner/run-claude.sh).

#### Экономия токенов: короткая база и компактный `swarm_context`

Модель на каждом ходу заново читает системный промпт CLI и описания всех его инструментов: у Claude Code это ~31 тыс.
токенов, у Qwen Code ~17 тыс. Сессия агента — это 10–20 ходов, поэтому база, а не ответы роя, решает расход. Примеры
runner'а запускают агентов с короткой базой:

- **свой системный промпт** — [swarm-system-prompt.md](examples/runner/swarm-system-prompt.md) (протокол, работа с кодом,
  границы: только папка проекта, коммиты только в свою ветку, без секретов). Runner подставляет его вместо
  `{systemPrompt}` (`--system-prompt "{systemPrompt}"`, поле `systemPromptFile` / флаг `--system-prompt-file`), файл
  перечитывается перед каждой сессией;
- **только нужные инструменты**: Claude — `--tools Read,Write,Edit,Glob,Grep,Bash` (плюс `Skill`, если агенты грузят скиллы: каждый ход читает их список); Qwen — `--exclude-tools web_fetch agent
  list_agents get_goal update_goal manage_memory search_memory notebook_edit` (плюс `skill`, если скиллы агентам не нужны).

Замер одного хода: Claude ~31 тыс. → ~7 тыс. токенов, Qwen ~17 тыс. → ~7.6 тыс. На настоящем Haiku (задача «два файла, ревьюер
только проверяет») — 1.18 млн токенов / $0.32 / 1 мин 7 с до и 385 тыс. / $0.137 / 53 с после.

Ответ `swarm_context` компактный: только поля текущей фазы (договорённость целиком в DISCUSS, кратко дальше; права на
файлы — в IMPLEMENT; работа коллег — в SYNC и INTEGRATE), без пустых полей, описание задачи — один раз за сессию,
`exampleCall` — только для `propose` и `respond`. Это вдвое короче прежнего (например, INTEGRATE: ~710 → ~280 токенов).
`swarm_context({full: true})` отдаёт всё — например, после перезапуска.

**Ответы остальных инструментов не повторяют уже показанное.** Всё, что вернул инструмент, остаётся в контексте и
перечитывается на каждом следующем ходу. Поэтому `wait`, `send_message`, `propose`, `complete` и `create_task` вместо
крупных частей, которые агент уже видел в этой фазе и которые не изменились (`openspec`, `agreement`, `assignment`,
`ownership`, `subtasks`, `teamImplementations`, `fixedFindings`, `fixRequests`, `followUps`), пишут `"(unchanged)"` и
одну строку `unchanged` с пояснением. Сообщения, `nextAction` и подсказка приходят всегда. Новая фаза или раунд
показывает всё заново, явный `swarm_context` — всегда всё для фазы. `subtasks` возвращает только открытые пункты.
Замер на change из 39 задач: ответ `send_message` в DISCUSS — ~7.1 → ~2.1 тыс. символов, в IMPLEMENT — ~8.8 → ~1.4 тыс.

**Ответы инструментов — JSON в одну строку.** Без отступов: на 780 настоящих ответах из прогонов это −19–21% токенов
ответов (а ответы — около трети контекста lead'а). Формат TOON на тех же ответах дал лишь ещё −2%: наши ответы — вложенные
объекты с длинными строками, а не таблицы, — и его не взяли.

**Неизменное — один раз за сессию.** Название, агенты, lead, команда проверки и описание задачи ответы инструментов
(кроме `swarm_context`) присылают только в первый раз за сессию: дальше в `task` лишь то, что меняется (фаза, статус,
раунд, причина блокировки). Итог `build` пишет пути относительно папки агента. На свежих прогонах это ещё −15% токенов
ответов сверх JSON в одну строку.

**Сборка и тесты — через инструмент `build`.** В прогоне `add-multi-currency` (lead на Sonnet, 2 сессии по ~200 ходов)
треть–половина контекста lead'а была выводом Maven и git, и он перечитывался на каждом следующем ходу. Поэтому у агентов
есть инструмент роя `build({command?, timeoutMin?})`:

- запускает сборку или тесты в папке агента и отвечает **коротко**: итог (`PASS` / `FAIL (exit 1)` / `TIMEOUT`), время,
  число тестов и упавших, упавшие тесты с первыми строками причины, ошибки компиляции, `BUILD FAILURE` — не больше
  60 строк. Maven и Gradle читаются по своим меткам, остальное (npm, vitest, jest, make) — по строкам с ошибками и хвосту;
- **полный лог** — в `<папка агента>/.agent-network/builds/build-NNN.log` (последние 5), путь есть в ответе: агент
  грепает его или читает кусок, когда нужно больше;
- без команды запускает `verifyCommand` задачи; хвост вроде `2>&1 | tail -60` в команде отбрасывается (вывод и так
  короткий);
- запускает **только сборщики** (`./mvnw`, `mvn`, `./gradlew`, `gradle`, `npm`, `npx`, `yarn`, `pnpm`, `make`; свои —
  через `AGENT_NETWORK_BUILD_TOOLS=bazel,just` в окружении MCP-сервера) и **без shell**: `&&`, `;`, `|`, `>`, `$VAR`
  дают отказ. Это **не граница безопасности**: `npx` скачивает и запускает любой пакет, `npm run`/`make` выполняют то,
  что записано в package.json/Makefile, а любой прогон тестов выполняет код, который написал агент. Разрешения на shell
  (`Bash(./mvnw:*)` / `run_shell_command(./mvnw)`) ограничивают команды, а не то, что они делают; изолировать агентов —
  задача песочницы или контейнера;
- таймаут по умолчанию 20 мин: процесс сборки получает SIGTERM вместе со своими детьми (форкнутая JVM surefire), через
  5 с — SIGKILL. Если сессию агента остановили, сборка тоже останавливается. Qwen по умолчанию прерывает вызов MCP через
  10 мин, поэтому в примере у сервера роя `"timeout": 1800000` (30 мин);
- на странице в карточке агента — последняя сборка: «сборка ✓ 180 тестов · 2 мин 13 с» или «✗ 2/180 упало».

Промпты ролей ([instructions/](examples/runner/instructions)) и системный промпт велят собирать через `build`, тесты
во время работы — узко (`-Dtest=<Class>`), полную сборку — один раз перед `complete`, при падении читать отчёт теста в
`target/surefire-reports/` или грепать лог. Для `verifyCommand` задачи берите тихий вариант: `./mvnw -q -B verify`.

#### Статистика задач: время и токены

- **Время** — из `phaseHistory` задачи (сервер отмечает вход в каждую фазу): всего и по фазам (повторные IMPLEMENT/SYNC
  после исправлений суммируются). Есть только у задач, созданных этой версией; у старых — «нет данных».
- **Токены и стоимость** — из итога каждой сессии, которую запустил runner: CLI должен печатать JSON-события
  (`claude -p … --output-format stream-json --verbose`, `qwen … -o stream-json`; `json` тоже подходит). Runner превращает
  поток в читаемый лог (текст агента, `→ tool(args)`, `[result] …`) и сохраняет сессию в
  `tasks/<id>/sessions/session-NNN.json`: агент, попытка, начало/конец, код выхода, токены (вход с кэшем, выход, из кэша),
  стоимость (у Claude), число ходов, модель. С обычным текстовым выводом время сессий есть, токенов нет.
- Claude считает кэш отдельно от `input_tokens`, Qwen — внутри; в статистике «вход» — всё, что прочитала модель, «всего» —
  вход + выход. У Qwen туда входят и фоновые вызовы (агент памяти).
- Сессия, которая сама перешла на follow-up задачу, учитывается в задаче, ради которой её запустили; у follow-up так и
  написано: «токены учтены в task-001».
- Где смотреть: строка статистики и таблица по агентам (с моделями сессий) в карточке задачи на странице, `task stats [--id task-001]` в CLI.
- Стоимость: у Claude её сообщает CLI, у Qwen и локальных моделей она считается по вашим ценам — поле `"prices"` в
  `runners.json`, см. [Цена токенов](#цена-токенов-если-cli-не-сообщает-стоимость).
- `--json-file` у Qwen (dual output) в неинтерактивном режиме 0.24.7 ничего не пишет, поэтому runner читает `stdout`.

#### Лимит стоимости задачи

`maxCostUsd` задачи — сколько могут стоить все её сессии вместе (агенты и надзор). Когда runner записал сессию и сумма
дошла до лимита, страница переводит задачу в **BLOCKED** с причиной «cost limit $10 reached ($10.42 spent)». Агенты
заканчивают сессии, как на любой BLOCKED-задаче, и runner'ы ждут без модели.

- **Где задаётся:**
  - в форме новой задачи — поле «Лимит стоимости, $» (пусто — без лимита);
  - `task create --max-cost 10`;
  - `"maxCostUsd"` у расписания;
  - `"maxTaskCostUsd": 10` в `runners.json` — значение по умолчанию для задач со страницы и из расписаний (в примерах
    стоит 10).

  Follow-up задачи получают тот же лимит, у каждой свой счёт.
- **Что входит в сумму:** кроме сессий самой задачи — поручения её lead'а (`delegate`, это отдельные задачи) и запуски
  критика плана. На карточке это видно: «стоимость $0.80 — в т.ч. поручения $0.30, критик плана $0.10». Когда поручение
  доводит сумму до лимита, в BLOCKED встают и задача lead'а, и само поручение. Критик проверяется со следующей сессией
  агента.
- **Решаете вы:** в карточке задачи кнопки «+$2 / +$5 / +$10» поднимают лимит, и агенты продолжают с того места, где
  остановились (раунды исправлений не трогаются); или «Отменить задачу». CLI: `task unblock --id task-001 --usd 5`.
  **Надзор** такую блокировку не снимает (маршрут отвечает ему 403): он отдаёт её вам через «нужно решение» с
  рекомендацией.
- **Стоимость** — от CLI (Claude сообщает её сам) или по `prices` из `runners.json` (Qwen). Сессии модели без цены не
  считаются, в журнал страницы пишется об этом. Для бесплатной локальной модели с ценой 0 лимит не сработает.
- **Перерасход:** стоимость известна только в конце сессии, поэтому лимит могут превысить сессии, идущие в этот момент
  (по одной на агента). Новая сессия после этого не начнётся. Сессии короче при меньшем `--max-turns`.
- В карточке задачи стоимость показана как «$3.20 из $10» с полоской: жёлтая от 80%, красная на лимите.

#### Qwen Code

Пример — [examples/runner/run-qwen.sh](examples/runner/run-qwen.sh) с [qwen-mcp.json](examples/runner/qwen-mcp.json) и
промптом [qwen-prompt.md](examples/runner/qwen-prompt.md):

```bash
node dist/index.js run --agent backend --network-dir /abs/project/.agent-network --cwd /abs/project-backend \
  --prompt-file examples/runner/qwen-prompt.md -- \
  qwen "{prompt}" -o stream-json -m qwen/qwen3.5-9b --mcp-config examples/runner/qwen-mcp.json --approval-mode auto-edit \
    --allowed-tools mcp__agent-network "run_shell_command(./mvnw)" \
    "run_shell_command(git status)" "run_shell_command(git diff)" "run_shell_command(git log)" "run_shell_command(git show)" "run_shell_command(git add)" "run_shell_command(git commit)" "run_shell_command(git merge)" "run_shell_command(git rev-parse)" \
    --max-session-turns 300 --max-wall-time 1h
```

Проверено на Qwen Code 0.24.7 (runner → `qwen` → поддельная OpenAI-совместимая модель, которая вызывает инструменты):

- **Идентичность.** `${AGENT_ID}` в `--mcp-config` qwen **не** подставляет (сервер падает с `Invalid AGENT_ID: "${AGENT_ID}"`), но
  передаёт MCP-серверу своё окружение. Поэтому в `qwen-mcp.json` нет `AGENT_ID`/`NETWORK_DIR` — их задаёт runner.
- **Глобальный конфиг.** Сервер из `--mcp-config` заменяет одноимённый `agent-network` из `~/.qwen/settings.json` (например, с
  пулом `backend,reviewer`), так что сессия получает id от runner'а, а не из пула.
- **Права без интерактива.** В `default` инструменты agent-network отклоняются («non-interactive mode cannot prompt»), а
  `write_file` в сессии нет вовсе. `auto-edit` разрешает правки файлов; `--allowed-tools mcp__agent-network` (или
  `"trust": true` у сервера) — инструменты роя; `run_shell_command(git commit)` — только команды с этим префиксом (с
  узким списком из примеров `git reset --hard`, `git branch -D`, `git push` отклоняются). Только читающие команды (`ls`)
  qwen пропускает и так, остальные (`touch`) без разрешения отклоняет. `--approval-mode yolo` разрешает всё — только в
  песочнице.
- **Скиллы.** Инструмент `skill` грузит скиллы из `.qwen/skills/` папки агента (не из `.claude/skills/`) и разрешения не
  требует; если он в `--exclude-tools`, скиллы недоступны.
- **Отложенные инструменты.** MCP-инструменты в qwen скрыты за `tool_search`/`tool_call` (полное имя
  `mcp__agent-network__swarm_context`). `qwen-prompt.md` говорит модели, как их найти: маленькой модели это экономит ходы.
- `--allowed-tools` принимает несколько значений: промпт ставьте первым, сразу после `qwen`.
- `--max-wall-time` и `--max-session-turns` ограничивают сессию (по `--max-wall-time` qwen выходит с кодом 55); runner
  перезапустит её, если задача не закончена. Хуки agent-network для qwen не портированы: сообщения он видит через
  `wait()` и `swarm_context`.

node dist/index.js ui --runners runners.json [--runners other.json ...] [--port 4777]   # → http://127.0.0.1:4777

Страница обновляется раз в 2 с. Слева — меню разделов, сверху — строка статуса (runner'ы, сколько задач идёт и ждёт в
очереди, открытые вопросы, расход за 24 ч), над разделом — вопросы агентов, пока на них нет ответа.

| Раздел | Что там |
|---|---|
| **Входящие** | Всё, что ждёт вашего решения, по всем проектам: вопросы, страницы на просмотр, BLOCKED, вливания без проверки, задачи на приёмку, решения надзора, предложения наблюдателя; «Открыть» ведёт к месту. Уведомления браузера и Linux — [Входящие и уведомления](#входящие-и-уведомления) |
| **Обзор** | «Прогресс задач» — каждая открытая задача одной строкой: фаза, полоса и процент (сданные агентами задачи OpenSpec, без OpenSpec — подзадачи), у `BLOCKED` — раунд исправлений; клик ведёт к карточке. Показатели: идёт (задачи, которыми занят хотя бы один агент), очередь (задачи, чьи агенты заняты другими), расход и сделано за 24 ч / 7 д / 30 д. Runner'ы: модель, что делает сейчас (задача, фаза, подзадачи, скилл, который агент загрузил последним), расход. Задачи по фазам с самой старой. Последние события |
| **Задачи** | Кнопка «+ Новая задача» (форма), блок «По расписанию» ([cron-задачи](#задачи-по-расписанию-cron)) и карточки задач. Прогресс: шкала фаз, где ширина — время в фазе (раунды исправлений суммируются), текущая подсвечена, у `BLOCKED` — красная; итоги «Задачи OpenSpec — сданы агентами» и «Подзадачи агентов» (последняя галочка); по агенту — полоса подзадач, что делает (▶ подзадача, «ждёт X (dependsOn)», «сдал работу», ревью раунда), его последний вызов и строка «скиллы: …» — какие скиллы он загрузил в этой задаче (вызов `Skill` или чтение `SKILL.md`, в том числе его субагентами; ▶ — последний в идущей сессии; завершённые сессии хранят их в `skills`). Ниже: фаза, «ждём:», agreement и одобрения, подзадачи, implementation, sync-отчёты, интеграция, OpenSpec, статистика, сообщения, события; у `BLOCKED`-задачи — срок, после которого исправление берёт lead, и кнопки «+1/+2/+3» (раунды исправлений), «Отдать lead'у сейчас», «Отменить задачу»; у DONE-задачи — [пакет приёмки](#приёмка-пакет-вместо-диффа) и [проверка вливания](#вливание-с-проверкой); у закрытой — [«Удалить задачу»](#удаление-задачи) |
| **Запуски** | Строка — одна сессия CLI, номер С-N сквозной по проекту в порядке завершения сессий: статус (идёт, ок, ошибка с кодом выхода, остановлена), агент, модель, задача, начало, длительность, токены, стоимость (≈ — по вашим ценам). Клик раскрывает подробности: задачи сессии (и те, что она закончила по пути, например follow-up), номер попытки, ходы, токены по видам (вход, из кэша, выход), как она завершилась, откуда стоимость, файл записи. Фильтры по агенту, задаче, модели, статусу и итог по фильтру |
| **Активность** | Лента того, что делают агенты, новые сверху: `session`, `thinking`, `text`, `tool_use` (инструмент и суть вызова: команда, файл, аргументы), `tool_result` (✓/✗, время выполнения, первая строка ответа; отказ в правах — красным), `result` (ходы, токены, стоимость), строки runner'а и stderr. Клик раскрывает полный вызов или ответ. Фильтры по виду, агенту, задаче и поиск; «следить» держит ленту на новых событиях, без него новые копятся в плашке «показать». В карточке runner'а — последние 12 событий агента и ссылка на его ленту. Ведут ленту runner'ы (stream-json Claude и Qwen), в памяти UI до 1500 событий на агента |
| **Надзор** | [Агент-помощник оператора](#надзор-агент-который-снимает-проблемы-роя): включить/выключить, состояние (следит, работает, ждёт лимита), модель следующей сессии, сессии за час, расход за 24 ч и бюджет, пороги правил, инструменты с переключателями, «нужно ваше решение» с рекомендацией и кнопкой «Решено», журнал (`incident`, `action`, `note`, `needs-you`, `session`) и лог |
| **Runner'ы** | Карточки runner'ов (старт/стоп, модель, инструкции, лог, что делает сейчас, расход за 24 ч), таблица «Скиллы агентов» (какой агент какие скиллы может загружать; см. [Скиллы агентов](#скиллы-агентов-включить-и-выключить)) и агенты в сети: статус, активность, pid; `DEAD` — процесс пропал, хотя статус не `OFFLINE` |
| **Проекты** | Все проекты страницы: ветка и HEAD, задачи (идёт / в очереди / готово), runner'ы, OpenSpec change'и, открытые вопросы, расход за 24 ч, последняя активность. Строка переключает страницу на проект |
| **События** | Лента событий задач проекта (последние 50 на задачу) с фильтрами по задаче и типу |

**Несколько проектов.** Каждый `--runners` — отдельный проект со своей сетью: она берётся из `"networkDir"` конфига, а без
него — из git-репозитория папки (`cwd`) первого агента (worktree попадают в сеть своего репозитория). Адрес раздела —
`#/<раздел>/<проект>`, его можно сохранить в закладки. Без `--runners` страница показывает одну сеть только для чтения:
задачи из терминала (`task create`), вопросы видны, но ответить можно только с `--runners`.

Страница слушает только `127.0.0.1`, чужие `Host` отклоняются. UI смотрит ровно в тот каталог, который вы указали: если
агенты работают в другом `NETWORK_DIR`, страница будет пустой.

### UI с runner'ами: задачи и агенты из браузера

```bash
node dist/index.js ui --runners runners.json [--port 4777]
```

Одна команда поднимает страницу и runner'ы агентов из конфига (с `"autostart": false` — по кнопке). На странице появляются:

- в разделе «Задачи» форма **«Новая задача»** (кнопка «+ Новая задача»): название, описание, lead и остальные агенты, `--verify` (заполнен `"verifyCommand"` из `runners.json`; пусто — без проверки сборки), бюджет follow-up задач, лимит раундов
  исправлений; runner'ы подхватывают задачу за пару секунд;
- в разделе «Runner'ы» — **runner'ы**: статус `RUNNING`/`STOPPED`, что делает сейчас, кнопки «Старт»/«Стоп», папка, команда, **модель агента** (список и
  «Применить»), **файл инструкций агента** (поле ввода, «Сохранить», начало текста) и хвост лога (строки runner'а и вывод сессий CLI, последние 400 строк);
- в карточке задачи — **подзадачи** каждого агента (`2/3`, ✓ ▶ · ✕) и **цепочка follow-up**: «follow-up от task-001»,
  «follow-up задачи: …», бюджет; у открытой задачи рядом с lead'ом — ✉ «написать lead'у»: сообщение от оператора придёт
  ему, даже если он сейчас занят (через хук), а ждущего разбудит; остальным он передаст сам.

Готовые примеры для проекта в git (три агента, у каждого свой worktree, без путей — проект берётся из папки запуска):
[runners.qwen.example.json](examples/runner/runners.qwen.example.json) и
[runners.claude.example.json](examples/runner/runners.claude.example.json); как запускать — ниже.

#### Запуск в своём проекте одной командой

Примеры `runners.claude.example.json` и `runners.qwen.example.json` не нужно править: запустите
`ui` из папки проекта — git-репозитория хотя бы с одним коммитом.

```bash
cd ~/myprojects/test
agent-network-mcp ui                      # свой конфиг проекта из шаблона Qwen (в первый раз), дальше — он
agent-network-mcp ui --template claude    # то же с шаблоном Claude Code
agent-network-mcp ui --runners ~/Downloads/files/agent-network-mcp/examples/runner/runners.claude.example.json   # пример как есть
```

Без `--runners` конфиг проекта — `.agent-network/runners.json`: копия шаблона, где ссылки на промпты и инструкции
указывают в пакет (`{agentNetworkMcp}/examples/runner/…`). Правки страницы идут в неё. С `--runners` на пример из
репозитория страница пишет свои правки в сам пример.

Без `npm link` (см. [Быстрый старт](#быстрый-старт)) — `node ~/Downloads/files/agent-network-mcp/dist/index.js ui --runners …`.

- **Проект** — git-репозиторий, из которого запущен `ui`; сеть — `<проект>/.agent-network`. Она добавляется в
  `.git/info/exclude`, коммитить `.gitignore` не нужно.
- **Worktree агентов создаются сами** (`"worktree": true` в `defaults`): `~/myprojects/test-backend`, `-reviewer`,
  `-tester` на ветках `swarm-backend` и т.д., от текущего `HEAD` проекта. Если папка уже есть, она используется как есть;
  если ветка уже есть, worktree берёт её. Агент со своим `"cwd"` работает там, где указано.
- **`{agentNetworkMcp}`** в конфиге — папка этого репозитория, загрузчик подставляет её сам; MCP-серверы (и у Claude —
  хуки, `--settings`) заданы JSON прямо в команде, `${AGENT_ID}` и `${NETWORK_DIR}` Claude берёт из окружения сессии.
  Поэтому пример работает и с места, и копией в любой папке.
- **Своё — в копии:** модели (`model`, `models`), сборка в разрешениях shell и `verifyCommand` (копия уже подогнана под
  стек проекта, см. [Быстрый старт](#быстрый-старт)), `maxTaskCostUsd`, у Qwen — адрес сервера моделей. Пути в копии не нужны.
- **Сабагент `helper`** для Qwen — файл, один раз: `mkdir -p ~/.qwen/agents && cp …/examples/runner/qwen-agents/helper.md ~/.qwen/agents/`.
- **Сервер моделей** в примере — `http://127.0.0.1:1234/v1`; другой адрес — скопируйте пример и поменяйте
  `--openai-base-url` в двух командах (агентов и надзора). Так же меняются модель, сборка (`run_shell_command(./mvnw)` →
  `run_shell_command(npm)`) и прочее под проект.
- **Агенты видят закоммиченное.** Изменения в проекте после старта — закоммитить и влить в их ветки
  (`git -C ../test-backend merge main`) или убрать worktree (ниже): они создадутся заново от свежего `HEAD`.
- **После задачи — влить и убрать** (в карточке DONE-задачи, блок «Ветка lead'а»):
  - **«Посмотреть изменения»** — что принесёт вливание: коммиты ветки lead'а, файлы с +/− и дифф каждого файла
    (раскрывается по клику). После вливания — то, что влилось.
  - **Замечания к строкам.** Клик по строке диффа — поле замечания; замечания встают под строками, сверху счётчик.
    Пока задача идёт (блок «Изменения в работе», с выбором ветки любого агента), «Отправить lead'у» уходит ему одним
    сообщением с файлом, строкой и кодом строки — lead правит или раздаёт агентам. После DONE та же кнопка
    «Создать задачу по замечаниям» ставит рою follow-up задачу с этим списком.
  - **«Влить в проект»** кладёт ветку lead'а (`swarm-backend`) в текущую ветку проекта **одним коммитом**
    «task-001: <название>» (squash; в теле — список коммитов агентов), без push. История проекта читается по задачам, а
    откат задачи — откат одного коммита. Сначала `git merge-tree`: при конфликте называет файлы и ничего не меняет. Отказ
    и при незакоммиченных изменениях в проекте или detached HEAD. Уже влитая ветка (её изменения уже в HEAD) — «уже была
    в main». Lead со своим `"cwd"` — вливается ветка, на которой стоит его папка; lead в папке проекта — вливать нечего.
    Нужен коммит слияния с историей агентов — `"mergeStrategy": "merge"` в `runners.json`.
    У задачи с `verifyCommand` вливание сначала **проверяется сборкой** отдельно от проекта —
    [Вливание с проверкой](#вливание-с-проверкой); без `verifyCommand` вливается сразу, с пометкой «без проверки сборки».
  - **«Откатить»** — после вливания: `git revert` этого коммита (новый коммит «Revert task-001: …», история не
    переписывается). При незакоммиченных правках или конфликте с более поздней работой ничего не меняет и говорит об
    этом. Rebase мы не используем: он переносит коммиты агентов по одному, и откатывать пришлось бы диапазон.
  - **«Убрать worktree агентов»** — `git worktree remove` и `git branch -d` для всех авто-worktree проекта, без
    `--force`: папка с незакоммиченными правками и невлитая ветка остаются (ответ говорит, что и почему). Ветку, влитую
    одним коммитом, `-d` не узнаёт (её коммитов в проекте нет), поэтому её удаляет проверка содержимого: если её слияние
    ничего не изменило бы в HEAD, она удаляется. Только когда у
    этих агентов нет открытых задач и идущих сессий.
  - Перед следующей сессией runner сам создаёт недостающий worktree от текущего `HEAD` проекта — то есть уже с влитым
    результатом, на новой ветке `swarm-<id>`.
  - Если worktree остался, а в ветке агента нет коммита, от которого начата задача (проект ушёл вперёд, например
    squash прошлой задачи), runner перед сессией вливает этот коммит в ветку. Если в папке есть незакоммиченные
    правки или слияние даёт конфликт, ничего не меняется, а причина пишется в лог runner'а. Работой агента по задаче
    считаются только его коммиты, сделанные после создания задачи: коммиты прошлой задачи в той же ветке не дают
    ложного `FILE_NOT_OWNED`.
- **Несколько проектов на одной странице:** скопируйте пример на каждый проект и впишите в копию
  `"project": "/Users/me/myprojects/test"` (из одной папки запуска несколько проектов не угадать), затем
  `ui --runners a.json --runners b.json`.

`runners.json` (относительные пути — от папки конфига; любое поле агента можно вынести в `defaults`; поля `_comment`
игнорируются):

```json
{
  "networkDir": "/abs/project/.agent-network",
  "defaults": {
    "command": ["qwen", "{prompt}", "-m", "{model}", "--mcp-config", "/abs/agent-network-mcp/examples/runner/qwen-mcp.json",
                "--approval-mode", "auto-edit", "--allowed-tools", "mcp__agent-network", "run_shell_command(./mvnw)",
                "run_shell_command(git status)", "run_shell_command(git diff)", "run_shell_command(git log)", "run_shell_command(git show)",
                "run_shell_command(git add)", "run_shell_command(git commit)", "run_shell_command(git merge)", "run_shell_command(git rev-parse)",
                "--max-session-turns", "300", "--max-wall-time", "1h"],
    "model": "qwen/qwen3.5-9b",
    "models": ["qwen/qwen3.5-9b", "qwen/qwen3-coder-30b"],
    "promptFile": "/abs/agent-network-mcp/examples/runner/qwen-prompt.md",
    "maxRestarts": 2
  },
  "agents": [
    { "id": "backend", "cwd": "/abs/project-backend" },
    { "id": "reviewer", "cwd": "/abs/project-reviewer", "model": "qwen/qwen3-coder-30b", "autostart": false }
  ],
  "prices": { "qwen/qwen3.5-9b": { "input": 0.05, "output": 0.25 } },
  "verifyCommand": "./mvnw -q -B verify -Dsurefire.timeout=900"
}
```

`verifyCommand` — команда сборки и тестов для задач со страницы и из расписаний, у которых своей нет: lead сдаёт задачу
с PASS только после её зелёного прогона на слитом результате. Это одна команда сборщика без shell (как у `build`):
`npm test && npm run lint` конфиг не примет — заведите скрипт `check` в `package.json`.

**Вопросы агентов к вам.** Сессия runner'а без собеседника: её чат никто не читает. Поэтому то, что может решить только
человек (неясная задача, требования), агент спрашивает через сеть: `send_message({to: "operator", message})` и `wait()`.
Вопрос появляется вверху страницы в блоке «Вопросы агентов» (число открытых — в заголовке вкладки), вы отвечаете в поле
под ним, и ответ приходит агенту обычным сообщением: его `wait()` просыпается, и он продолжает **в той же сессии**. Пока
вопрос в DISCUSS без ответа, `nextAction` агента — `wait` (не `propose`/`approve`), чтобы он не додумывал задачу; в других
фазах вопрос не останавливает работу, а лишь напоминает, что ответ ещё не пришёл. **Без ответа 10 минут** (переменная
`AGENT_NETWORK_OPERATOR_TIMEOUT_MIN`) агент перестаёт ждать: подсказка велит взять вариант, который он назвал в вопросе
(не назвал — самый безопасный), и сказать об этом остальным агентам и в `result`. Вопрос остаётся открытым на странице, и
поздний ответ всё равно дойдёт до агента. Поэтому в вопросе агент сразу называет, что сделает сам. Тем же путём агент
пишет и о проблемах среды: команда отклонена, процесс завис, сервис или порт недоступен — после двух неудачных попыток
он не повторяет то же самое и не обходит запрет (в прогоне lead пробовал `kill -9` с `dangerouslyDisableSandbox`), а
спрашивает оператора: что застряло, что пробовал, что нужно. Чтобы зависший тест не ждал человека, инструкции велят
запускать тесты с лимитом времени: `-Dsurefire.timeout=300` (Maven убивает тестовую JVM), для полной сборки — 900. Ответить можно только из UI с
`--runners`; без него вопросы видны, но только для чтения. Вопрос, который уже не нужен (агент сделал по своему
предложению, решили иначе), закрывается кнопкой «Закрыть без ответа»: агент ничего не получает.

**К сведению.** Не всё, что агент пишет оператору, — вопрос: ответ на ваше сообщение, «понял», отчёт, который вы
просили. Такое агент шлёт с `send_message({to: "operator", message, fyi: true})`: оно не ждёт ответа, не держит агента в
`wait` и не будит надзор. На странице такие сообщения — в синем блоке «К сведению» под вопросами, с кнопкой «Ок»
(убрать; агенту ничего не уходит), со всплывашкой при появлении; ответы lead'а видны и в истории под «Написать lead'у».
Сообщение оператора lead'у само подсказывает: «ответ не нужен; если отвечаешь — с `fyi: true`». `operator` — зарезервированное имя, агента так назвать нельзя.

То же между агентами: `send_message({to: "reviewer", message, fyi: true})` — заметка, на которую не нужно отвечать
(«понял», «переименовал DTO»). Она **не будит** получателя: его `wait()` не возвращается из-за неё, запаркованный
агент не получает новую сессию; заметка приходит с его следующим ответом сервера (с пометкой `quiet`). Так же тихо
приходит lead'у копия вашего ответа на вопрос другого агента. Всё, на что надо реагировать скоро, шлётся без `fyi`.

**Без лишних ходов.** `propose()` сразу считается одобрением автора: lead после него только ждёт остальных. Агенту
«только ревью» (`files: []`) сервер сам отмечает часть готовой в начале IMPLEMENT — ему не нужен отдельный
`complete()`, он ждёт SYNC.

**Написать команде самому, без вопроса — через lead'а.** В карточке открытой задачи (`ACTIVE` или `BLOCKED`) рядом с
lead'ом — кнопка ✉. Текст уходит **только lead'у** обычным сообщением от `operator` (тип `INFORMATION`) с пометкой в
начале: «вы lead этой задачи — выполните своё и передайте <остальным агентам> через `send_message` то, что им делать».
Lead раздаёт поручения сам: у команды остаётся один план, и оператор не даёт агентам указаний в обход lead'а. Так можно
подсказать, где искать причину, поправить курс («сначала DTO, потом сервис»), попросить reviewer'а ответить. В тексте
называйте агента, которого это касается. Как сообщение доходит до lead'а:

- ждёт в `wait()` — просыпается сразу, сообщение у него в `pendingMessages`;
- Claude Code и занят — получает его после ближайшего вызова любого инструмента, через хук `post-tool` (нужен
  `--settings` с хуками agent-network, как в примере `runners.claude.example.json`);
- Qwen (хуков нет) и занят — видит его в `pendingMessages` при следующем обращении к рою (`swarm_context`, `subtasks`,
  `complete`, `send_message`, `wait`).

**Срочно.** Агент может быть занят своим и не обратить внимания на сообщение: Claude видит его после очередного вызова
инструмента, но может продолжать своё, а Qwen без хуков увидит, только когда обратится к рою. Галочка «Срочно» в окне
сообщения работает для любого CLI. Runner дожидается конца текущего вызова инструмента — не обрывает запись файла или
прогон тестов, но ждёт не дольше 90 с, — останавливает сессию lead'а и сразу запускает новую. Её промпт начинается с
«URGENT FROM THE OPERATOR» и вашего текста. Такая остановка не считается неудачной попыткой. Цена — новая сессия заново
ориентируется (несколько ходов), поэтому срочно — только когда агент должен переключиться сейчас: «стоп, сначала
закоммить», «не трогай X». Если runner lead'а остановлен, сообщение просто ждёт его в `pendingMessages`.

Завершённой или отменённой задаче написать нельзя. Сообщение видно в карточке задачи в «Сообщениях». Ответы на вопросы
агентов (блок «Вопросы агентов») по-прежнему идут прямо спросившему. Тем же путём пишет
[надзор](#надзор-агент-который-снимает-проблемы-роя) (`message_lead`): на вкладке «Надзор» это запись `action`
«message to the lead …». Маршрут — `POST /api/tasks/<id>/message {"text": "...", "urgent": true?}` (получатель всегда lead); из
терминала такой команды нет.

**Модель для каждого агента.** Поставьте `"{model}"` в `command` туда, где CLI ждёт имя модели (`"-m", "{model}"` у
Qwen, `"--model", "{model}"` у Claude Code), `"model"` — модель по умолчанию (в `defaults` или у агента), `"models"` —
список, из которого её выбирают на странице. В карточке runner'а модель выбирается из списка («другая…» — ввести имя) и
применяется со следующей сессии, без перезапуска; значение записывается в `runners.json`. Имя — как его понимает CLI
(у LM Studio — id из `GET /v1/models`), без пробелов и не с `-`. Без `{model}` в команде модель задаёт сама команда, и
выбора на странице нет. Какая модель реально работала, видно в логе (`[session] model …`) и в статистике по агентам.

**Свои инструкции каждому агенту** — `instructionsFile` (у агента или в `defaults`): роль, правила, стиль. Текст
**добавляется** к стандартному промпту после строки «Instructions from the operator for you (<id>)», подстановки
`{agent}`, `{taskId}`, `{title}` работают. Файл читается заново перед каждой сессией: правка применяется со следующей,
без перезапуска. На странице путь задаётся в карточке runner'а: файл должен читаться, относительный путь — от папки
конфига, значение записывается обратно в `runners.json` (остальное, включая `_comment`, сохраняется); пустое поле —
без инструкций. Готовые роли — в [examples/runner/instructions/](examples/runner/instructions/) (Maven; для Gradle —
[gradle/](examples/runner/instructions/gradle), для npm, yarn и pnpm — [npm/](examples/runner/instructions/npm), их
свой конфиг проекта берёт сам по стеку):
[backend.md](examples/runner/instructions/backend.md) (код через TDD; как lead — сборка, галочки в `tasks.md`, доки),
[reviewer.md](examples/runner/instructions/reviewer.md) (только ревью, чеклист SYNC),
[tester.md](examples/runner/instructions/tester.md) (сквозные тесты в своём пакете; тест задачи остаётся у её
исполнителя, полный прогон — у lead'а). `promptFile`, наоборот,
заменяет весь промпт целиком (тоже читается перед каждой сессией): в нём легко потерять «вызови `swarm_context`, иди по
`nextAction` до `done`», поэтому для роли агента берите `instructionsFile`.

`command`, `promptFile`, `maxRestarts`, `freshPhases` — те же, что у [`run`](#runner-агенты-работают-без-остановки); для Claude Code — команда из
`run-claude.sh`. `networkDir` можно задать и флагом `--network-dir` / `NETWORK_DIR` (они важнее). Ctrl+C останавливает
runner'ы (их сессиям — SIGTERM) и страницу.

Без `--runners` страница остаётся только для чтения. С ним изменяющие запросы (`POST /api/tasks`,
`POST /api/runners/<id>/start|stop|instructions|model`, `POST /api/questions/answer`, `POST /api/openspec/archive`,
`POST /api/tasks/<id>/unblock|handover|cancel|message`, `POST /api/supervisor/start|stop|model|tools|note|resolve`) принимаются только как JSON с той же страницы: запрос с чужим `Origin` или
`Sec-Fetch-Site: cross-site` получает 403, обычная HTML-форма — 415. Иначе любой сайт, открытый в том же браузере, мог бы
поставить агентам задачу. Страница по-прежнему слушает только `127.0.0.1`.

### Входящие и уведомления

Всё, что ждёт вашего решения, собрано в разделе **«Входящие»** (первый в меню, со счётчиком; число — и в заголовке
вкладки) по всем проектам страницы:

| Что | Когда уходит |
|---|---|
| вопрос агента (со сроком: когда агент пойдёт по своему варианту; у допроса срока нет) | вы ответили |
| план, спека аналитиков, change на просмотр или приёмку | вы утвердили, посмотрели, приняли |
| BLOCKED-задача (со сроком, когда исправление возьмёт lead) | разблокировали, отдали, отменили |
| вливание не прошло проверку (красное, конфликт, прервано, проект сдвинулся) — и контракта, и сервиса | отдали команде, проверили снова, влили |
| DONE-задача ждёт приёмки | приняли или вернули |
| «нужно ваше решение» надзора | «Решено» |
| новое предложение наблюдателя | приняли или отклонили |

Сверху — то, без чего рой стоит (вопрос, страница, BLOCKED), среди них — со сроком. «Открыть» ведёт прямо к месту:
вопросу, плану, пакету приёмки, карточке задачи, вкладке надзора или наблюдателя.

**Уведомления:**

- **браузера** — кнопка «Включить уведомления браузера» во «Входящих»; приходят, пока страница открыта хоть в фоновой
  вкладке, клик открывает пункт;
- **системные на Linux** — `notify-send` (пакет `libnotify-bin`), их шлёт сервер страницы, так что вкладку можно
  закрыть, лишь бы работал `ui`. На других системах и без `notify-send` этот канал выключен (раздел «Входящие» говорит
  почему).

Об одном пункте — одно уведомление; несколько новых за раз — одно общее. Одно напоминание, если вопрос, страница или
BLOCKED ждут дольше 30 минут, и одно предупреждение за 2 минуты до того, как агент пойдёт по своему варианту без вас.
Что уже сказано, хранится в `.agent-network/attention.json`: после перезапуска страницы старое не придёт снова, а пункт,
который ушёл и вернулся (новый раунд), — новость. Настройки — в `runners.json`:

```json
"notify": { "os": true, "remindAfterMin": 30, "kinds": ["question", "blocked", "plan", "merge", "acceptance", "supervisor", "observer"] }
```

`os: false` — без системных уведомлений, `remindAfterMin: 0` — без напоминаний, `kinds` — о чём уведомлять (во
«Входящих» видно всё).

### Уточнение задачи: коротко или допрос

**Подготовка одним выбором.** В форме задачи — «Подготовка» (CLI: `--depth`):

| | уточнение | допрос | план на утверждение | для чего |
|---|---|---|---|---|
| **быстро** (`fast`) | — | — | — | мелкая понятная задача: сразу к соглашению |
| **стандарт** (`standard`) | да | — | — | по умолчанию: lead задаёт вопросы или пишет, как понял |
| **тщательно** (`thorough`) | да | да | да | большая или рискованная задача; критик плана — если настроен |

Под «настроить вручную» — те же три галочки по отдельности; изменили одну — пресет становится «своя настройка».

В форме задачи — галочки «Сначала уточнить постановку» и «Допрос (grill-me)» (CLI: `--clarify`, `--grill`):

- **коротко** — lead читает задачу и код и либо задаёт вопросы, либо пишет «Как я понял: …». Засчитывается только
  вопрос или такая заметка; отчёт об ошибке — нет.
- **допрос (grill-me)** — по методу скилла `grilling`. Lead строит дерево решений (объём, поведение, граничные случаи,
  данные, что считать готовым, что не трогать) и задаёт вопросы раундами: все, на которые уже можно ответить, каждый
  с вариантами и своей рекомендацией. Факты из кода он выясняет сам. В конце — вопрос «Как я понял: … Всё так?»;
  `propose()` открывается только после вашего «Да», «Нет» с поправкой — следующий раунд. Без ответа lead не идёт
  дальше по своей рекомендации, как в обычной задаче, а ждёт. С «Планом на утверждение» допрос идёт до плана: `plan()` до вашего «Да» не
  принимается, а все решения допроса lead переносит в план блоком «Что решили на допросе». Критик плана получает те же
  решения и считает серьёзным риском решение, которого в плане нет или которому план противоречит.

### План на утверждение

Чтобы увидеть и поправить план до того, как агенты начнут писать код, отметьте в форме задачи «План на
утверждение» (CLI: `task create --plan`). Идея взята из [Lavish](https://github.com/kunchenguid/lavish-axi) (MIT), но
своим кодом и на нашем сервере.

1. **Lead пишет план одной HTML-страницей** в DISCUSS — инструментом `plan({html, note})`. На странице: цель,
   что меняется и где, кто что делает и с какими файлами, контракты, порядок работ, риски, как проверить. Вопросы к вам
   оформляются блоками `data-question` с вариантами: вы отмечаете ответ прямо в плане. Схемы — inline SVG или Mermaid.
2. **На карточке задачи** появляется «План ждёт вас» и кнопка «Открыть и проверить». План открывается на весь экран,
   справа панель:
   - **Замечание** — кликните блок или выделите слова и напишите, что не так;
   - **Править текст** — исправляйте прямо на странице, lead получит «было → стало», а ваш вариант сохранится новой
     версией плана;
   - **схема** (Mermaid): в режиме «Замечание» клик по узлу или стрелке даёт замечание именно к ним («схема: стрелка
     «save Refund»»); в режиме «Править текст» клик по схеме открывает справа её код — правьте, схема перерисуется в
     плане, ошибка в коде видна сразу; lead получит новый код схемы;
   - **подсветить новое** — блоки, изменившиеся с прошлой версии;
   - список версий, история отзывов.
3. **«Отправить lead'у»** — замечания, правки и ответы уходят lead'у одним сообщением. На панели остаётся зелёная
   плашка «✓ Отправлено lead'у … в 15:34: 1 замечание, 1 правка», а кнопка серая, пока вы не добавите что-то новое:
   дважды одно и то же не отправить. Lead смотрит отзыв и решает: дорабатывает план (`plan({edits: [{find,
   replace}]})` или целиком) или, если менять нечего, присылает ту же страницу с пояснением (`plan({note})`). Пока он
   думает, «Утвердить» тоже серая. Новая версия откроется сама, если у вас нет неотправленных замечаний.
4. **«Утвердить план»** — только после этого lead может `propose()` (иначе `PLAN_NOT_APPROVED`); соглашение
   строится по плану. Пока у вас есть неотправленные замечания или правки, кнопка серая: сначала их смотрит lead,
   решает, что менять, и присылает новую версию — её и утверждаете. Вместе с утверждением уходят только ответы на
   вопросы плана.

**Критик плана** (`planCritic` в `runners.json`). Каждую версию плана, которую пишет lead, читает отдельная сессия
только с инструментами чтения: план и код проекта. Она ищет, что сломается в проде, если строить ровно по плану:
существующие данные и миграции, деплой и откат, потребители API, повторы и гонки, нагрузка, безопасность, решения,
которые план оставил открытыми. Риски появляются в панели плана с серьёзностью, местом и предложением; «В замечания»
добавляет риск к вашим замечаниям lead'у. Версии с вашими правками и утверждённый план критик не читает, «Покритиковать
ещё раз» запускает его снова. Одна сессия за раз, на sonnet около $0.05–0.3 за версию. Версию с той же страницей,
что уже прочитана (lead ответил «оставляю как есть»), критик не читает заново: у неё та же критика с пометкой «как у
vN». Если lead пишет новую версию, пока критик читает старую, старая сессия останавливается и критик берёт новую.

Скиллы критику подбираются по проекту — `planCritic.skillSets`:

```json
"skillSets": [
  { "name": "always", "when": ["*"], "skills": ["~/.claude/agents/critic.md"] },
  { "name": "java-spring", "when": ["pom.xml", "build.gradle", "build.gradle.kts"],
    "skills": ["{agentNetworkMcp}/../backend-design-java", "{agentNetworkMcp}/../java-extensibility-review"] },
  { "name": "node", "when": ["package.json"], "skills": ["~/skills/node-review"] }
]
```

Набор применяется, когда в корне проекта есть один из файлов `when` (`*` — любой проект); подходящих наборов может быть
несколько. В `skills` — папка скилла (`SKILL.md`), папка с несколькими скиллами (`backend-design-java`: migration-safety,
idempotency, error handling, …) или один `.md`-файл, например определение агента. Скиллы кладутся в рабочую папку
критика: Claude видит их как свои скиллы, любой другой CLI читает их файлы. Критик открывает только те, чьё описание
подходит к плану; в панели видно, с какими наборами он смотрел.

План хранится в `tasks/<id>/plan/` (`v1.html`, `v2.html`, …, `state.json`). Страница плана открывается в изолированном
фрейме (CSP `sandbox allow-scripts`, `connect-src 'none'`): её скрипты не могут обратиться к API страницы, загрузить
что-то, кроме Mermaid с `cdn.jsdelivr.net`, или отправить форму. Для задачи, которая пишет OpenSpec change, отдельного
плана нет: проверяется сам change.

### OpenSpec: рой пишет change

Если change'а ещё нет, его пишет рой, а вы проверяете спеку до кода. Кода в такой задаче нет: хуки `pre-write` (Write,
Edit, write_file…) и `pre-bash` / `pre-shell` (rm, mv, sed -i, `>`, git checkout/restore/reset…) отклоняют любую запись
вне `openspec/changes/<имя>/` — в момент записи, а не при сдаче работы.

1. **Задача.** В форме «+ Новая задача» в списке OpenSpec выберите «+ написать новый change…», впишите имя
   (`add-loyalty-discount`) и в описании — что нужно, своими словами. Lead — автор, остальные — ревьюеры. CLI:
   `task create --propose add-loyalty-discount --agents backend,reviewer --description "..."`. Нужен `openspec/` в
   проекте (`openspec init --tools claude,qwen` и коммит); сами мы его не создаём. Имя должно быть свободным.
2. **DISCUSS.** Автор получает `files: ["openspec/changes/<имя>/**"]`, остальные — `files: []`. Код в такой задаче
   менять нельзя: соглашение с другими файлами отклоняется (`SPEC_ONLY`).
3. **IMPLEMENT.** Автор пишет `proposal.md`, `specs/<capability>/spec.md` (сценарии WHEN/THEN, по которым можно
   написать тест), `design.md`, `tasks.md` — скиллом `openspec-propose`, если он есть, иначе через
   `openspec new change` и `openspec instructions`. Решения, которые может принять только человек, приходят вам
   вопросами на страницу. `complete()` принимается, только если `openspec validate <имя> --strict` в папке автора
   проходит (без CLI — проверка формы: proposal, хотя бы один spec.md, задачи в tasks.md).
4. **SYNC.** Ревьюер проверяет change (скиллом `java-spec-review`, если он есть, но без правок и без вопросов
   пользователю напрямую): у каждого сценария есть тест, у каждого требования — сценарии, включая ошибки, tasks.md
   покрывает сценарии, design.md не противоречит коду, решения не спрятаны. Дефекты — ERROR автору, дальше обычный
   цикл исправления.
5. **INTEGRATE.** Вливать нечего: автор ещё раз проверяет `validate --strict` и сдаёт.
6. **После DONE** в карточке: «Посмотреть изменения» → «Влить в проект» → **«Реализовать change»** открывает форму
   задачи с этим change (дальше — как ниже). Если в папке кого-то из выбранных агентов change'а нет (их ветки старше
   проекта), форма так и пишет, а кнопка **«Подтянуть change»** вливает текущую ветку проекта в их ветки (`git merge`,
   без force; при незакоммиченных правках или конфликте у агента ничего не меняется). Worktree, который ещё не создан,
   получит change сам: он создаётся от `HEAD` проекта.

**Ответы оператора — в design.md.** Задача реализации — это новые сессии, они видят только файлы change'а, а не
переписку задачи-спеки. Поэтому автор записывает каждый ваш ответ решением в `design.md` (вопрос, ответ, что это
значит), а ревьюер проверяет, что все ответы там есть и спеки им следуют: в задаче-спеке у обоих в `swarm_context`
есть `operatorAnswers`.

Автору нужен `openspec` в разрешениях shell: в примерах есть `Bash(openspec:*)` и `run_shell_command(openspec)`.
Инструкции ролей про код и тесты в такой задаче не действуют — подсказки роя говорят агентам об этом.

### OpenSpec: change по артефактам аналитиков

Аналитики прислали свой набор OpenSpec (proposal.md, spec.md, design.md, tasks.md)? Не кладите его в
`openspec/changes/`: он написан без знания кода, и агенты построят по чужому дизайну. Дайте его задаче «написать change»
как **вход** — lead покажет его вам, допросит вас и напишет свой change по правилам проекта.

1. **Задача.** В форме «+ Новая задача» → «+ написать новый change…» → имя → поле «Артефакты аналитиков»: путь к папке
   или `.md`-файлам, по одному на строку (только `.md`, до 40 файлов, до 200 KB каждый и 1 MB всего). Допрос включается
   сам. CLI: `task create --propose add-loyalty --from ~/Downloads/loyalty/ --agents backend,reviewer`. Файлы
   копируются в задачу (`tasks/<id>/input/`), а оттуда — в `.agent-network/input/<id>/` в папке каждого агента: git их
   не видит, в проект они не попадают.
2. **Страница 1 — их спека** (DISCUSS). Страницу собирает сервер из их файлов как есть; lead присылает только то, что
   знает он один: `plan({stage: "input", departures: [{where, what, rule}], diagrams: ["sequenceDiagram …"], note})` —
   расхождения с кодом и правилами проекта (таблица наверху страницы) и схемы Mermaid. Своего HTML lead не пишет: страница
   одинаковая у любой модели и не остаётся в его контексте. В карточке «Спека аналитиков · ждёт просмотра» → «Открыть и
   проверить». Замечания можно оставить — они станут вопросами допроса; кнопка **«Посмотрел»**. До неё `propose()`
   отклоняется (`INPUT_NOT_REVIEWED`).
3. **Допрос** — как [grill-me](#уточнение-задачи-коротко-или-допрос): раунды вопросов карточками (Q1, Q2, …), итог
   «Как я понял…» с флагом `send_message({…, summary: true})`, ваше «Да». По флагу сервер узнаёт итог при любой
   формулировке; без флага — по словам «Как я понял», «Сводка», «Всё верно?».
4. **Свой change** (IMPLEMENT). Lead пишет change по правилам проекта: в `design.md` — эталон, таблица классов по слоям,
   контракт API; задачи — одна на сценарий, тест первым. Файлы аналитиков не копируются. Каждый ваш ответ на допросе
   записывается в `design.md` с номером вопроса (`Q3: …`): страница 2 не принимается (`DECISIONS_MISSING`, с номерами
   пропущенных), пока в `design.md` нет всех номеров.
5. **Страница 2 — наш change против их.** Её тоже собирает сервер: решения допроса, файлы change (proposal → spec →
   design → tasks) и вход аналитиков под катом. Lead присылает `plan({stage: "change", coverage: [{analyst, outcome:
   "taken"|"adapted"|"dropped"|"added", where, why}], diagrams, note})` — таблицу покрытия (взято / адаптировано /
   отброшено / добавлено — почему). После доработки достаточно `plan({stage: "change"})`: страница пересобирается из
   новых файлов с прежней таблицей. Кнопки **«Принять change»** и **«Вернуть на доработку»** (с замечаниями; lead правит
   файлы и присылает новую версию). Критик плана, если настроен, читает эту страницу.
   `complete()` автора отклоняется (`CHANGE_NOT_APPROVED`), пока change не принят, и если файлы change изменились после
   принятия (например, после исправлений по ревью) — тогда новая версия страницы и снова «Принять».
6. **SYNC** — ревьюер проверяет `java-spec-review` и покрытие входа, дальше как выше: DONE → «Реализовать change».

Скилл, по которому работает lead, — `java-spec-intake` (в этом же наборе скиллов); без него хватает подсказок сервера.

**Модель посильнее для change.** Спеку дешёвая модель пишет хуже, чем код по готовой спеке. `"proposeModel": "sonnet"` у
агента в `runners.json` — модель его сессий в задаче, которая пишет change (`--propose`); в остальных задачах — `model`.
В примере так настроен ревьюер; карточка агента на странице показывает обе модели.

### OpenSpec: рой по готовому change

Если в проекте есть [OpenSpec](https://github.com/Fission-AI/OpenSpec), задачу роя можно поставить прямо по change:
proposal, design и спеки уже описывают ЧТО строить, а `tasks.md` даёт пронумерованные задачи, которые агенты делят между
собой. Change создаётся и проверяется заранее, в обычной сессии: `/opsx:propose` → `/java-spec-review <name>`.

1. **Закоммитьте change** и обновите ветки агентов, если они работают в своих worktree (`git merge main` в каждой).
   Агент в worktree видит только закоммиченное; страница проверяет это при создании задачи и называет агента, у которого
   change нет.
2. **В форме «Новая задача» выберите change** в списке «OpenSpec change» (рядом с именем — сколько задач `tasks.md` уже
   отмечено). Название и описание можно не заполнять: название — имя change, описание указывает на его файлы; ваш текст,
   если он есть, добавляется ниже. Из терминала — `task create --openspec <change> --agents backend,reviewer`.
3. **DISCUSS.** Агенты видят в `swarm_context.openspec` все задачи `tasks.md` и делят их, не перепроектируя: у каждого
   assignment есть `tasks` — номера задач, которые агент делает (`[]` — только ревью). Сервер принимает разбиение, только
   если **каждая открытая задача досталась ровно одному агенту**: без пропусков, повторов и чужих номеров
   (`OPENSPEC_TASKS`). Папка `openspec/changes/<change>/` принадлежит lead'у: сервер сам добавляет её в его `files`, а в
   чужих `files` отклоняет (`OPENSPEC_DIR_LEAD_ONLY`). Если дизайн нужно менять, агенты спрашивают вас.
4. **IMPLEMENT.** Агент видит только свои задачи (`openspec.yourTasks`) и отчитывается номерами:
   `complete({result, filesChanged, tasksDone: [...]})`. Без `tasksDone` или с чужим номером complete отклоняется.
   `tasks.md` никто, кроме lead'а, не трогает.
5. **SYNC.** Ревьюер видит `tasksDone` коллег и сверяет их со сценариями в `specs/`.
6. **INTEGRATE.** Lead видит открытые задачи — кто взял и кто отчитался, — после зелёного `--verify` отмечает их `[x]` в
   `tasks.md`, запускает `openspec validate <change> --strict` (если CLI установлен) и называет в `result` то, что осталось
   открытым.
7. **После DONE — архив.** Влейте ветку lead'а в папку проекта (там, где `.agent-network`): lead отмечает задачи у себя.
   Когда в папке проекта отмечены все задачи, в карточке задачи активна кнопка **«Архивировать change»**: она запускает
   `openspec archive <change> -y` (change переезжает в `openspec/changes/archive/`, его спеки — в `openspec/specs/`) и
   показывает вывод. Результат архива — обычные изменения в рабочей копии: закоммитьте их сами.

Карточка задачи показывает change, сколько задач отмечено в папке проекта, кто какие номера взял и о каких отчитался. Агенту
runner'а скиллы не нужны: всё это приходит в `swarm_context` и подсказках сервера. Правила «как» (TDD по сценариям, ревью
миграций) для сессий со скиллами — в `java-dev-flow/references/swarm.md`.

### Скиллы агентов: включить и выключить

Вкладка «Runner'ы» → «Скиллы агентов»: таблица «скилл × агент», галочка — агент может загружать скилл. Скиллы
берутся из `~/.claude/skills`, `~/.qwen/skills` и `.claude/skills` (`.qwen/skills`) проекта и папок агентов. Скилл,
которого на диске нет (из плагина, или поставите позже), выключается по имени полем под таблицей; `плагин:*`
выключает все скиллы плагина, а имя без префикса — и его вариант с префиксом (`migration-safety` закрывает
`backend-design-java:migration-safety`).

Выключенные скиллы пишутся в `runners.json` (`"disabledSkills": ["java-tdd", "backend-design-java:*"]` у агента; в
`defaults` — всем) и действуют со следующей сессии:

- **Claude Code их не видит вовсе.** Runner дописывает в JSON команды после `--settings` (в примере там хуки)
  `"skillOverrides": {"java-tdd": "off"}`, и скилл пропадает из списка сессии. Его описание больше не читается на
  каждом ходе. Отказ хука такого не даёт: отклонённый скилл в списке остаётся. Если у claude нет `--settings`, runner
  добавляет его сам;
- иначе runner называет их в промпте («Skills the operator switched off for you: …»), чтобы агент не тратил ход на
  отказ. Так бывает для Qwen, для `--settings` с путём к файлу и для маски `плагин:*`: её через `skillOverrides` не
  выключить;
- в любом случае runner передаёт список сессии (`AGENT_NETWORK_DISABLED_SKILLS`), и хук `PreToolUse` `hook pre-skill`
  отклоняет вызов `Skill` и чтение `SKILL.md` такого скилла. В примере для Claude хук стоит в `--settings` (matcher
  `Skill`), для Qwen — в [`examples/qwen-hooks/settings.json`](examples/qwen-hooks/settings.json) (`skill` и `read_file`).

**По типу задачи.** Часть скиллов нужна только в одном типе задач. `disabledSkillsByTask` (у агента или в `defaults`)
выключает их в остальных, поверх `disabledSkills`:

```json
"disabledSkillsByTask": { "propose": ["java-tdd", "java-code-review"], "code": ["java-spec-intake"] }
```

`propose` — задача, которая пишет OpenSpec change (`--propose`): кода там нет, TDD и ревью кода не нужны. `code` — любая
другая задача: в ней не нужен разбор артефактов аналитиков. Так настроен пример. В таблице на странице у такого скилла
стоит «без: change» или «без: код», а переключаются эти списки в `runners.json`.

Какие скиллы агент на самом деле загружал, видно в карточке задачи (строка «скиллы: …»). Совсем убрать инструмент
`Skill` у роли — `withoutTools`.

### Приёмка: пакет вместо диффа

После DONE в карточке задачи — **«Пакет приёмки · ждёт вас»** → «Открыть и проверить». Страница открывается на весь
экран, как план. Вам не нужно читать сырой дифф, чтобы понять, сделано ли то, что просили: страницу собирает сервер, а
lead присылает только то, что знает он один.

**Что присылает lead** — с `complete({status: "PASS"})` в INTEGRATE:

```js
acceptance: {
  criteria: [{ requirement: "Повторный возврат отдаёт 409", status: "done",          // done | partial | not-done
               tests: ["src/test/java/shop/RefundControllerTest.java#returns409WhenRefunded"],
               where: ["src/main/java/shop/RefundService.java"], note: "…" }],       // note — для partial / not-done
  checks: [{ step: "Вернуть заказ дважды", command: "curl -X POST …/refund", expect: "409 ALREADY_REFUNDED" }],
  risks:  [{ what: "…", why: "…" }]
}
```

Сервер отклоняет PASS:

- `ACCEPTANCE_MISSING` — таблицы нет;
- `ACCEPTANCE_EVIDENCE` — файла нет в итоговом коммите или в нём нет названного теста (`path#имя`: метод или
  заголовок `it()`/`test()`): нельзя сослаться на тест, которого нет;
- `ACCEPTANCE_INCOMPLETE` — для задачи по OpenSpec: сценарий из `specs/` не назван ни в одном требовании (требование
  начинается с имени сценария).

Тест lead называет целиком — файл, `#` и имя теста. Только файл (`test/refunds.test.js`) PASS не останавливает, но в
пакете это тревога «Тест назван только файлом»: какой тест доказывает требование, не видно, а сервер смог проверить
лишь то, что файл есть. Так haiku сослался на все пять требований одним файлом в живом прогоне.

Не нужна таблица в поручениях (`delegate`) и в задачах «написать change»: у тех своя страница change.

**Что собирает сервер** — при каждом открытии, из данных задачи:

| Раздел | Откуда |
|---|---|
| **На что посмотреть** | всё ниже, что требует человека: невыполненные и частичные требования, требования без теста или с тестом, названным только файлом, красная сборка, файлы вне соглашения, код без изменений в тестах, обязательные свойства, не заданные в окружении, решения «без вас» (вопрос остался без ответа, агент пошёл по своему варианту), ваши отклонённые замечания, оставшиеся WARNING ревью |
| шапка | ветка, коммит, verify и тесты на нём, раунды исправлений, время, стоимость, влита ли |
| Требования → доказательства | таблица lead'а |
| Как проверить руками | `checks` |
| Что просили | описание задачи, вопросы вам и ответы |
| Ревью | находки по раундам (ERROR — в каком раунде исправлен), ваши замечания к диффу и ответы lead'а |
| Что изменилось | файлы диффа; красным — файл, которого нет ни в одном assignment соглашения |
| Для раскатки | то же, что «Для раскатки» на вкладке «Раскатка» |
| Риски и что осталось | риски, отброшенные подзадачи с причинами, follow-up задачи, итог интеграции |

**Решение** — в панели справа:

- **«Принять и влить»** — ветка lead'а вливается в проект, как «Влить в проект», то есть
  [с проверкой](#вливание-с-проверкой): задача принимается, только когда вливание прошло сборку и легло в проект. Если
  ветка уже влита или своей ветки у lead'а нет — просто «Принять»;
- **«Вернуть с замечаниями»** — в режиме «Замечание» кликните блок или выделите слова и напишите, что поменять.
  Замечания уходят той же команде новой follow-up задачей; её lead отвечает на каждое (`resolve_comments`). Замечания к
  строкам кода — как раньше, в «Посмотреть изменения».

Решение пишется в задачу (`acceptance` в `task.json`) и в итог задачи для наблюдателя (`outcome.acceptance`), так что
видно, какую долю результатов вы возвращаете. У задач, сданных до пакета приёмки, страница та же, но без таблицы lead'а.

### Вливание с проверкой

`verifyCommand` lead прогоняет на своей ветке. Но в проект она попадает поверх его **текущего** HEAD: пока рой
работал, туда могли влить другую задачу, и вместе они ломают сборку. Поэтому у задачи с `verifyCommand` «Влить в
проект» и «Принять и влить» не вливают сразу, а проверяют:

1. **Кандидат.** Во временном worktree `<проект>-merge-<task>` на HEAD проекта собирается то же вливание (squash
   или merge, тем же сообщением коммита). Конфликт виден сразу, со списком файлов. Проект в это время не меняется.
2. **Подготовка.** Свежему worktree нужны зависимости: по lockfile проекта — `npm ci`, `yarn install
   --frozen-lockfile`, `pnpm install --frozen-lockfile` или `npm install`; Maven и Gradle — ничего. Свои команды —
   `"mergeCheck": {"setup": ["npm ci"]}` в `runners.json`, `[]` — без подготовки. Команды — как у инструмента
   `build`: одна команда сборочного инструмента, без shell.
3. **Сборка.** `verifyCommand` на кандидате (до 20 мин). Лог остаётся в `.agent-network/tasks/<task>/merge-check/build.log`.
4. **Итог:**
   - **зелёная** — ветка проекта сдвигается на **этот же коммит** (`git merge --ff-only`): без нового вливания и
     второй сборки, так что «сборка зелёная» — ровно про то, что легло в проект. В карточке и пакете приёмки —
     «сборка после вливания зелёная»;
   - **проект сдвинулся**, пока шла сборка (новый коммит или незакоммиченные правки), — ничего не вливается,
     «Проверить снова»;
   - **красная** или **конфликт** — проект не тронут, кандидат хранится в `refs/agent-network/merge/<task>`.

После красной сборки или конфликта в карточке задачи:

- **«Отдать команде»** — follow-up задача той же команде. После красной сборки она начинает с проверенного
  вливания (`baseCommit` — кандидат) и в описании получает, что упало; после конфликта — вливает HEAD проекта в свои
  ветки и разрешает конфликты. Её вливание пройдёт ту же проверку;
- **«Проверить снова»** — на текущем HEAD проекта (например, после правки в main);
- **«Влить всё равно»** — после красной сборки, с подтверждением: вливается как есть, задача помечается «без
  проверки сборки», а пакет приёмки показывает это тревогой. Надзору эта кнопка недоступна.

Проверка идёт одна на проект; состояние — в `.agent-network/tasks/<task>/merge-check.json`. Проверка, прерванная
перезапуском страницы, видна как прерванная.

### Уборка worktree

Кнопка в карточке DONE-задачи «Убрать worktree агентов» убирает worktree агентов. На вкладке «Runner'ы» — **«Убрать все
worktree проекта»**, разом:

- worktree агентов — если у них нет открытой задачи и сессии;
- worktree [контрактов API](#контракт-api-в-другом-репозитории) закрытых задач, в том числе удалённых (их ищет и в
  `deleted/`); ветку контракта — только если контракт влит;
- worktree, брошенные [проверками вливания](#вливание-с-проверкой) (`<проект>-merge-task-NNN`, например после
  остановки страницы посреди проверки), кроме идущей проверки.

Всё без `--force`, кроме брошенных проверок (они одноразовые): папка с незакоммиченными правками и невлитая ветка
остаются, ответ говорит, что убрано, что осталось и почему. Нужные worktree агентов создадутся заново перед следующей
задачей. Надзору кнопка недоступна.

### Удаление задачи

Закрытую задачу (DONE или отменённую) можно убрать со страницы кнопкой «Удалить задачу» в её карточке. Ничего не
стирается: папка задачи — переписка, соглашение, отчёты ревью, план, сборки, логи сессий — переезжает в
`.agent-network/deleted/<id>/`, и задача уходит со страницы и из статистики расхода. Код в ветках агентов и влитые
коммиты остаются.

В подтверждении можно написать, **почему** удаляете («агент придумал задачу», «не та команда»), — необязательно.
Причина попадает в итог задачи для [наблюдателя](#наблюдатель-агент-который-улучшает-саму-систему)
(`deleted: {at, reason, folder}`): то, что вы выбрасываете, — тоже находка о рое. Наблюдатель читает её файлы из
`deleted/<id>/`, а задача, удалённая после его отчёта, снова приходит ему как новая.

Номер не освобождается: в `tasks/<id>/` остаётся `deleted.json` (что, когда, почему, куда), и новая задача получит
следующий номер — на старый ссылаются раскатки, журнал надзора, follow-up.

Не удаляется: открытая задача (сначала «Отменить»), задача с открытым follow-up или поручением (они читают её), задача,
чьё вливание проверяется или раскатывается. Удаляет только оператор: надзору это недоступно.

### Контракт API в другом репозитории

Спека OpenAPI живёт отдельным Maven-проектом: он выпускается в Nexus, сервис берёт его как зависимость релизной
версии, а локально — из `~/.m2` после `mvn install`. Задача, которой надо поменять API, меняет и контракт, и сервис —
в одной задаче, на два репозитория.

**Путь к контракту указывается при проектировании:**

- в форме задачи — поле «Проект контракта OpenAPI» (абсолютный путь к репозиторию). Страница сразу показывает его
  `groupId:artifactId`, версию и найденные спецификации (`.yaml` с `openapi: 3`);
- или в карточке задачи, пока она в DISCUSS, — «Указать проект контракта». Если lead на проектировании понял, что API
  надо менять, а контракта нет, подсказка велит ему спросить вас. Сессия lead'а после этого перезапускается с доступом
  к контракту. После соглашения контракт уже не добавить.

**Как его меняют агенты:**

- у задачи свой worktree контракта: `<контракт>-<task>` на ветке `swarm-<task>`;
- меняет контракт **только lead** (как папку OpenSpec-change): в соглашении его файлы — `contract:<путь>`, у других
  агентов они отклоняются (`CONTRACT_LEAD_ONLY`), без указанного проекта — тоже. Сессии lead'а runner даёт этот
  worktree (`--add-dir` у Claude Code, `--include-directories` у Qwen);
- lead поднимает **версию контракта** (ломающее изменение — major, новые операции или поля — minor), ставит её в
  `~/.m2` — `build({in: "contract"})`, по умолчанию `./mvnw -q -B install -DskipTests` — и переводит зависимость
  сервиса на неё. Новая версия никому не мешает: уже выпущенная в `~/.m2` не перезаписывается;
- коммитит контракт **сервер** при `complete()` lead'а — только файлы `contract:` из его assignment, иначе
  `FILE_NOT_OWNED`. Своих git-прав в чужом репозитории агенту не нужно;
- остальные агенты и ревьюеры читают контракт инструментом `contract` (`{file}`, `{diff: true}`).

**В пакете приёмки** — раздел «Изменения API»: что поменялось в спецификации (операции, параметры, ответы, поля, обязательные
поля, enum, типы), какие изменения **ломающие**, какой нужен подъём версии. Тревоги: ломающие изменения; версия не поднята
или поднята меньше, чем нужно; сервис зависит не от новой версии; новая версия есть только локально в `~/.m2` (Maven
пишет происхождение в `_remote.repositories`), то есть в Nexus её ещё нет; сборка контракта не зелёная.

**«Принять и влить»** вливает сначала контракт в его репозиторий — с [проверкой](#вливание-с-проверкой) его собственной
сборкой (`verifyCommand` по стеку: `./mvnw -q -B verify …`), — затем сервис. Красный контракт до сервиса не доходит;
чинится в репозитории контракта, затем «Проверить снова» (или «Влить всё равно»). «Откатить» откатывает и сервис, и
контракт.

**В таблице приёмки** lead доказывает требование и файлами контракта: `contract:<путь>` (например,
`contract:src/main/resources/openapi/orders.yaml#refundOrder`) проверяется на ветке контракта, как обычный путь — на
итоговом коммите сервиса. Так требование, сделанное в контракте, — «сделано», а не «частично».

**Worktree контракта** остаётся после задачи; его убирает кнопка «Убрать все worktree проекта» (вкладка «Runner'ы»):
ветку контракта — только если контракт влит.

**Выпуск контракта в Nexus** — вашим CI. На вкладке «Раскатка» сервис, который зависит от ещё не выпущенной версии
контракта, без вашего подтверждения не отправляется: в Jenkins такая сборка его не найдёт.

### Раскатка: Bitbucket → Jenkins → Kubernetes

Вкладка **«Раскатка»** отправляет влитую задачу дальше. Запускаете только вы: агентам `git push` запрещён хуком
`pre-bash`, а у этой вкладки нет инструментов для агентов.

1. **Влитые задачи** — задачи, влитые кнопкой «Влить в проект» и не откаченные, с состоянием: «не отправлена», «в
   ветке, ждёт» (ветка в Bitbucket, на стенде её нет), «на стенде: dev, …» (последняя раскатка в это окружение прошла
   проверку в Kubernetes), «идёт раскатка», «ошибка раскатки». Кнопки над списком фильтруют по состоянию, выбор
   запоминается. «Раскатить…» → окружение →
   **«Для раскатки»**: что нужно сервису в этом окружении. Список собирается из diff задачи:
   - новые поля `@ConfigurationProperties`, новые `@Value("${…}")` и ключи `application*.yml` / `.properties`;
   - для каждого: переменная окружения по правилам Spring (`orders.gift-wrap.price` → `ORDERS_GIFTWRAPPRICE`),
     значение по умолчанию, обязательно ли (сервис без него не стартует), похоже ли на секрет. Значения секретов
     не показываются;
   - задано ли оно в каждом окружении: в его values-файле или в списке «Заданы там же» из настроек;
   - новые changeset'ы, топики Kafka и внешние адреса.

   Обязательное свойство, которого нет в окружении, выделено красным и названо в подтверждении перед push.
2. **Push в Bitbucket** — коммит задачи уходит в ветку по шаблону (`feature/{task}-{slug}`) через `git push` по SSH
   вашим ключом: agent-network не хранит токенов Bitbucket. Перед push — `git fetch`, в отчёте список ушедших
   коммитов. Без force: если в ветке в Bitbucket есть чужие коммиты, push отклоняется.
3. **Job в Jenkins** — через MCP-сервер Jenkins из настроек. Сервер страницы запускает его по команде (по аргументу на
   строку) с переменными: значение `${ИМЯ}` берётся из окружения сервера страницы, так что токен не лежит в
   настройках. Дальше он:
   - вызывает инструмент запуска job с аргументами из JSON-шаблона. Плейсхолдеры: `{job}`, `{params}` (объект
     параметров), `{branch}`, `{commit}`, `{env}`, `{task}`; `"{x}"` целиком подставляется как значение JSON. Параметры
     job: общие из настроек плюс параметры окружения, у них приоритет;
   - достаёт номер сборки и ссылку из ответа: поля `number` / `buildNumber` / `build_number`, `url` в JSON, или
     «#42» и адрес `…/job/…/42/` в тексте;
   - раз в 15 секунд опрашивает инструмент статуса (`{build}` в его шаблоне) до результата: `building: false` и
     `result`, или слово SUCCESS / FAILURE / ABORTED / UNSTABLE в тексте. Ждёт не дольше таймаута из настроек;
   - при любом результате, кроме SUCCESS, берёт хвост лога инструментом лога и останавливает раскатку до
     Kubernetes. Ссылка на сборку — в строке шага.

   Пример для MCP с инструментами `trigger_build` / `get_build` / `get_build_log`: запуск
   `{"jobName": "{job}", "parameters": {params}}`, статус и лог `{"jobName": "{job}", "buildNumber": {build}}`. Без
   MCP в настройках шаг пропускается с причиной, и шаг Kubernetes ждёт раскатку, которую запустили не отсюда.
4. **Kubernetes** — проверка раскатки, kubectl только на чтение: `get deployment / rs / pods / events -o json` и
   `logs` с контекстом и namespace из настроек (у окружения — namespace, deployment, метки подов; без меток берутся
   `matchLabels` Deployment). Тег образа со сборкой не связан, поэтому «наша» раскатка — текущий ReplicaSet Deployment,
   созданный после старта раскатки. Шаг ждёт его до таймаута из настроек, затем ждёт, пока все реплики обновлены,
   готовы и доступны. Поды в `CrashLoopBackOff`, `ImagePullBackOff` или `CreateContainerConfigError` — сразу ошибка:
   к ней прикладываются хвост лога пода (с `--previous` после перезапуска) и предупреждения из events, а лог
   сверяется с «Для раскатки» («не задано ORDERS_PARTNERAPIKEY — оно было в «Для раскатки»»). Без namespace и
   deployment у окружения шаг пропускается. Нужен контекст kubeconfig с правами `get`/`list` на deployments,
   replicasets, pods, events и `get` на `pods/log`.

Каждая раскатка хранится в `.agent-network/deploys/dep-NNN.json` со статусом и выводом каждого шага. Раскатка, которую
прервал перезапуск страницы, помечается прерванной. Настройки — в `.agent-network/deploy/settings.json`, их правят на
той же вкладке. Секреты MCP пишите как `${ИМЯ}`: значение возьмётся из окружения сервера страницы.

### Задачи по расписанию (cron)

Повторяющуюся работу — каждую ночь чинить флаки-тесты, раз в неделю обновлять зависимости — можно не ставить руками:
расписание (на странице кнопкой «+ Расписание» или секцией `"schedules"` в `runners.json`), и страница сама создаёт
задачу в нужное время. Модель для этого не нужна: задачу
ставит код, а runner'ы подхватывают её, как любую задачу из формы.

```json
"schedules": [
  {
    "id": "nightly-flaky-tests",
    "cron": "0 3 * * 1-5",
    "title": "Flaky tests {date}",
    "description": "Run the full test suite twice ... In result: which tests were flaky, why, what you changed.",
    "agents": ["backend", "reviewer"],
    "maxFixRounds": 1,
    "enabled": true
  }
]
```

- **`cron`** — 5 полей по местному времени: минута, час, день месяца, месяц, день недели. Поддерживаются `*`, списки
  `1,15`, диапазоны `1-5`, шаги `*/15` и `9-18/3`, имена `mon..sun` и `jan..dec`. Есть сокращения `@hourly`, `@daily`,
  `@weekly`, `@monthly`, `@weekdays` (пн–пт в 9:00). Если заданы и день месяца, и день недели, достаточно совпадения
  одного, как в cron.
- **`title`, `description`, `agents`** (первый — lead), `openspec`, `verifyCommand` (иначе — `verifyCommand` конфига),
  `maxFixRounds`, `maxFollowUps`, `maxCostUsd` (иначе — `maxTaskCostUsd` конфига) —
  как в форме «Новая задача». `{date}` и `{time}` в тексте заменяются датой и временем запуска. Агенты должны быть из
  этого `runners.json`: иначе задачу некому взять, и конфиг не загрузится.
- **Без накопления.** Пока задача прошлого запуска того же расписания открыта (`ACTIVE` или `BLOCKED`), новый запуск
  пропускается с пометкой «пропуск». Пропущенные, пока страница была выключена, запуски не догоняются, как в cron.
- **На странице**, в разделе «Задачи», — блок «По расписанию»: переключатель вкл/выкл, cron, когда следующий запуск,
  чем кончился последний (задача, пропуск или ошибка), кнопки «Запустить сейчас», «Изменить», «Удалить».
- **«+ Расписание»** открывает форму: id, cron с подсказкой трёх ближайших запусков (неверный cron виден сразу),
  название, описание, lead и остальные агенты, сборка, раунды, лимит стоимости, вкл/выкл. Сохраняется в `runners.json`
  проекта (`.agent-network/runners.json` при запуске одной командой) с той же проверкой, что при старте, и действует
  сразу. Переименованное расписание сохраняет историю; удаление не трогает уже созданные им задачи. Блок «По расписанию»
  есть всегда, когда страница запущена с runner'ами, даже без единого расписания. Задачи из
  расписания помечены «по расписанию <id>». История запусков — `.agent-network/schedules/state.json`.
- Расписания перечитываются из `runners.json` каждые 30 с: правка файла руками тоже действует без перезапуска.
  Новое расписание первый раз срабатывает в ближайшее по cron время, а не сразу.

В примерах `runners.*.example.json` есть выключенное расписание `nightly-flaky-tests`: включите его на странице, когда
захотите.

### Надзор: агент, который снимает проблемы роя

В живых прогонах рой застревал на мелочах, которые снимал человек: тест висел на незакрытой транзакции, а lead раз за
разом пробовал запрещённый `kill -9`; вопрос оператору висел полтора часа; агент спрашивал «почему lead не одобряет?».
**Надзор** — LLM-сессия с правами помощника оператора, которая делает это за вас.

**Как работает.** Детектор без модели раз в 10 с смотрит на рой и ищет инциденты:

| Инцидент | Когда | Порог в `rules` |
|---|---|---|
| `question` | вопрос агента оператору без ответа | `questionAfterSec` (60) |
| `blocked` | задача стала `BLOCKED` | сразу |
| `stall` | у агента идёт сессия, но нет прогресса: подзадачи, события, git его папки | `stallMin` (15) |
| `repeat` | агент повторяет одну и ту же команду (сборки и тесты не в счёт) | `repeatCount` (3) |
| `check-in` | агент работает (не ждёт) над одной фазой задачи дольше порога — и снова через каждый такой отрезок: надзор смотрит, движется ли он или ходит по кругу, и предлагает помощь | `checkInMin` (30) |
| `refused` | агенту отказывают в правах раз за разом, даже если каждый раз команда другая (ищет переменные окружения, файлы вне своей папки) | `refusedCount` (4 за 10 мин) |
| `hung-test` | тестовая JVM в папке агента живёт слишком долго | `testMin` (10) |
| `gave-up` | runner сдался после неудачных сессий | сразу |

Каждый инцидент попадает в журнал один раз, даже после перезапуска страницы. На новые инциденты стартует **одна сессия
надзора**: CLI (Claude Code или Qwen Code) с инструментами `supervisor-mcp`, промптом
[supervisor-prompt.md](examples/runner/supervisor-prompt.md) и списком инцидентов. Что всплыло, пока она идёт, ждёт
следующей. В спокойном прогоне надзор не стоит ничего.

**Что делает сам** (через те же маршруты, что и ваши кнопки, — в журнале это `action` от `supervisor`):
отвечает на процессные и технические вопросы агентов; пишет lead'у задачи, что нашёл и что делать (lead передаёт
дальше); даёт `BLOCKED`-задаче ещё
раунд или отдаёт исправление lead'у; смотрит тестовые JVM в папках агентов (`processes`, `thread_dump` — jstack) и базы
Testcontainers (`db_activity` — `pg_stat_activity`), завершает зависший тест (`kill_test`) или соединение `idle in
transaction` (`db_terminate`). Чужие процессы, CLI самих агентов и контейнеры не от Testcontainers он тронуть не может.
Код, ветки, задачи он не меняет: у его CLI только чтение файлов, без shell и правок, и инструмента «отменить задачу» нет.

**Что отдаёт вам** (`escalate`): требования и объём работы, дизайн change, отмену задачи, всё необратимое и всё, в чём он
не уверен. Такой вопрос с его рекомендацией висит на вкладке «Надзор» и красной всплывашкой, пока вы не решите. Кнопки
карточки: **«Принять рекомендацию»** — текст рекомендации уходит агенту; **«Ответить по-своему»** — ваш текст;
**«Закрыть без ответа»** — агент ничего не получает. Если решение про вопрос агента (надзор передаёт его `messageId`),
ответ приходит этому агенту ответом на вопрос и вопрос закрывается; иначе — lead'у задачи, который передаст дальше. Действия надзора всплывают синими уведомлениями, в строке статуса — «надзор: следит / работает / ждёт / выкл».

**Включение.** Секция `"supervisor"` в `runners.json` — готовые в
[runners.claude.example.json](examples/runner/runners.claude.example.json) (Claude, `sonnet`) и
[runners.qwen.example.json](examples/runner/runners.qwen.example.json) (Qwen Code с моделью из LM Studio), MCP-конфиги
[supervisor-mcp.json](examples/runner/supervisor-mcp.json) и [qwen-supervisor-mcp.json](examples/runner/qwen-supervisor-mcp.json):

```json
"supervisor": {
  "command": ["claude", "-p", "{prompt}", "--output-format", "stream-json", "--verbose", "--system-prompt", "{systemPrompt}",
              "--model", "{model}", "--max-turns", "30", "--tools", "Read,Grep,Glob",
              "--mcp-config", "/abs/path/agent-network-mcp/examples/runner/supervisor-mcp.json", "--strict-mcp-config",
              "--allowedTools", "mcp__supervisor", "Read", "Grep", "Glob"],
  "model": "sonnet", "models": ["haiku", "sonnet", "opus"],
  "promptFile": "supervisor-prompt.md", "systemPromptFile": "supervisor-system-prompt.md",
  "rules": { "questionAfterSec": 60, "stallMin": 15, "repeatCount": 3, "testMin": 10, "refusedCount": 4, "checkInMin": 30 },
  "maxSessionsPerHour": 6, "budgetUsd": 5, "autostart": true,
  "tools": [ { "name": "agent_git_log", "description": "The latest 15 commits of an agent's worktree branch",
               "command": ["git", "log", "--oneline", "--decorate", "-15"], "cwd": "{agentCwd}" } ],
  "disabledTools": []
}
```

- **Модель** — `"{model}"` в `command` и `"model"`; на вкладке «Надзор» её выбирают из `"models"`, выбор пишется в
  `runners.json` и действует со следующей сессии.
- **Вкл/выкл** — кнопка на вкладке; `"autostart": false` — надзор стартует выключенным. Выключение останавливает и
  идущую сессию.
- **Лимиты** — не больше `maxSessionsPerHour` сессий в час и `budgetUsd` долларов за сутки. Стоимость сессии — от CLI
  (Claude) или по `"prices"` (Qwen, локальные модели); без цены считается только лимит сессий. Когда лимит исчерпан,
  инциденты ждут, а журнал и вкладка говорят почему.
- **Свои команды** — `"tools"`: `name`, `description` (по нему надзор выбирает инструмент), `command` — argv без shell.
  Подстановки: `{agentCwd}` (появляется параметр `agentId` — папка этого агента), `{projectDir}`, `{networkDir}` и свои
  параметры из `"params"` (`{"type": "string"|"integer", "enum": [...], "pattern": "..."}`). Значение без `enum` и
  `pattern` — слово или путь без пробелов и не с `-`, так что флаг или вторую команду не подсунуть. `"cwd"` — где
  запускать (по умолчанию папка проекта), `"timeoutSec"` — до 600, `"action": true` — команда что-то меняет, и каждый
  её запуск пишется в журнал.
- **Выключить инструмент** — встроенный или свой: переключатель на вкладке или `"disabledTools"`; со следующей сессии.
- **Лимиты** («сессий в час», «$ за сутки», пусто — без бюджета) тоже меняются на вкладке «Надзор» кнопкой «Сохранить
  лимиты»: пишутся в `maxSessionsPerHour` и `budgetUsd`, действуют сразу — придержанные лимитом инциденты уходят в
  работу при следующей проверке.
- **Пороги** правил меняются прямо на вкладке «Надзор» («Сохранить пороги» пишет их в `supervisor.rules`) или в файле.
  Пороги, лимиты, инструменты и модель перечитываются из `runners.json` на лету, без перезапуска.

**Журнал и разбор решений.** Всё, что надзор увидел и сделал, остаётся на диске и переживает перезапуск страницы:

- **журнал** — `.agent-network/supervisor/journal/entry-NNN.json`: `incident` (что нашёл детектор, с исходными данными),
  `note` (что он увидел и почему решил так — промпт требует такую запись перед каждым действием), `action` (что сделал),
  `needs-you` (вопрос вам, рекомендация, когда вы нажали «Решено»), `session` (итог сессии и ссылка на её лог);
- **сессия целиком** — `.agent-network/supervisor/sessions/session-NNN.jsonl`: промпт с инцидентами, каждый вызов
  инструмента с аргументами, каждый результат (✓/✗, время, текст), его текст и мысли, итог (ходы, стоимость). Пишется по ходу
  сессии, так что и оборванная сессия оставляет то, что успела; одинаково для Claude и Qwen;
- **транскрипт CLI** — Claude Code сам хранит свою сессию в `~/.claude/projects/<папка>/<id>.jsonl`; её id и путь
  записываются в итог сессии.

На вкладке «Надзор» журнал показывает последние 100 записей («показать все» — весь), а под записью `session` — кнопка
«Показать сессию» с её полным логом. Для разбора в терминале:

```bash
node dist/index.js supervisor journal [--task task-002] [--since 24h] [--kind note,action,needs-you] [--json]
node dist/index.js supervisor sessions            # когда, какие инциденты, итог, стоимость
node dist/index.js supervisor session 3 [--full]  # одна сессия: вызовы, результаты, текст (--full — с аргументами и промптом)
```

**Стоимость.** Спокойный прогон — $0: правила проверяет код. Один инцидент на `sonnet` — примерно $0.2–0.6, прогон с
5–8 инцидентами — $2–4. Сессии надзора записываются как сессии агента `supervisor` в задаче инцидента: они видны во
вкладке «Запуски», в статистике задачи и в ленте «Активность».

### Наблюдатель: агент, который улучшает саму систему

Надзор снимает проблемы по ходу задачи. Наблюдатель смотрит назад, по многим закрытым задачам, и ищет проблемы самой
системы — протокола, подсказок роя, промптов ролей, runner'ов, конфигурации: «тестировщики упираются в лимит ходов»,
«lead'ы получают CLARIFY_FIRST», «вопросы ждут ответа по 40 минут», «половина стоимости — фаза SYNC».

1. **Итоги задач без модели.** Когда задача закрывается (DONE или отменена), страница пишет её итог в
   `.agent-network/observer/digests/<task>.json`: минуты по фазам, стоимость и упавшие / упёршиеся в лимит сессии по
   агентам, блокировки с причинами, находки ревью, вопросы к оператору и время ответа, отказы протокола по коду
   (агенты пишут их в `observer/errors/<agent>.jsonl`), красные сборки, инциденты надзора, добавленные агенты, ваши
   замечания к диффу и к странице приёмки — с тем, чей это файл по соглашению и чем кончилось (исправлено / отклонено с
   ответом lead'а), — и вердикт приёмки. Это бесплатно.
2. **Сессия наблюдателя** — по `cron` из `runners.json` (в примерах — понедельник 9:00; без новых закрытых задач
   пропускается) или кнопкой «Запустить сейчас» на вкладке «Наблюдатель». CLI с правами только на чтение (папка сети и
   исходники agent-network-mcp) и свой MCP-сервер `observer-mcp`: `digests` (новые итоги), `history` (что он уже
   отслеживает и как вы решили по прошлым предложениям), `save_report`. Писать он может только в `observer/`.
   Повторяющиеся ваши замечания одной роли (в двух задачах и больше) наблюдатель превращает в предложение — правило в
   файл инструкций этой роли (`instructionsFile` агента в `runners.json`), с задачами и замечаниями как доказательством.
3. **Отчёт** (по-русски) с доказательствами — задачи, числа, строки логов — и **предложения**: проблема, где видна, во
   что обходится, конкретная правка (файл и что поменять), приоритет и цель: `agent-network` (код, подсказки и примеры
   самого роя) или `project` (runners.json и инструкции проекта). Ещё он ведёт список известных проблем и отмечает,
   когда проблема ушла после правки.
4. **Решаете вы** на вкладке «Наблюдатель»: **«Принять → задача»** создаёт задачу для роя (с уточнением постановки и
   лимитом стоимости по умолчанию) — в этом проекте или, для `agent-network`, в сети репозитория agent-network-mcp
   (там должны работать его runner'ы: `agent-network-mcp ui` в этом репозитории). Дальше как с любой задачей: дифф,
   «Влить в проект». **«Отклонить»** — с причиной: наблюдатель её прочтёт и больше это не предложит.

```json
"observer": {
  "command": ["claude", "-p", "{prompt}", "--output-format", "stream-json", "--verbose", "--system-prompt", "{systemPrompt}",
              "--model", "{model}", "--max-turns", "40", "--tools", "Read,Grep,Glob",
              "--add-dir", "{agentNetworkMcp}", "--add-dir", "{networkDir}",
              "--mcp-config", "{\"mcpServers\":{\"observer\":{\"command\":\"node\",\"args\":[\"{agentNetworkMcp}/dist/index.js\",\"observer-mcp\"],\"env\":{\"NETWORK_DIR\":\"${NETWORK_DIR}\"}}}}",
              "--strict-mcp-config", "--allowedTools", "mcp__observer", "Read", "Grep", "Glob"],
  "model": "sonnet", "models": ["haiku", "sonnet", "opus"],
  "promptFile": "observer-prompt.md", "systemPromptFile": "observer-system-prompt.md",
  "cron": "0 9 * * 1"
}
```

`{networkDir}` в команде — папка сети этого проекта. Промпт —
[observer-prompt.md](examples/runner/observer-prompt.md): закономерности по нескольким задачам, а не разовые сбои;
причина до предложения; два-три обоснованных предложения лучше десяти догадок. Сам наблюдатель ничего не меняет:
улучшения доходят до системы только через принятую вами задачу и ваше вливание.

**Вместе со skills разработки** (например, `java-dev-flow`) слои разделены: этот skill решает *когда и кто* (фаза, assignment,

## Конфигурация

Переменные окружения процесса MCP:

| Переменная | Обязательна | Описание |
|---|---|---|
| `AGENT_ID` | да | идентичность агента (`[A-Za-z0-9][A-Za-z0-9_-]{0,63}`) или пул через запятую |
| `NETWORK_DIR` | да | абсолютный путь к `.agent-network/` (не `/`); у всех агентов одинаковый. `auto` — `<корень git-репозитория>/.agent-network`, общий для всех его worktree |
| `AGENT_TYPE` | нет | `qwen`, `claude`, ... (метка; по умолчанию `unknown`) |
| `AGENT_ROLE` | нет | роль (метка) |
| `AGENT_NETWORK_WAIT_MS` | нет | таймаут `wait` по умолчанию, 1000..300000 (по умолчанию 120000); ниже таймаута tool у клиента |
| `AGENT_NETWORK_ADVANCED` | нет | `1` включает расширенные tools |
| `AGENT_NETWORK_RUNNER` | нет | `1` ставит runner: на `BLOCKED` сессия заканчивается, а не ждёт |
| `AGENT_NETWORK_OPERATOR_TIMEOUT_MIN` | нет | сколько минут оператор может думать (по умолчанию 10): над вопросом агента (потом агент идёт по своему варианту и говорит об этом) и над застрявшей `BLOCKED`-задачей (потом исправление на раунд берёт lead) |
| `AGENT_NETWORK_FRESH_PHASES` | нет | ставит runner (`--fresh-phases`): фазы, которые сессия, видевшая задачу раньше, передаёт свежей (`SYNC`, `IMPLEMENT`, `INTEGRATE`) |

Добавьте `.agent-network/` в `.gitignore` проекта. Процесс при старте регистрирует агента сам (отдельного `agent_register`
больше не нужно); если `AGENT_ID` уже держит живой процесс, сервер не стартует (клиент покажет «disconnected»).

### Конкурентность и надёжность

- **Общих JSON-массивов нет**: одно сообщение/событие/отчёт — один файл. Перезапись состояния — temp-файл в той же
  директории и атомарный `rename`.
- **Уникальные id** выделяются эксклюзивным созданием (`link` / `mkdir` падают с `EEXIST`); проигравший гонку берёт
  следующий номер. Файлы не теряются и не перезаписываются даже при записи из нескольких процессов.
- **Read-modify-write состояния задачи** (одобрение, start/complete, sync, переходы фаз, отмена) идёт под простым
  кросс-процессным lock на `mkdir` (`tasks/task-NNN/.lock`). В lock'е лежит `owner` (pid и токен):
  - держатель трогает lock каждые 5 с, поэтому долгая работа под ним (git merge, `openspec archive`) не считается
    зависшей;
  - lock, чей процесс умер, снимается сразу, а нетронутый 30 с — как зависший;
  - держатель удаляет только свой lock, а при выходе процесса свои lock'и освобождаются.

  Чек-лист агента (`subtasks/<agent>.json`) меняется под своим lock'ом: его пишут и агент, и поручения lead'а.
- **Нагрузка на диск с ростом истории:**
  - страховочный опрос ждущих процессов идёт раз в 10 с, если `fs.watch` работает (без него — раз в 1 с);
  - неизменённый `task.json` повторно не читается: его узнают по inode, а запись всегда идёт через rename;
  - запаркованный runner читает только новые события и сообщения задачи;
  - страница не пересобирает завершённые задачи: вид задачи строится заново, когда меняется её `task.json` (слияние,
    откат), но не реже раза в минуту;
  - скрытая вкладка страницы не обновляется, а при возврате на неё обновляется сразу.
- **Id новых агентов** (`spawn_agent`, `delegate`) занимаются один раз на всю сеть — `claims/agents/<id>.json`
  создаётся только если его нет. Два lead'а разных задач не получат одинаковый id.
- **События адресные.** `targetAgent: "<id>"` получает только адресат, `null` получают все агенты задачи; агента не
  будят его собственные события (`sourceAgent`). Курсоры у каждого агента свои, поэтому рестарт ничего не теряет и не
  проигрывает повторно. Доставка «не более одного раза»: если процесс упал сразу после чтения события, оно не придёт
  снова, но состояние восстанавливается через `swarm_context`.
- **Ожидание.** Сначала проверка файловой системы, затем регистрация waiter, один общий `fs.watch` на процесс (+ резервный
  опрос раз в секунду на случай потерянных OS-событий), при пробуждении состояние перечитывается с диска.
- **Crash recovery.** Сервер не хранит состояние workflow в памяти. После `SIGKILL` и рестарта `swarm_context` возвращает
  то же состояние, непрочитанные сообщения не теряются, `wait` продолжает работать.
- **Дубликаты агентов.** Один `AGENT_ID` одновременно у двух живых процессов невозможен (проверка по pid); перерегистрация
  после рестарта разрешена.

## Безопасность

- Идентичность — только из `AGENT_ID`; из аргументов tools её получить нельзя.
- Все пути строятся из проверенных сегментов, резолвятся и должны оставаться внутри `NETWORK_DIR`; запрещены `..`,
  абсолютные пути, разделители, NUL. Id задач/сообщений/агентов валидируются по шаблонам; `filesChanged`/`files` не
  читаются с диска, это только отчёт агента, но тоже проверяются на `..` и абсолютные пути; `commits` только hex и
  передаются в `git` только как аргументы (`execFile`, без shell). `verifyCommand` сервер не выполняет: его запускает lead.
- Ошибки не содержат stack trace (он пишется в stderr процесса). stdout занят протоколом MCP.
- UI только читает, слушает loopback и проверяет `Host`.
- Аутентификации и авторизации нет: все процессы с доступом к `NETWORK_DIR` доверяют друг другу (локальная машина).

## Частые вопросы

**Агент задал вопрос — куда отвечать?** На странице `ui --runners`, в блоке «Вопросы агентов» вверху (число открытых
вопросов видно и в заголовке вкладки). Ответ приходит агенту сообщением, и он продолжает в той же сессии. В терминале
runner'а ответить нельзя: сессия headless и ввод не читает. UI без `--runners` вопросы показывает, но ответить из него
нельзя. Не ответили за 10 минут — агент идёт по варианту, который предложил в вопросе, и пишет об этом команде.

**Я подключил MCP-сервер (Serena) в Qwen — агенты runner'а его получат?** Сам сервер у Qwen, скорее всего, подтянется,
но вызывать его агенты не смогут, пока его нет в `--allowed-tools`; у Claude Code с `--strict-mcp-config` — нет. Подробно
и про цену в токенах — [Свои MCP-серверы для агентов runner'а](#свои-mcp-серверы-для-агентов-runnerа-например-serena).

**Как запустить агентов в моём проекте, не прописывая пути?** Запустите `ui` из папки проекта (git, хотя бы один
коммит) с примером `runners.claude.example.json` или `runners.qwen.example.json` как есть: проект берётся из текущей папки, worktree агентов
(`<проект>-backend` и т.д. на ветках `swarm-*`) и сеть `<проект>/.agent-network` создаются сами. Несколько проектов —
копия примера на каждый с полем `"project"`. Подробно — [Запуск в своём проекте одной командой](#запуск-в-своём-проекте-одной-командой).

**Change'а ещё нет — как его написать?** Задача «+ написать новый change…»: lead пишет change, ревьюер проверяет,
вопросы о решениях — вам; после DONE вы смотрите изменения, вливаете и нажимаете «Реализовать change».
[OpenSpec: рой пишет change](#openspec-рой-пишет-change).

**Можно не сидеть у страницы, пока идёт рой?** Да: то, что ждёт вас, приходит
[уведомлением](#входящие-и-уведомления) — браузера или, на Linux, системным — и копится во «Входящих». Включите и
[надзор](#надзор-агент-который-снимает-проблемы-роя): он сам
отвечает на процессные вопросы агентов, снимает зависшие тесты и блокировки в тестовой базе, даёт застрявшей задаче ещё
раунд. Вам остаются только решения, которые может принять человек: они ждут на вкладке «Надзор» с его рекомендацией.

**Я создал задачу, пока агенты заняты другой. Что будет?** Новая задача встаёт в очередь. Агент работает над одной
задачей за раз — самой старой незавершённой (`ACTIVE` или `BLOCKED`) — и переходит к следующей сам, в той же сессии или
в новой. Свободный агент новой задачи начинает сразу и ждёт остальных в `wait()`, а каждый `wait()` — это ход модели и
токены. Пока задача `BLOCKED`, её агенты новые задачи не берут, нужен `task unblock` или `task cancel`. Чтобы две задачи
шли параллельно, нужны другие агенты (например, `backend2` и `reviewer2` в `runners.json`), лучше в своих worktree:
владение файлами проверяется только внутри одной задачи.

**Несколько агентов на одной LM Studio.** Каждый агент шлёт запросы из своей сессии, и все они идут одновременно. Если
LM Studio обрабатывает их по одному, запросы встают в очередь и медленнее работают все агенты. Включите параллельные
запросы в настройках загрузки модели, если ваша версия LM Studio это умеет, или дайте части агентов модель поменьше.

**Добавил агента в `runners.json`, а на странице его нет.** Конфиг читается при старте UI: перезапустите его. Ctrl+C
останавливает и runner'ы, и их сессии, поэтому лучше делать это между задачами. Модель и файл инструкций агента
меняются на странице без перезапуска.

**Где указать цену токенов? Почему стоимость «—» или «нет цены для …»?** Стоимость сообщает только Claude Code. Для Qwen
и локальных моделей впишите цены в поле `"prices"` в `runners.json` (доллары за 1 млн токенов, ключ — имя модели из
колонки «Модель»): [Цена токенов](#цена-токенов-если-cli-не-сообщает-стоимость). Правка подхватывается без перезапуска UI.

**Почему у сессии нет токенов («без токенов»)?** CLI сообщает токены в самом конце сессии. Пока сессия идёт, их ещё нет;
у сессии, остановленной кнопкой «Стоп», их не будет; CLI без JSON-вывода (`stream-json`) их не печатает.

**Как поставить рою готовый OpenSpec change?** Выберите его в форме задачи: агенты разделят `tasks.md` по номерам задач,
lead отметит их, а после DONE change архивируется кнопкой. Подробно — [OpenSpec](#openspec-рой-по-готовому-change).

**`AGENTS.md`, `SKILL.md` и `instructionsFile` — что для чего?**

- `AGENTS.md` — протокол роя для интерактивных сессий. CLI читает его из корня проекта в каждой сессии: Codex и Qwen
  сами, Claude Code — через строку `@AGENTS.md` в `CLAUDE.md`.
- `skills/agent-network/SKILL.md` — тот же протокол в виде [skill](#skill-для-агентов): модель загружает его, только когда
  он нужен. Сверх `AGENTS.md` объясняет, как совмещать рой с dev-скиллами (java-dev-flow) и OpenSpec.
- `instructionsFile` — короткая роль одного агента runner'а: что проверять, чего не трогать. Протокол агент runner'а уже
  получает из промпта и из ответов сервера (`nextAction`, `hint`), поэтому `AGENTS.md` в `instructionsFile` не нужен: он
  лишь удлиняет каждый ход. Пример роли — [instructions/reviewer.md](examples/runner/instructions/reviewer.md).

## Если что-то не работает

| Симптом | Причина и решение |
|---|---|
| MCP «disconnected» / `failed to start` | в логе CLI (`~/.qwen/debug/*.txt`, строка `MCP STDERR`): `AGENT_ID environment variable is required` — в конфиге нет `AGENT_ID`; `already registered by a running process` — этот id держит живой процесс (дайте каждому агенту своё имя или используйте пул); `NETWORK_DIR must be an absolute path` |
| Второй агент не подключается | оба CLI читают один глобальный конфиг с одним `AGENT_ID`. Используйте пул `a,b` или отдельные конфиги |
| `HAS_ACTIVE_TASK` | у агента уже есть активная или заблокированная задача: завершите, разблокируйте или отмените её |
| Задача `BLOCKED`, агенты ждут | ревью/интеграция снова нашли ошибки, а раунды исправлений кончились. Посмотрите findings в UI и решите: кнопка «Разблокировать +N» в карточке задачи (или `task unblock --id ...`), либо `task cancel` |
| `wait` обрывается по таймауту клиента | уменьшите `AGENT_NETWORK_WAIT_MS` ниже таймаута tool у CLI (Codex: 60 с) |
| `NO_ACTIVE_TASK` / агент вечно ждёт | задача создана в другой сети (`NETWORK_DIR`) или под другие имена. Ответ `swarm_context` показывает `networkDir`, сверьте его с `--network-dir` у `task create` |
| Модель вызывает tools с пустым `{}` | слабая модель/неподходящий протокол. Для LM Studio поставьте `"wireApi": "chat-completions"` и выберите этот маршрут в `/model`; повторяющееся `Invalid side query response ... shouldBlock` в логе значит, что модель не справляется со структурными ответами: нужна модель сильнее. `exampleCall` у `propose` и `respond` упрощает копирование |
| Агент придумал своё задание | описание задачи было пустым. Отмените (`task cancel`) и создайте с конкретным описанием |
| Новые tools/схемы не видны | CLI запоминает схемы при подключении; перезапустите агента. `npm run build` после правок |
| Агент завис после серии ошибок | перезапустите его, состояние сохранено на диске |
| В UI пусто | UI смотрит в другой каталог, чем агенты |
| Агент `DEAD` в UI | процесс убит, не успев выставить `OFFLINE`; перезапуск займёт то же имя |

## Ограничения и статус

- Одна машина: живость агента определяется по pid, синхронизация идёт через локальную файловую систему (нужна поддержка
  hard links, обычная для macOS/Linux).
- В исходном плане tools было ровно пять; `create_task` добавлен по запросу пользователя (с защитами выше). Нет автоматической оркестрации, декомпозиции задач, интеграции с GitHub/GitLab, автомержа, HTTP/WebSocket-API и баз данных
  (см. [PLAN.md](PLAN.md)). Страница без `--runners` (или с `--read-only`) — только для просмотра; с runner'ами она
  ставит задачи, отвечает агентам, вливает и откатывает результат.
- Сервер не анализирует код. Сборку и тесты запускают агенты (инструмент `build`); интеграцию с PASS сервер принимает
  только при зелёном `verifyCommand` на итоговом коммите (см. [Интеграция](#интеграция-pass-только-после-зелёной-сборки)).
- Протокол барьерный: каждая фаза ждёт всех. Параллельна только IMPLEMENT, поэтому выигрыш по времени есть, только если
  задача делится на сопоставимые независимые части с заранее зафиксированным `interfaces`.
- **Реальные прогоны.** Протокол проверен автотестами на реальных stdio-процессах. Полный цикл до DONE пройден на живых
  Claude Code (haiku/sonnet) на Maven-проекте, включая план на утверждение и критика плана; на Qwen CLI с локальной
  моделью — до IMPLEMENT. Связка Qwen + Claude Code в одной задаче и Codex не проверялись. Качество работы сильно зависит
  от модели.

Правила для самих агентов: [AGENTS.md](AGENTS.md) — единственный источник протокола; skill генерируется из него (`npm run docs:sync`, тест сверяет); skill для CLI со skills (Qwen, Claude Code): [skills/agent-network/SKILL.md](skills/agent-network/SKILL.md). План и принципы дизайна: [PLAN.md](PLAN.md).
