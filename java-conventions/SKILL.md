# Java conventions

Three rules for every Java change in the project. They are short on purpose: they apply to every edit, including a one-line one.

| Rule | What it protects |
|---|---|
| 1. Every class sits in the package of its role | anyone finds a class without searching |
| 2. The API is changed in the spec, the controller implements the generated interface | the spec stays the single source of truth for clients |
| 3. A comment is written only when the code cannot say it | comments that are read, because there are few of them |

The project's own `CLAUDE.md` and the existing code win over this skill when they differ — follow the project and mention the difference in the report.

## 1. Project structure

Packaging is by layer. Under the root package (`com.<company>.<service>`):

```
<Service>Application.java
controller/    REST controllers; each implements a generated *Api interface
service/       business logic, transactions
repository/    Spring Data repositories
entity/        JPA @Entity and the enums they persist
mapper/        entity ↔ generated DTO
config/        @Configuration, @ConfigurationProperties
util/          stateless static helpers with no Spring dependencies
exception/     the project's exceptions and the @RestControllerAdvice handler
client/        calls to external systems (RestClient, Feign, WebClient)
listener/      Kafka / RabbitMQ consumers, @EventListener
scheduler/     @Scheduled jobs
dto/           only DTOs that are NOT in the OpenAPI spec (internal, events, client payloads)
```

Create a package only when its first class appears — no empty `dto/` "for the future".

Dependencies go one way: `controller → service → repository`. A controller does not call a repository; an entity does not leave the service layer. The service maps entity → DTO through `mapper/` inside its transaction, so lazy associations are read while the session is open.

Full rules — where an unusual class goes, naming, `util` and `config` limits, what never goes into `src/main/java` — in [references/project-structure.md](references/project-structure.md). Read it when you create a class whose package is not obvious from the tree above, or a new package.

## 2. API: the spec first, then the generated interface

The REST contract lives in the OpenAPI spec. openapi-generator runs with `interfaceOnly=true`: it generates `*Api` interfaces and models, and the controller implements the interface.

When an endpoint is added or changed:

1. **Edit the spec**, not the controller. Find it via `<inputSpec>` of `openapi-generator-maven-plugin` in `pom.xml` (or `inputSpec` of `openApiGenerate` in `build.gradle`).
2. **Generate**: `./mvnw -q generate-sources` / `./gradlew openApiGenerate`.
3. **Read the generated interface** in `target/generated-sources/openapi/…` (`build/generate-resources/…` for Gradle) and copy the method signature from there — do not guess it from the spec.
4. **Implement it in the controller** with `@Override`:

```java
@RestController
@RequiredArgsConstructor
public class OrdersController implements OrdersApi {

    private final OrderService orderService;

    @Override
    public ResponseEntity<OrderDto> getOrder(Long orderId) {
        return ResponseEntity.ok(orderService.getOrder(orderId));
    }
}
```

5. **Check that every new operation has an `@Override`.** With `interfaceOnly` the generated methods are usually `default` and return `501 NOT_IMPLEMENTED`, so a forgotten method still compiles and fails only at runtime.

Do not:
- write `@GetMapping` / `@PostMapping` on a controller method — the mapping comes from the interface; a hand-written endpoint is invisible to clients of the spec;
- repeat `@PathVariable`, `@RequestBody`, `@Valid`, `@RequestParam` on the implementation — they are inherited from the interface;
- put `@RequestMapping` on the controller class — the base path is already set by the interface or `openapi.*.base-path`;
- write your own DTO that duplicates a generated model, or edit generated files — they are overwritten on the next build;
- change an existing field, its type or `required` without saying in the report that it breaks the contract for clients.

Details — a new tag, a name clash between a model and an entity, old controllers without an interface, a user explicitly asking for an endpoint outside the spec — in [references/openapi-workflow.md](references/openapi-workflow.md). Read it when the change creates a new `*Api` interface or does not fit the five steps above.

## 3. Comments

Comments are in **Russian**. The default is no comment: a reader trusts the comments that are left only when there are few of them, and every comment that restates code is one more thing to keep true.

**A line comment** is written only when the code cannot tell *why*: a business rule from outside the code, a non-obvious constraint, a workaround, an order that matters, the origin of a number. Up to **5 words**. Do not comment *what* the code does: if that is unclear, rename a variable or extract a method instead. A ticket key (`ORD-123`) does not count towards the 5 words.

```java
// плохо
// получаем заказ по id
Order order = orderRepository.findById(id).orElseThrow();
// проверяем статус
if (order.getStatus() == OrderStatus.PAID) { … }

// хорошо — комментарий не нужен
Order order = orderRepository.findById(id).orElseThrow();
if (order.isPaid()) { … }

// хорошо — причина, которую код не скажет
// банк отклоняет суммы ниже 10
if (amount.compareTo(MIN_BANK_AMOUNT) < 0) { … }
```

**Class Javadoc.** First decide whether it is needed: the name and package already say what `OrderService`, `OrderRepository` or `OrderMapper` are — then there is no Javadoc. It is needed when the class has something the name does not show: a boundary of responsibility, an invariant, thread-safety, an unusual lifecycle. Up to **20 words**, one or two sentences, without retelling the name.

```java
/**
 * Повторно отправляет платежи, зависшие в PENDING дольше 15 минут. Идемпотентен по paymentId.
 */
public class PendingPaymentRetrier { … }
```

**Method Javadoc** — by the same test and the same 20 words: only when the contract is not visible from the signature (returns `null`, a side effect, which exception and when).

Never write:
- comments that restate code, `@param id идентификатор`, `@return результат`;
- dividers and labels: `// ===== геттеры =====`, `// конструктор`, `// поля`;
- `@author`, `@since`, `@version`;
- commented-out code — git keeps history;
- `TODO` without a ticket key.

Comments in code you do not change stay as they are — they are not your diff. A comment your change made false — fix it or remove it.

**Before you finish**, run the check on your changes and go through every comment it lists:

```bash
python3 <this-skill>/scripts/check_comments.py            # uncommitted changes + new files
python3 <this-skill>/scripts/check_comments.py main...HEAD # a branch
```

It flags line comments over 5 words, Javadoc over 20 words, `@author` / `@since`, labels like `// геттеры`, likely commented-out code and TODOs without a ticket, and prints every other added comment for a quick look. It does not judge whether a short comment is needed at all — that is your call by the rules above.

## In the report

One line per rule if something deviated: a class placed outside the tree and why, an endpoint outside the spec at the user's request, a contract-breaking spec change. Nothing deviated — say nothing.
